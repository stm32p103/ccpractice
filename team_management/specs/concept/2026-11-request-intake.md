# 依頼の受付(チーム業務補佐プラグイン 第1弾)

## 1. 背景・困りごと
- チームは別チームから依頼を受け、作業・設計・実装・評価をして納める
- 依頼の入口がばらばらだと、取りこぼしや納期の認識違いが起きる
- Issue 上のやり取りが長くなると、合意事項と未決事項が追えなくなる

## 2. 目的(できるようになると嬉しいこと)
- Issue をチーム外との唯一の窓口にする
- 依頼を「受付済」として管理下に置き、取りこぼしを無くす
- 納期、実施事項、担当の合意を依頼ファイルに残す
- 過去の似た依頼と対応をすぐ引ける

## 3. 想定する利用者
| 利用者 | 立場・頻度 | 主な目的 |
|---|---|---|
| メンバー | チームの担当者。毎日 | 受付の指示、依頼ファイルの確認、問い合わせの承認 |
| マネージャー | チームの管理者。定例会など | 未受付・受付済・完了の把握 |
| 依頼者 | 別チーム。依頼の都度 | Issue への書き込みのみ。AI は使わない |

### 決まっていること
- 依頼: ラベル「依頼」がついた Issue。受付済はラベル「受付済」で表す
- 受付の起動(TM-D01): Issue に `/受付` とコメントして目印にし、利用者が手元の AI に「受付して」と頼む
  - スクリプトが目印のある Issue を検出する
  - Claude Code / Copilot で同じ動きにする。資格情報は利用者の `gh` のもの
  - 有効な目印: チームメンバーのコメントだけ(TM-D13)
  - 目印の語・メンバーの一覧・ラベル名: 設定ファイル `config/tm.yaml` で変えられる
- 開発と配布を分ける(TM-D12、TM-D15)
  - 開発: `team_management/`(specs、docs、.specify)
  - 配布: リポジトリ直下の `team-desk/`。既存の marketplace に `team-desk` として追加する
- 依頼ファイル(TM-D02): 1 件 1 ファイルの Markdown。先頭に YAML。Pydantic で検査する
  - 機械用の索引は JSONL
- リスト(TM-D03): 受付済リスト・完了リストは依頼ファイルから毎回作り直す。追記しない
- 単純な加工はスクリプトで行う。AI は要約・判断・文案だけを担う

### 外部へのアクセス(TM-D04、TM-D10)
- アクセスしてよい先: 対象リポジトリだけ
  - Web 検索・Web 取得はしない
  - 他のリポジトリ・他のサービスへ書き込まない
  - Issue へのコメント投稿: 対象リポジトリ内なので可
- ファイル: コミット時に人が差分を確認するルールとする。自動の検査は置かない(TM-D11)
  - 理由: 定型で定義できない以上、局所的な自動ガードは油断を招く
  - 漏えいは「リポジトリ外にアクセスしない」ことで防ぐ
- 秘密情報の自動検出(伏字、投稿前の検査): 本要件から外す(TM-D10)
- 依頼ファイル: Issue と同じリポジトリに置く。push も対象リポジトリへのアクセスとして認める(TM-D07)
- 利用者の指示があっても守る。指示文だけに頼らず、仕組みで止める(下表)

| 層 | 止め方 |
|---|---|
| AI のフック(PreToolUse) | Web 系ツールを拒否。`gh` は対象リポジトリだけ許可。Issue への書き込みは `tm.py post` 経由だけ許可 |
| スクリプト | 対象リポジトリは設定ファイルで固定 |
| コミット時 | 差分を確認してからコミットするルール |
| 置き場所 | プラグインのリポジトリにチームのデータを置かない |

### 過去の知見の蓄積(TM-D05、TM-D06)
- 登録するもの: エラーメッセージ、解決の糸口になった特徴的な挙動、原因、対処
- 要約は人が確認してから索引に登録する
- キーワード: 広くヒットする語にする
  - 挙げる: 現象、エラーメッセージ、ツール名、技術名
  - 挙げない: 開発コード、個人名などピンポイントの名称
  - スクリプトで検査する(禁止語リスト: 開発コードのパターン、メンバー名)
- 索引の 1 件(案):

```json
{"id": "REQ-42", "issue": 42, "closed": "2026-11-20",
 "keywords": ["CAN", "タイムアウト", "python-can", "バス負荷"],
 "errors": ["can.CanOperationError: Failed to transmit: Transmit buffer full"],
 "clues": ["送信周期を 10ms 以下にすると数分後に発生"],
 "cause": "送信キューの溢れ", "resolution": "送信周期の見直しと再送処理の追加",
 "links": ["requests/archive/2026/REQ-42.md"], "confirmed_by": "<確認者>"}
```

### 依頼ファイルの形(案)

```markdown
---
schema: 1
id: REQ-42
issue: 42
title: <依頼の件名>
status: accepted          # accepted / closed
stakeholders:             # 複数。依頼者側・チーム側それぞれに役割
  - {who: <ID>, side: requester, role: リーダー}
  - {who: <ID>, side: requester, role: エンジニア}
  - {who: <ID>, side: team, role: 担当}   # side: team が無ければ観点の不足
due: 2026-12-10           # 日付、または出来事の文章("HIJ のテスト開始まで")
due_history:              # 期限の変更履歴
  - {due: 2026-11-27, by: <ID>, on: 2026-11-13}
  - {due: 2026-12-20, by: <ID>, on: 2026-11-18, reason: 開発の延期}
inputs_from_requester:    # 依頼者から受け取るものと時期
  - {item: 試験対象, when: 2026-11-13}
waiting_on:               # 回答待ち。経過日数はスクリプトが計算
  - {who: requester, what: <質問の内容>, asked: 2026-11-22, reminded: [2026-11-28]}
deliverables: [<成果物>]
acceptance: [<受入条件>]
relations:                # 依頼どうしの関係。片方向だけ書き、逆向きはスクリプトが導く
  - {to: REQ-17, type: depends_on, note: 機材Q の設置が先}
source:                   # 変更検知用。スクリプトが書く
  updated_at: 2026-11-13T09:00:00Z
  last_comment_id: 123456789
  body_sha256: <hash>
generated_by: {plugin: <名前>@0.1.0, model: <モデル名>}
---
## 依頼の要約
## 合意事項
## 未決事項
## 過去の事例(第 2 弾)
## 取り込み履歴
```

- 依頼ファイルはチームへの入力だけを書く。チームがやると決めたことは書かない(対応案で別に管理。第 2 段階)
- 「対応案」は、チームがやると決めたことの名前として取っておく。依頼ファイルの節は「過去の事例」と呼ぶ
- 関係の種類(`relations.type`、初期案):
  | type | 意味 | 逆向き(スクリプトが導く) |
  |---|---|---|
  | `depends_on` | 相手が済まないと実行できない | `blocks` |
  | `same_target` | 同じ対象(製品、ベンチ、プロジェクト)を扱う | `same_target` |
  | `duplicates` | 同じ依頼の重複 | `duplicated_by` |
  | `related` | 上のどれでもないが関係がある | `related` |
- 関係の種類の一覧は設定ファイルに置き、使いながら足す(TM-D24)
- 関係の影響(期限の連動など)を知らせるのは第 3 弾の計画管理(TM-D23)
- 関係者(`stakeholders.who`): GitHub の ID。ID が分からない人だけ自由な文字列とし、スクリプトが一覧に出す(TM-D25)
- 日付に年が無いときは、Issue の作成日から年を補う
- 観点: `viewpoints.yaml` に並べる。不足の判定はスクリプト。使いながら追加する
  - 初期案: 納期(出来事のときは具体的な日付が無いと出す)、チーム側の担当、成果物、受入条件、依頼元の窓口、依頼者から受け取るものと時期、回答待ち(経過日数)

### 置き場所と肥大化の対策
| パス | 内容 | AI が読むか |
|---|---|---|
| `requests/open/REQ-<番号>.md` | 進行中の依頼ファイル | 対象の 1 件だけ |
| `requests/archive/<年>/` | クローズ済み | 指示がない限り読まない |
| `kb/index.jsonl` | 知見の索引(1 件 1 行) | 検索で当たった行だけ |
| `lists/*.md` | 未受付・受付済・完了(年別)のリスト | 読まない(生成物) |
| `config/tm.yaml` | 対象リポジトリ、目印の語、メンバーの一覧、ラベル名 | スクリプトのみ |
| `config/viewpoints.yaml`, `config/keywords-deny.yaml` | 観点、禁止語 | スクリプトのみ |

### スクリプト(`tm.py`、LLM 不使用)
| サブコマンド | 内容 |
|---|---|
| `pending` | 未受付(依頼あり・受付済なし)の一覧を Markdown で出す |
| `fetch <番号>` | Issue を取得。前回の取り込みからの差分だけを出す |
| `check` | 受付後に変更・コメント追加があった依頼を一覧にする |
| `validate` | 依頼ファイルの型検査と、観点の不足の一覧 |
| `accept <番号>` | 承認後にラベル「受付済」を付け、リストを作り直す |
| `lists` | 受付済・完了リストを作り直す |
| `close-sync` | クローズした依頼を archive へ移す |
| `kb-search <語>` / `kb-add <file>` | 索引の検索 / 確認済みの知見の登録(禁止語の検査つき) |
| `post <番号> <file>` | 問い合わせの投稿。人の承認 → 投稿(対象リポジトリのみ) |

### ゲート(人の確認)
| ゲート | 直前の処理 | 人が見るもの | 機械が見るもの | 止める条件 |
|---|---|---|---|---|
| G-受付 | ラベル付与・コミット | 依頼ファイルの YAML 部、未決事項、コミットの差分 | `validate` | 型エラー |
| G-問い合わせ | Issue への投稿 | 投稿文 | 投稿先が対象リポジトリか | 未承認、対象外の投稿先 |
| G-知見 | 索引への登録 | 知見の 1 件 | 禁止語 | 禁止語、未確認 |

### トークンの目安(推定。P6 で測る)
| 操作 | AI が読むもの | 目安 |
|---|---|---|
| UC-1, 4, 6, 7 | なし | 0 |
| UC-2 初回 | Issue 全体、スキル、当たった知見数行 | 5〜20k |
| UC-5 再受付 | 差分と今の依頼ファイル | 2〜5k |
| UC-8 知見 | 依頼ファイルのみ(Issue は読み直さない) | 約 2k |

## 7. 却下した案(理由つき)
- GitHub 上で AI を自動起動(TM-D01 b): 環境で動きが変わる。外部への経路が増える
- Markdown と JSON を別ファイルで持つ(TM-D02 b): 食い違いが起きる
- リストへの追記(TM-D03 b): 手直しでずれる。作り直しなら何度でも同じ結果
- キーワードに開発コード・個人名: 検索に当たりにくい。名称の流出にもなる
- 秘密情報の自動検出(伏字、投稿前・保存前の検査)(TM-D10): 決まった形がなく、誤認しうる
- pre-commit での自動検査(TM-D11 b): 局所的なガードが油断を招く
- 依頼ファイルを別リポジトリに置く(TM-D07 b): アクセスしてよい先が増える
- 誰の目印でも受付とする(TM-D13 b): 依頼者が自分で受付済にできてしまう
- プラグインを別リポジトリに分ける(TM-D12 b): ai-process と同じ配り方を使えない
- `team_management/` 全体を配る(TM-D15 b): 仕様書や Spec Kit の道具まで配られる

## 9. specify への入力
```
/speckit.specify チームへの依頼の受付を補佐する。Issue をチーム外との唯一の窓口とし、ラベル「依頼」の Issue を依頼として扱う。
範囲: 未受付の一覧、受付と依頼ファイルの作成、不足する観点の問い合わせ、受付後の変更の検知と差分での更新、受付済・完了リストの生成、クローズした依頼の archive(UC-1〜UC-7)。
方式: 単純な処理は Python スクリプト(利用者の gh の資格情報で動く)。AI は要約・判断・文案のみ。Claude Code と GitHub Copilot の両方で動く。
データ: 依頼ファイルは 1 件 1 ファイルの Markdown + YAML。Pydantic で検査する。依頼ファイルはチームへの入力だけを書く。
依頼ファイルの項目: 関係者(複数、依頼者側・チーム側と役割)、納期(日付または出来事)と変更履歴、依頼者から受け取るもの、回答待ち、成果物、受入条件、依頼どうしの関係(種類つき)。
受付の目印: チームメンバーが Issue に書いた目印のコメント。目印の語、メンバー、ラベル名は設定ファイルで変えられる。
アクセス: 対象リポジトリだけ(Issue への投稿を含む)。Web 検索・取得はしない。仕組みで止める。ファイルはコミット時に確認する。
対象外: 知見の蓄積と検索、定例会のトピック、計画管理、課題対応管理。
参照: specs/concept/2026-11-request-intake.md
```
