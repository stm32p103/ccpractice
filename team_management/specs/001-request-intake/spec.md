# Feature Specification: 依頼の受付

**Feature Branch**: `001-request-intake`

**Created**: 2026-11-13

**Status**: Draft

**Input**: User description: "チームへの依頼の受付を補佐する。Issue をチーム外との唯一の窓口とし、ラベル「依頼」の Issue を依頼として扱う。範囲: 未受付の一覧、受付と依頼ファイルの作成、不足する観点の問い合わせ、受付後の変更の検知と差分での更新、受付済・完了リストの生成、クローズした依頼の archive(UC-1〜UC-7)。(全文: specs/concept/2026-11-request-intake.md の 9 章)"

## Clarifications

### Session 2026-11-13

- Q: 受付後に人が依頼ファイルを手で直した後で再受付したとき、AI は人の修正をどう扱うか? → A: Issue を正とし、AI が上書きする。人の修正は、コミット前の差分確認で気づく前提とする
- Q: 依頼ファイルを承認して「受付済」ラベルを付ける操作は誰が行うか? → A: メンバーがチャットで承認の語を答えたときだけ、AI がスクリプトを実行してラベルを付ける。メンバーが自分でスクリプトを実行してもよい。承認の語は設定で変えられる
- Q: 受付の前にクローズされた依頼(取り下げ、誤って立てた Issue など)はどう扱うか? → A: 依頼ファイルは作らず、完了リストに「未受付でクローズ」の印を付けて載せる
- Q: 受付したとき、Issue に「受け付けました」とコメントを投稿するか? → A: ラベルの付与と同時に、設定で変えられる定型文を投稿する
- Q: archive 後に、クローズした依頼が再び開かれたらどう扱うか? → A: 依頼ファイルを archive から進行中の置き場所へ戻し、変更の一覧に出す。「受付済」ラベルはそのまま

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 未受付の依頼を一覧にする (Priority: P1)

メンバーまたはマネージャーが、受け付けていない依頼を知りたいときに一覧を出す。
一覧は AI を使わずに作られ、各依頼へのリンクを持つ。

**Why this priority**: 依頼を管理下に置く入口。これが無いと取りこぼしに気づけない。

**Independent Test**: 「依頼」ラベルあり・「受付済」ラベルなしの Issue を含む対象リポジトリで一覧を出し、該当する Issue だけが並ぶことを確かめる。

**Acceptance Scenarios**:

1. **Given** 「依頼」あり・「受付済」なしの Issue が 2 件、「依頼」「受付済」両方ありの Issue が 1 件ある, **When** 利用者が未受付の一覧を求める, **Then** 2 件だけが件名とリンクつきで Markdown に並ぶ
2. **Given** 未受付の依頼が 0 件, **When** 利用者が一覧を求める, **Then** 「未受付の依頼はありません」と示す
3. **Given** 利用者が AI に「未受付の依頼を出して」と頼む, **When** AI が応じる, **Then** AI は決まった処理を実行してその結果を示し、Issue の中身を自分で読まない

---

### User Story 2 - 依頼を受け付け、依頼ファイルを作る (Priority: P1)

メンバーが依頼者と Issue でやり取りし、ある程度まとまった段階で Issue に受付の目印を書く。
その後、手元の AI に受付を頼むと、Issue と全コメントを読み込み、要約を依頼ファイルとして保存する。
不足する観点があれば一覧で示す。メンバーが内容を確認して承認すると、Issue に「受付済」ラベルが付く。

**Why this priority**: 本機能の中心。合意事項・未決事項・回答待ちを 1 か所にまとめ、取りこぼしを防ぐ。

**Independent Test**: 架空の依頼(評価ケース)を入力に受付を行い、依頼ファイルの項目と不足する観点の一覧が期待どおりかを確かめる。

**Acceptance Scenarios**:

1. **Given** メンバーが目印を書いた依頼の Issue, **When** メンバーが AI に受付を頼む, **Then** 依頼ファイルが 1 件作られ、関係者、納期、成果物、受入条件、依頼者から受け取るもの、回答待ち、未決事項が書かれる
2. **Given** 依頼者が途中で期限を変えた Issue(11/27 → 12/20), **When** 受付する, **Then** 納期は最新の 12/20 で、変更履歴に 2 件が残る
3. **Given** 納期が「HIJ のテスト開始まで」と出来事で書かれた Issue, **When** 受付する, **Then** 納期は出来事として保存され、不足する観点に「具体的な日付が無い」と出る
4. **Given** チームが依頼者に質問し、回答が無い Issue, **When** 受付する, **Then** 回答待ちとして、質問の内容、質問した日、催促した日が残る
5. **Given** チーム側の担当者がいない Issue, **When** 受付する, **Then** 不足する観点に「チーム側の担当」が出る
6. **Given** 依頼ファイルの内容, **When** メンバーがチャットで承認の語を答える、または自分でラベル付けの処理を実行する, **Then** Issue に「受付済」ラベルが付き、受付の定型文が投稿され、受付済リストに載る
7. **Given** 依頼ファイルの内容, **When** メンバーが承認の語以外(「いいね」など)で答える, **Then** ラベルは付かず、承認の語を案内する
8. **Given** チームメンバー以外(依頼者など)が目印を書いた Issue, **When** 受付を頼む, **Then** 受付を行わず、有効な目印が無いことを示す

---

### User Story 3 - 不足する観点を Issue で問い合わせる (Priority: P2)

受付で不足する観点が見つかったとき、メンバーが求めれば AI が問い合わせの文案を作る。
メンバーが承認した文だけが、その依頼の Issue にコメントとして投稿される。

**Why this priority**: 不足を見つけるだけでは埋まらない。ただし手で問い合わせても代えられるので P2。

**Independent Test**: 不足する観点がある依頼ファイルから文案を作り、承認の前には投稿されないこと、承認の後に対象の Issue にだけ投稿されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 納期と受入条件が不足している依頼, **When** メンバーが問い合わせを求める, **Then** 2 つの観点を尋ねる文案が示され、まだ投稿されない
2. **Given** 文案, **When** メンバーが承認する, **Then** 対象の Issue にだけコメントが投稿され、依頼ファイルの回答待ちに追加される
3. **Given** 文案, **When** メンバーが承認しない, **Then** 何も投稿されない

---

### User Story 4 - 受付後の変更を検知し、差分で更新する (Priority: P2)

受付の後に Issue の本文が変わったり、コメントが増えたりした依頼を、AI を使わずに一覧にする。
メンバーが Issue に再び目印を書いて受付を頼むと、AI は前回の取り込み以降の変更だけを読み、依頼ファイルを更新する。

**Why this priority**: 受付後の期限変更や追加の依頼を見落とさないため。初回の受付ができてから意味を持つので P2。

**Independent Test**: 受付後にコメントを追加した評価ケースで、変更の一覧に載ること、更新時に AI へ渡す内容が追加分だけであることを確かめる。

**Acceptance Scenarios**:

1. **Given** 受付後にコメントが 1 件増えた依頼と、変化の無い依頼, **When** 利用者が変更の確認を求める, **Then** 前者だけが、増えたコメントの数とリンクつきで一覧に出る
2. **Given** 受付後に依頼者が期限の変更をコメントした依頼, **When** メンバーが目印を書いて受付を頼む, **Then** AI には前回以降のコメントと今の依頼ファイルだけが渡り、納期と変更履歴が更新される
3. **Given** 変化の無い依頼, **When** 受付を頼む, **Then** 依頼ファイルを変えず、変化が無いことを示す

---

### User Story 5 - リストの作り直しとクローズした依頼の archive (Priority: P3)

受付済リストと完了リストを、依頼ファイルと Issue の状態から AI を使わずに作り直す。
クローズした依頼の依頼ファイルは archive へ移し、以後は指示が無い限り AI が読まない。

**Why this priority**: 文書の肥大化を防ぎ、全体を見渡せるようにする。受付が回り始めてから必要になるので P3。

**Independent Test**: 進行中 2 件・クローズ 1 件の状態で作り直しと archive を行い、リストの内容と依頼ファイルの置き場所を確かめる。2 回目を実行しても結果が変わらないことも確かめる。

**Acceptance Scenarios**:

1. **Given** 受付済の依頼が 2 件、クローズした依頼が 1 件, **When** 利用者がリストの作り直しを求める, **Then** 受付済リストに 2 件、その年の完了リストに 1 件が載る
2. **Given** クローズした依頼, **When** archive を行う, **Then** 依頼ファイルが進行中の置き場所から、その年の archive へ移る
3. **Given** 一度作り直した後, **When** もう一度作り直す, **Then** リストの内容は変わらない

---

### Edge Cases

- 目印が複数回書かれている: 最後の目印を有効とし、それより後に増えたコメントは次回の受付で取り込む
- 受付の前にクローズされた依頼: 依頼ファイルを作らず、完了リストに「未受付でクローズ」として載せる(FR-032)
- クローズした依頼が再び開かれた: archive から進行中の置き場所へ戻し、変更の一覧に出す。ラベルはそのまま(FR-034)
- 「依頼」ラベルが後から外された: 一覧の対象から外す。依頼ファイルがあれば変更の一覧に出し、扱いを人に委ねる
- 日付に年が無い: Issue の作成日から年を補い、補ったことを依頼ファイルに記録する
- 関係者の GitHub ID が分からない: 自由な文字列で書き、ID の無い関係者の一覧に出す
- 人が依頼ファイルを手で直した後に再受付した: Issue の内容で上書きする(FR-031)。失われる修正は、コミット前の差分で人が気づく
- 依頼ファイルが型に合わない(人が手で書き換えた など): 検査で場所と理由を示し、リストの作り直しでは飛ばして警告する
- 対象リポジトリ以外の Issue の URL を渡された: 読み込まず、対象外であることを示す
- 資格情報が無い、または権限が足りない: 何も変更せず、必要な操作を示す

## Requirements *(mandatory)*

### Functional Requirements

**依頼と受付の判定**

- **FR-001**: 「依頼」ラベルのある Issue を、チームへの依頼として扱わなければならない
- **FR-002**: 「受付済」ラベルのある依頼を受付済、無い依頼を未受付として扱わなければならない
- **FR-003**: 受付の目印は、チームメンバーが書いたコメントだけを有効としなければならない
- **FR-004**: ラベル名、目印の語、承認の語、受付の定型文、チームメンバーの一覧、対象リポジトリ、観点の一覧、関係の種類の一覧を、設定で変えられなければならない

**未受付の一覧(US1)**

- **FR-005**: 未受付の依頼を、件名とリンクつきの Markdown で一覧にできなければならない
- **FR-006**: 一覧の作成は AI を使わない決まった処理で行い、利用者自身の資格情報で実行できなければならない
- **FR-007**: 利用者が AI に一覧を求めたとき、AI はその決まった処理を実行して結果を示さなければならない

**受付と依頼ファイル(US2)**

- **FR-008**: 有効な目印がある依頼について、Issue の本文と全コメントを読み込み、依頼ファイルを 1 件作らなければならない
- **FR-009**: 依頼ファイルは、人が読める文章と、機械で集計できる構造化された項目を 1 つのファイルに持たなければならない
- **FR-010**: 依頼ファイルは次の項目を持たなければならない: 関係者(複数。依頼者側・チーム側の別と役割)、納期(日付または出来事)、納期の変更履歴、依頼者から受け取るものと時期、回答待ち(相手、内容、質問日、催促日)、成果物、受入条件、依頼どうしの関係(種類つき)、要約、合意事項、未決事項、取り込み履歴
- **FR-011**: 依頼ファイルには、チームへの入力だけを書き、チームがやると決めたことを書いてはならない
- **FR-012**: 依頼ファイルには、取り込んだ時点の Issue の状態(最終更新日時、最後のコメント、本文の要約値)を記録しなければならない
- **FR-013**: 依頼ファイルには、作成に使った本機能の版とモデル名を記録しなければならない
- **FR-014**: 依頼ファイルの型を、AI を使わない決まった処理で検査し、違反の場所と理由を示さなければならない
- **FR-015**: 設定した観点ごとに不足を AI を使わずに判定し、一覧で示さなければならない。初期の観点は、納期(出来事なら具体的な日付が無いとする)、チーム側の担当、成果物、受入条件、依頼元の窓口、依頼者から受け取るものと時期、回答待ち(経過日数つき)とする
- **FR-016**: メンバーが依頼ファイルを承認したときだけ、Issue に「受付済」ラベルを付けなければならない。付ける方法は次の 2 つとし、どちらも同じ決まった処理を使う
  - メンバーがチャットで承認の語(初期値「承認」)を答えたときだけ、AI がその処理を実行する
  - メンバーが自分でその処理を実行する
  - AI がラベルを直接付けてはならない
- **FR-033**: その処理は、ラベルの付与と同時に、設定した定型文を受付の通知として Issue に投稿しなければならない。定型文は AI が作らない
- **FR-017**: 関係の種類は、初期を「実行に必要(依存)」「同じ対象」「重複」「その他の関係」とし、片方向だけを記録して、逆向きは決まった処理で導かなければならない

**問い合わせ(US3)**

- **FR-018**: 不足する観点について、問い合わせの文案を作れなければならない
- **FR-019**: Issue への投稿は、メンバーが承認した文だけを、対象リポジトリのその依頼の Issue にだけ行わなければならない
- **FR-020**: 投稿した問い合わせは、依頼ファイルの回答待ちに加えなければならない

**変更の検知と更新(US4)**

- **FR-021**: 受付済の依頼について、取り込んだ時点から本文の変更やコメントの追加があったものを、AI を使わずに一覧にできなければならない
- **FR-022**: 再受付では、前回の取り込み以降の変更分と今の依頼ファイルだけを AI に渡し、依頼ファイルを更新しなければならない
- **FR-023**: 再受付の内容を、取り込み履歴に日付とともに残さなければならない
- **FR-031**: 依頼の内容は Issue を正とする。再受付では、人が依頼ファイルを手で直した箇所も Issue の内容で上書きしてよい。依頼ファイルだけで合意を変えてはならず、合意の変更は Issue に書いてから再受付する

**リストと archive(US5)**

- **FR-024**: 受付済リストと完了リストを、依頼ファイルと Issue の状態から、AI を使わずに毎回作り直さなければならない。追記はしない
- **FR-025**: 完了リストは年ごとに分けなければならない
- **FR-032**: 受付の前にクローズされた依頼は、依頼ファイルを作らず、完了リストに「未受付でクローズ」の印を付けて載せなければならない。印の有無で、受付した依頼の完了と区別できなければならない
- **FR-026**: クローズした依頼の依頼ファイルを、AI を使わずに年ごとの archive へ移さなければならない
- **FR-027**: AI は、指示が無い限り archive とリストを読んではならない
- **FR-034**: archive にある依頼の Issue が再び開かれたら、AI を使わずに依頼ファイルを進行中の置き場所へ戻し、変更の一覧に出さなければならない。「受付済」ラベルは変えない

**アクセスの範囲と両対応**

- **FR-028**: 外部へのアクセスは対象リポジトリ(Issue の読み書き、依頼ファイルの push)だけとし、Web 検索・Web 取得をしてはならない。利用者の指示があっても守り、AI への指示文だけでなく仕組みで止めなければならない
- **FR-029**: ファイルの保存はコミットの前に人が差分を確認する運用とし、自動の秘密情報検査は行わない
- **FR-030**: US1〜US5 は、Claude Code と GitHub Copilot のどちらから使っても、同じ入力に対して同じ構造の結果にならなければならない

### Key Entities *(include if feature involves data)*

- **依頼**: 「依頼」ラベルのある Issue。未受付・受付済・クローズの状態を持つ
- **受付の目印**: チームメンバーが依頼の Issue に書くコメント。最後の有効な目印が受付の区切りになる
- **依頼ファイル**: 依頼 1 件に 1 つ。要約と構造化された項目を持つ。進行中と archive の 2 つの置き場所がある
- **関係者**: 依頼ファイルの項目。GitHub ID(分からなければ自由な文字列)、依頼者側かチーム側か、役割を持つ
- **納期と変更履歴**: 日付または出来事。変更ごとに、新しい納期、変えた人、日付、理由を持つ
- **依頼者から受け取るもの**: 物や情報と、受け取る時期
- **回答待ち**: 相手、内容、質問日、催促日。経過日数は決まった処理で計算する
- **依頼どうしの関係**: 相手の依頼、種類、補足
- **観点**: 不足を判定する項目の一覧。設定で増やせる
- **取り込みの記録**: 取り込んだ時点の Issue の状態。変更の検知と差分の切り出しに使う
- **受付済リスト・完了リスト**: 依頼ファイルから作り直す生成物。人が見るためのもので、AI は読まない
- **設定**: 対象リポジトリ、ラベル名、目印の語、承認の語、受付の定型文、チームメンバー、観点、関係の種類

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 未受付の一覧、変更の一覧、リストの作り直し、archive は、AI の利用量 0 で行える
- **SC-002**: 依頼 200 件までのリポジトリで、未受付の一覧を 1 分以内に出せる
- **SC-003**: 評価ケース(基本、観点の不足、受付後の変更)で、期待する観点の不足・回答待ち・納期の変更をすべて拾う(見逃し 0 件)
- **SC-004**: 再受付で AI に渡す内容は、前回以降の変更分と今の依頼ファイルに限られ、初回の受付で渡す内容の半分以下になる(コメントが十分にある依頼で測る)
- **SC-005**: リストの作り直しを 2 回続けて行ったとき、結果の差は 0 になる
- **SC-006**: メンバーが受付 1 件を確認・承認するのにかかる時間は 5 分以内(構造化された項目と未決事項だけを見ればよい)
- **SC-007**: 全操作を通して、対象リポジトリ以外へのアクセスは 0 件
- **SC-008**: 同じ評価ケースを Claude Code と GitHub Copilot で実行し、依頼ファイルの構造化された項目の型検査がどちらも通る

## Assumptions

- 利用者(メンバー、マネージャー)は手元で AI(Claude Code または GitHub Copilot)と GitHub の資格情報を使える。依頼者は Issue に書き込むだけで、AI を使わない
- 依頼ファイル、リスト、設定は、Issue と同じ対象リポジトリに置く(TM-D07)
- 依頼ファイルのコミットと push は、差分を確認したメンバーが行う
- 受付の起動は手元から行う。GitHub 上で AI を自動起動しない(TM-D01)
