# 04. バージョンアップ

## 1. 種類と考え方

| 種類 | 例 | データ形式 | 作業の中身 | 頻度 |
|---|---|---|---|---|
| **マイナー** | 18.4 → 18.5 | 互換(そのまま使える) | バイナリの入れ替え + 再起動 | セキュリティ修正を含むので定期的に |
| **メジャー** | 17 → 18 | **変わる** | `pg_upgrade`、または dump / restore | 年1回程度。サポート終了の前に計画する |

どちらも、**作業前に `upgrade-prep.ps1` で点検とバックアップ取得**を行い、NG を残したまま進みません。

## 2. 共通の準備: `upgrade-prep.ps1`

更新する**すべてのサーバー**(main と backup、別PCならそれぞれのPC)で、更新作業の前に実行します。停止や設定変更は行いません。

```powershell
.\upgrade-prep.ps1 -ServerId prod-b -TargetVersion 18.5      # 点検 + ダンプ + レポート
.\upgrade-prep.ps1 -ServerId prod-a -TargetVersion 19        # メジャーの場合
.\upgrade-prep.ps1 -ServerId trial-a -SkipDump               # 点検だけ(ダンプなし。サービス停止中でも可)
```

| 実施内容 | 見るポイント |
|---|---|
| サービス状態・起動アカウント | 台帳との一致 |
| バイナリとデータのバージョン、台帳の `pg_major` | 食い違いは WARN(台帳を直す) |
| 更新種別(`-TargetVersion` 指定時) | マイナーかメジャーか。ダウングレードは NG |
| クラスタの実体(main / スタンバイ)と台帳の役割 | 食い違いは WARN。**先に原因を確認する** |
| ディスク空き容量(バックアップ先) | データサイズに対して不足なら WARN |
| 設定ファイルの退避(`config\`) | `postgresql.conf` / `pg_hba.conf` など |
| ダンプ(`globals.sql`、DBごとの `*.dump`)と `pg_restore -l` による読み取り確認 | ダンプが読めない場合は NG |
| 拡張機能・エンコーディング・レプリケーション状況 | メジャー更新では、拡張機能が新バージョンに存在するか確認する |

- 出力先は台帳の `backup_dir` 配下の `upgrade-prep_<ServerId>_<日時>\`。`report.md` に結果と「次の手順」が出ます。
- DB のパスワードは対話入力です(`-PgUser` で変更可。既定は `postgres`)。ファイルには残りません。
- **バックアップ機で取る場合**、スタンバイ上の長い `pg_dump` はレプリケーションとの競合で失敗することがあります。失敗したらメインで実行してください([02 §1](02-daily-operations.md))。
- NG が1つでもあると終了コード 1 になります。**解消するまで更新に進まない**でください。
- ダンプは必ず一度は**復元テスト**(別名DBへ `pg_restore`)をしておきます。

## 3. マイナーアップデート

### 順序: バックアップ → メイン

先にバックアップ機で動作を確認し、問題がなければメインを更新します。

| 手順 | バックアップ機(`prod-b`) | メイン機(`prod-a`) |
|---|---|---|
| 0 | 更新内容(リリースノート)を確認する。特別な手順(再インデックスなど)が書かれていないか | 同左 |
| 1 | `upgrade-prep.ps1 -ServerId prod-b -TargetVersion <版>` | `upgrade-prep.ps1 -ServerId prod-a -TargetVersion <版>` |
| 2 | – | (バックアップ機の更新が終わってから)アプリを停止する |
| 3 | `.\service.ps1 -Action Stop -ServerId prod-b` | `.\service.ps1 -Action Stop -ServerId prod-a` |
| 4 | 新しいマイナーバージョンのインストーラーで更新する(インストール先・データディレクトリ・サービスアカウントが変わらないことを確認) | 同左 |
| 5 | `.\service.ps1 -Action Start -ServerId prod-b`(メインが動いているので起動できる) | `.\service.ps1 -Action Start -ServerId prod-a` |
| 6 | `Status` で受付中・起動アカウント一致。メインの `pg_stat_replication` が `streaming` | 同左。アプリを再開して動作確認 |
| 7 | `.\inventory.ps1 -Action Set -ServerId prod-b -Field pg_version -Value <版>` | 同左(`prod-a`) |

- メインを更新する手順2〜5の間は、アプリを止める時間が必要です(通常は短時間)。
- インストーラーが起動アカウントを既定に戻した場合は、`services.msc` で台帳のアカウントに戻して再起動します(`Status` の警告で気づけます)。
- **ロールバック**: マイナー更新は、インストーラーで旧版へ戻すのが難しい場合があります。そのため「バックアップ機で先に更新 → 問題があればバックアップ機を作り直す(メインは無傷)」の順序にしています。メイン更新後に問題が出たら、ダンプから復元する前に、更新していない側(旧版のまま)の状態を確認してください。

## 4. メジャーバージョンアップ

メジャーを跨いだストリーミング更新はできません。**メインを更新し、バックアップ機は作り直す**流れです。

### 方式の選択

| 方式 | 特徴 | 向く場合 |
|---|---|---|
| `pg_upgrade` | 速い。`--link` を使うと旧データを共有するため、実行後は旧環境に戻れなくなる(バックアップ必須) | データが大きい、ダウンタイムを短くしたい |
| dump / restore | 単純で確実。新クラスタへ論理的に復元する。サイズに応じて時間がかかる | **小規模(まずはこちらを推奨)** |

### 手順(共通部分)

1. `upgrade-prep.ps1 -ServerId prod-a -TargetVersion <新メジャー>` を実行し、NG が無いこと、拡張機能が新版で使えること、ダンプの復元テストが済んでいることを確認する。
2. 新メジャーを、**別のインストール先・別のデータフォルダ・別ポート**にインストールする(旧環境は残す)。データフォルダには、既存のサービスアカウントのACLを付与する(`user.ps1 -Action Create` はアカウントが既にあればACLだけ付与する)。
3. アプリを停止する。
4. 旧メインのデータを新環境へ移す。
   - **dump / restore の場合**: 旧サーバーから、**新バージョンの `pg_dump` / `pg_dumpall`** でダンプを取り、新クラスタへ `globals.sql` → `pg_restore` の順に復元する(新版のツールで取るのが推奨)。
   - **`pg_upgrade` の場合**: 旧メインを停止し、新バージョンの `pg_upgrade` で `--check` → 本実行(`--link` はロールバック不可に注意)。`pg_upgrade` の実行ユーザーや権限は、公式ドキュメントの Windows の注記を確認する(管理者で失敗する場合は、サービスアカウント等の非管理者で実行する)。
   ```powershell
   & "<新bin>\pg_upgrade.exe" -b "<旧bin>" -B "<新bin>" -d "<旧data>" -D "<新data>" --check
   ```
5. 新メインを起動して動作確認し、アプリの接続先を切り替える。
6. 統計情報を作り直す: `vacuumdb --all --analyze-in-stages`(新バージョンの `bin` から実行)。
7. **台帳を更新する**(`inventory.ps1 -Action Set`): `service_name` / `install_dir` / `bin_dir` / `data_dir` / `port` / `pg_major` / `pg_version`。
8. **バックアップ機を作り直す**: バックアップ機にも新メジャーをインストールし、新メインから `pg_basebackup`([01 §3-4](01-architecture.md))。台帳も同様に更新する。
9. `pg_dump` を取り直し、`.\inventory.ps1 -Action Validate` と `.\service.ps1 -Action Status` で整合を確認する。
10. 旧環境は、一定期間(例: 数週間)残してからアンインストール・データ削除する。**旧環境のサービスアカウントは新環境でも使う場合は削除しない**(`user.ps1 -Action Delete` は使用中のサービスがあると拒否する)。

## 5. バージョンアップ後チェックリスト

- [ ] `Status`: 全サーバーが Running・受付中、起動アカウント一致、警告なし
- [ ] メインの `pg_stat_replication` が `streaming`、`replay_lag` が小さい
- [ ] アプリの動作確認(主要な機能)
- [ ] 台帳の `pg_version` / `pg_major` / パス類が実態と一致(`Validate` で NG なし)
- [ ] 更新後のダンプを取得し、復元テストをした
- [ ] 旧バージョンの残置物(メジャー更新時)の撤去予定日を決めた

## 6. 台帳との対応(更新する項目)

| 作業 | 更新する台帳項目 |
|---|---|
| マイナー更新 | `pg_version` |
| メジャー更新 | `pg_major` / `pg_version` / `service_name` / `install_dir` / `bin_dir` / `data_dir` / `port`(新しくなった項目すべて) |
| 旧環境の撤去 | 台帳に旧環境の行を作っていた場合は `status = retired` |
