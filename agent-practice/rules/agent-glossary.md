# エージェント用語集

- 対象: エージェント定義で使う用語
- 対象外: ドメイン駆動設計の用語

| 用語 | 意味 |
|---|---|
| 開発者 | エージェントに指示を出す人 |
| Agent Architect | エージェントを設計するエージェント |
| Coordinator | 利用時の窓口。依頼を振り分け、工程を進め、指示を中継する |
| 開発者対話型 | 開発者と直接対話するエージェントの種別 |
| ワーカー型 | エージェントの指示で動くエージェントの種別 |
| 親 | 指示を出すエージェント |
| 問い合わせ | エージェントから開発者への質問 |
| オープンな問い合わせ | 未解決の問い合わせ |
| 実行環境 | コード生成・テストを実施する環境。Claude のクラウド環境、GitHub の CI、ローカル環境 |
| 構想 | やりたいことから、エージェントと成果物のつながりを決める工程 |
| 構成 | エージェントと成果物のつながり |
| 構成例 | 構成の一般的な型 |
| 成果物 | エージェントが作成し、他のエージェントや開発者に渡すもの |
| 骨組み | 構想で決めた項目のみ記入したエージェント定義 |
| 未決 | エージェント定義で詰めていない項目 |
| 開発構想 | 開発者が提示する、アプリケーションでやりたいこと。`concept.md` にまとめる。エージェントの「構想」とは別 |
| 構想フォルダ | 開発構想ごとの作業フォルダ。`concepts/<x>` |
| 分野 | アナリストと設計者の担当範囲。`domain`、`api`、`persistence`、`auth`、`frontend`、`ops`。記号は `<y>` |
| 対象 | 分野内の仕様の単位。アナリストが分ける。記号は `<z>` |
| アナリスト | 分野ごとに提案と仕様の更新を担当するエージェント |
| 仕様チェッカ | 提案仕様と仕様の整合を確認するエージェント |
| 設計者 | 分野ごとにワーカーの選定、作業指示の作成、レビューを担当するエージェント |
| テスター | テストを実行し、結果を解析するエージェント。`backend`、`frontend`、`ops`、`e2e` |
| ワーカー | 実装とテスト作成を担当するエージェント。軽量ワーカーと通常ワーカー。種別のワーカー型とは別 |
| 軽量ワーカー | ロジックがほとんどないコードを担当するワーカー |
| 通常ワーカー | 軽量ワーカーの対象以外すべてを担当するワーカー |
| 中継 | エージェントの成果物を、Coordinator が次のエージェントに渡すこと |
| 提案 | アナリストが作成する分野ごとの対応案。`<y>.<z>.proposal.md` |
| 提案仕様 | 提案を統合し整合させた全体の案。`proposal.md` |
| 仕様 | 分野・対象ごとの確定した内容。`requirements/<y>/<z>.md` |
| 作業指示 | 設計者がワーカーに出す指示。`tasks/<y>.<z>.<n>.md` |
| レビュー結果 | 設計者による成果物と仕様の比較結果。`reviews/<y>.<z>.md` |
| テスト結果 | テスターによる OK/NG のサマリと NG の内容。`test-results/<テスター名>.md` |
| 軽微な未決事項 | 仮の判断で進め、開発者の決定を待つ詳細。提案時は提案ファイル内、それ以外は `<入力文書>.todo.md`。エージェント定義の「未決」とは別 |
| 問い合わせの下書き | ワーカー型が作成する、ID のない問い合わせ。提案時は提案ファイル内、それ以外は `<入力文書>.inquiry.md`。Coordinator が ID を発行する |
| ハンドラ | コマンド・クエリを受け、処理の手順とトランザクションを担当するコード。`api` 分野が担当 |
| API 契約 | API のメソッド、パス、リクエスト、レスポンス、エラー、必要な権限の取り決め。`api` 分野の仕様が正 |
| クエリ用のインターフェース | クエリのデータ取得の取り決め。定義は `api` 分野、実装は `persistence` 分野 |
| トランザクションのインターフェース | ハンドラがトランザクションを扱う取り決め。定義は `api` 分野、実装は `persistence` 分野 |
| ORM モデル | テーブルに対応する ORM のクラス。ドメインモデルとは別 |
| マッパー | ORM モデルとドメインモデルを変換するコード。`persistence` 分野が担当 |
| セッション | サーバー側で保持するログイン状態。定義は `auth` 分野、保存は `persistence` 分野 |
| Depends | FastAPI のエンドポイントごとの依存の宣言。認可に使う |
| 初期状態の拒否 | 権限の宣言がない API へのアクセスを許可しないこと |
| 初期管理者 | 最初のログインに使う管理者。手順の定義は `auth` 分野、スクリプトへの組み込みは `ops` 分野 |
| CSP | ブラウザの通信先を制限する設定。内容は `frontend` 分野、ヘッダーの付与は `api` 分野 |
| 必須の基準 | `frontend` 分野の依存ライブラリが満たす条件。外部通信がないことなど。`frontend-analyst.md` に記載 |
| 試行環境 | 開発者が動作を試す環境。ホットリロードが使える |
| 本番環境 | 利用者に提供する環境。スクリプトの実行は開発者のみ |
| 検証用環境 | 本番環境のスクリプトを確認する環境。本番環境とは別 |
| 自己署名証明書 | 外部の認証局を使わず自分で発行する HTTPS の証明書 |
| センシティブなデータ | 外部に送らないデータ。対象は `rules/rule.md` に記載 |
| 確認の観点 | 仕様チェッカが確認する項目。網羅、逸脱、矛盾、分野間の参照、完了条件 |
| 保留 | 仕様チェッカの判定の 1 つ。アナリストの修正では解決できず、開発者に提示する |
| 対象の仕様 | 今回の開発構想で変更する仕様の一覧。`proposal.md` に記載 |
| 仕様項目 | 仕様内の ID を付けた項目。INV-1、API-1 など |
| 仮の判断 | 軽微な未決事項について、開発者の決定まで一般的な事例で進める判断 |
| アプリケーションの組み立て | `main.py` で、ミドルウェアと各分野の実装を接続すること。`api` 分野が担当 |
| `ops` の基盤 | 実装の前に必要な準備。`install`、`test-tools`、テスト専用のデータベース |
| 不安定 | 再実行で結果が変わる E2E テスト。判定は NG のまま |
| 工程の状態 | 開発構想の進行状況と反復の回数。`concepts/<x>/status.md` に記録し、再開に使う |
