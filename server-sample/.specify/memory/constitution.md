# 汎用ジョブ実行基盤 憲章

## 目的

ジョブの受付・キュー管理、ランナーとジョブの管理を、特定の用途・プラットフォームに依存しない汎用部品として作り、
最初の用途(評価機材に接続された Windows PC で動くチェックツールの実行)をその上に載せる。
他の用途(別のツール、別の機材、別の提出元)へ、コアを変更せずに適用できることを目指す。

## 中核原則(Core Principles)

### S. 機密情報の保護(最重要・NON-NEGOTIABLE)

本節は他のすべての原則に優先する。他の原則・要望と衝突する場合は本節を守る。

- **S1. 持ち出し禁止**: ジョブを実行するワーカー(ランナーエージェント、エグゼキュータ、起動した外部ツール)と、
  GitHub Actions のランナー(ワークフロー)は、実行 PC 内の「ジョブ用の作業フォルダ」の外にある情報を、
  外部に送信してはならず、Git にコミットしてはならない。
  対象の情報: 作業フォルダ外のファイル、環境変数、他のサービスの情報(資格情報、トークン、設定、他のジョブの情報を含む)。
- **S2. 書き出し台帳**: 外部へ書き出す情報がある場合は、「どこに(出力先)・何を(内容)・どの条件で」書き出すかを、
  書き出し台帳(inputs/13-security-egress)と、各 spec・plan に明示する。台帳にない書き出しは禁止する。
  書き出しの追加は、台帳の更新とレビューを要する。
- **S3. 既定は拒否**: 既定は「何も送らない」。許可リスト(出力先・内容・パス・環境変数)で許可したものだけを扱い、
  許可リスト外は拒否する。
- **S4. 担保の方法**(plan で実装を決め、テストする):
  - 外部ツールの起動時の環境変数は、空の状態から許可リストの変数だけで組み立てる(親プロセスの環境を継承しない)。
  - ジョブの入力(payload、依頼ファイル由来の値)は、シェルを介さず引数配列として渡す。
    作業フォルダ外を指すパス(`..`、絶対パス、シンボリックリンク、ジャンクション)は、正規化して検査し、拒否する。
  - 成果物やログとして送るのは、作業フォルダ内の、明示したパターンに一致するものだけ。
  - ログは送信前に既知の機密パターンをマスクする(補助的な対策であり、主たる防御ではない)。
  - ワーカーとワークフローは、結果の書き戻しとして Git にコミット/プッシュしない。
    GitHub への書き戻しは、定義済みの項目(状態、短い説明、リンク)に限る。
  - 通知と GitHub への書き戻しに、ログの本文や成果物の中身を含めない。
  - ワークフローは最小権限(`contents: read`、`id-token: write`)で動かし、リポジトリの Secrets を使わない。
  - ランナー PC では、専用の低権限アカウントで実行し、作業フォルダ以外への読み取りを ACL で与えない。
    Windows ファイアウォールで、外向き通信を許可先(コア API、ソース取得先)に限定する。
  - 製品自身(エージェント、API、WebUI)は、利用状況の送信(テレメトリ・解析)や外部の配信資産の読み込みを行わない。
- **S5. 多層防御と限界の明記**: 多層防御として実装する。仮想化が使えないため、外部ツール自体が作業フォルダ外を
  読もうとした場合の技術的な限界を明記し、実行を許可するツールとリポジトリを信頼できるものに限る(許可リスト)。
- **S6. 脅威モデルの先行**: 実装前に、脅威モデル(誰を信頼し、何から守るか)を明文化する。

理由: 実行 PC には機密性の高い情報があり、仮想化による隔離が使えない。単一の対策に頼らず、
既定拒否・台帳・OS の権限制御を重ねて持ち出しを防ぐ。

### 1. モジュール分割と再利用性

- システムを、独立して使える部品に分ける: コア(ドメイン/アプリケーション)、コア API、ランナーエージェント、
  外部ツール実行(エグゼキュータ)、GitHub 連携、WebUI、通知。詳細は modules 定義(inputs/02-modules)に従う。
- 各モジュールは独立したパッケージとして、個別にテスト・バージョン管理できる。
- 依存は一方向: 連携・UI・用途固有部品 → コア API/コア。コアは他のモジュールを import しない。
  依存規則は import の検査(import-linter 等)を CI で実行して守る。
- モジュール間の結合は、公開された契約(HTTP API の OpenAPI、ランナープロトコルのスキーマ、イベントスキーマ、ポート)のみ。
  契約はバージョン付きで管理し、契約テストで検証する。互換性を壊す変更は、バージョンを上げて明示する。
- 用途固有の語(機材、評価、特定ツール名)をコアに入れない。用途固有の部分は「プロファイル」として外に置く。
- 拡張点は「ポート + 起動時の設定による実装の差し替え」だけ。動的なプラグイン読み込み機構は作らない。

理由: 別の用途・提出元へ、コアを変更せずに適用するため。

### 2. ドメイン駆動設計(軽量版)

- 業務用語(ユビキタス言語)を spec・コード・DB・UI で統一する。
- 境界づけられたコンテキスト: ジョブ(受付・キュー)、ランナー(登録・能力・状態)、アクセス(ユーザー・ロール・権限)、通知。
  コンテキスト間は ID 参照とドメインイベントで結合し、他コンテキストの内部状態を直接参照しない。
- 集約ルートを経由してのみ状態を変更し、状態遷移の不変条件は集約内で守る。不正な遷移は拒否する。
- 戦術パターンは必要な箇所のみ使い、過剰な抽象化をしない。

### 3. プラットフォーム非依存(ポート&アダプタ)

- GitHub、GitHub Actions、GitLab 等の名称・概念を、コアとコア API に持ち込まない。
- 外部との接点はポートとして定義し、固有の処理はアダプタに閉じ込める。
  ポート: 提出者の本人性検証、ソース取得、認証基盤、通知、結果の書き戻し、ジョブ定義の解釈、外部ツール実行。
- 最初のアダプタは GitHub / GitHub Actions。新しいアダプタの追加が、コアの変更なしにできることを設計の合格条件とする。

### 4. 作らないもの(スコープの規律)

- パイプライン記述言語(複数ステップの DAG・条件分岐)、ソース変更の監視と自動トリガ、
  ランナー PC の自動プロビジョニング、プラグイン配布基盤、汎用の成果物リポジトリ、認証基盤の独自実装は作らない。
  1 ジョブ = 1 回の外部ツール実行とする。
- 上記の要望が出たときは、実装せず、スコープの見直しとして扱う。

理由: 既存の CI/CD 製品と競合する機能を抱えず、キュー管理と実行管理に集中するため(inputs/00-build-vs-adopt)。

### 5. 運用上の要件(待機列の順序の制御)

- システムは優先度の概念を持たない。待機列の順序を、ジョブの属性(優先度など)からシステムが自動で決めてはならない。
- 待機列の順序は、次の操作だけで決まる。
  - **追加**: 位置の指定がなければ待機列の末尾に並ぶ。スケジュール変更の権限を持つ利用者は、
    指定した待機中のジョブの直前または直後に追加できる。
  - **スケジュール変更**: スケジュール変更の権限を持つ利用者が、待機中のジョブを、
    指定した待機中のジョブの直前または直後へ移す。移したジョブ以外の相対的な順序は変えない。
- 突発のジョブは、独立した「割り込み」の仕組みを持たず、位置を指定した追加(例: 先頭のジョブの前への追加)として扱う。
- 権限を持つ利用者は、運用中にいつでも、位置を指定した追加、スケジュール変更、ジョブのやり直し(再提出)、
  待機中のジョブの取り消し、実行中のジョブの強制中断を行える。各操作の可否は権限(permission)単位で判定する(原則 9)。
- 位置を指定した追加とスケジュール変更は、実行中のジョブを止めない。

理由: 既存の仕組みに対する不満(運用中に順序を制御できない、突発の依頼に対応できない)を再発させないため。
ランナーは利用者の共用であり、順番は利用者同士の相談で決め、その結果を権限を持つ利用者が待機列に反映する。
システムが優先度で自動に並べ替えると、相談の結果と食い違い、順序が予測できなくなる。

### 6. 監査ログ

- 状態を変える操作はすべて監査ログ(誰が・いつ・何を)に残す。

### 7. 実行環境

- 実行環境は Windows PC のみ。仮想化・コンテナ・クラウドは使えない前提で設計する。

### 8. ネットワーク境界

- 外部公開しない(イントラネット限定)。
- ランナーへの着信接続は不要な設計にする(ランナーからサーバーへの接続のみ)。

### 9. 認可

- 認可は権限(permission)単位の RBAC とする。
- ロールは、認証基盤から得た所属(グループ)を、設定でロールへ対応付けて決める。

### 10. 実行対象の固定

- 利用者のコードを実行機材で動かすため、実行対象はコミット識別子(SHA 等)で固定する。
- 許可されたソースリポジトリのみ実行する。

### 11. テスト

- コアのドメイン層は単体テスト必須。状態遷移と権限は網羅的にテストする。
- 各ポートに契約テストを用意し、実アダプタと偽のアダプタ(Fake)の両方で同じテストが通ること。
- GitHub 連携なし(偽の提出経路・偽の認証基盤)でも、コア・コア API・ランナーエージェントの結合テストが動くこと。

### 12. 未確定事項の扱い

- 未確定事項は spec 内で `[NEEDS CLARIFICATION]` と明示し、推測で仕様化しない。

### 13. WebUI

- WebUI は TypeScript + React + Fluent UI(Fluent UI React v9)で作り、UI 部品は Fluent UI を使う
  (Fluent にない場合のみ独自部品)。
- Modern Web Guidance(Chrome チームらによるエージェント用スキル)に従う。
  旧来の API や回避策を避け、現在の Web 標準の API・手法を使う(アクセシビリティ、性能、安全性を含む)。
- ガイダンスを参照して実装した箇所は、PR/コミットで根拠(参照したガイドの ID)を示す。

### 14. 環境構築の支援

- サーバーとランナー(ワーカー)の環境構築、DB のマイグレーションは、再実行できる(冪等な)スクリプトで提供する。
- 各 feature は実装後に個別に試行するため、各 feature の試行の前に、その feature に必要な構築・マイグレーションを
  スクリプトで再現できるようにする(feature の完了の定義に含め、スクリプトは段階的に拡張する)。
- スクリプトは PowerShell で書き、秘密情報は Windows の資格情報の保管機能に置く。
  インストーラは公式サイトから、版を固定して取得する。
- スクリプトは、ドライラン、事前確認、動作確認、撤去を備え、環境ごとの値は設定ファイルで与える。
- スクリプトにも機密保護の原則(S1〜S6)を適用する(秘密情報をログに出さない、外部へ送らない、取得物のハッシュを検証する)。
- 用途固有の語を含めない。

## 参照文書と優先順位

- 本憲章は、プロジェクトの他のすべての文書・慣行に優先する。
- 次の文書は本憲章の下位にあり、憲章が参照する詳細を定める。憲章と矛盾する場合は憲章に従い、下位の文書を直す。
  - inputs/02-modules: モジュールの分割と依存規則(原則 1)
  - inputs/13-security-egress: 書き出し台帳と対策(S2〜S4)
  - 脅威モデル(S6): 最初の実装の前に作成する

## 開発の流れと品質ゲート

各 feature は、次のゲートを満たしてから次の段階へ進む。

- **spec**: 未確定事項を `[NEEDS CLARIFICATION]` で示している(原則 12)。外部への書き出しをすべて列挙し、
  書き出し台帳にあることを確認している(S2)。「作らないもの」に当たる要望を含まない(原則 4)。
- **plan**: 「Constitution Check」で S1〜S6 と原則 1〜14 への適合を確認する。違反がある場合は、
  理由と、より単純な代替を採らない理由を記録する。S4 の各項目の実装方法とテスト方法を決める。
- **実装・レビュー**: 依存規則の検査(原則 1)、契約テスト(原則 1、11)、ドメイン層の単体テスト(原則 11)を CI で通す。
  台帳にない書き出しを加えていないことをレビューで確認する(S2)。WebUI では参照したガイドの ID を示す(原則 13)。
- **完了**: その feature の試行に必要な構築・マイグレーションを、スクリプトで再現できる(原則 14)。

## Governance

- **改定の手続き**: 改定は、変更内容と版の判断を示したうえで、レビューと承認を経て行う。
  S(機密情報の保護)を変更・緩和する改定は、書き出し台帳と脅威モデルへの影響の確認を必須とする。
- **版の付け方**(セマンティックバージョニング):
  - MAJOR: 原則の削除、または互換性のない再定義(例: 禁止事項の緩和、スコープの拡大)
  - MINOR: 原則・節の追加、または指針の実質的な拡充
  - PATCH: 意味を変えない明確化、言い回し、誤字の修正
- **適合の確認**: すべての plan は Constitution Check を行い、すべての PR のレビューは本憲章への適合を確認する。
  改定時は、依存するテンプレート(spec・plan・tasks)と参照文書に食い違いがないかを確認する。
