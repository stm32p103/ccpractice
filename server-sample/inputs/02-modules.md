# モジュール分割と依存規則(参照用)

Spec Kit のコマンドへの直接入力ではない。constitution・各 specify・plan から参照する設計の骨格。
必要に応じて、各 specify に該当部分を貼り付ける。

## 構成図

```
                     ┌──────────────┐   ┌───────────────┐
 GitHub Actions ───▶ │ 005 GitHub   │   │ 006 WebUI      │ ◀── 利用者・管理者
 (提出)              │ 連携(提出     │   │ (コア API の   │
                     │ ゲートウェイ/ │   │  クライアント) │
                     │ 認証/認可)    │   └──────┬────────┘
                     └──────┬───────┘          │
                            │  公開 API(003) ──┤
                            ▼                  ▼
                     ┌──────────────────────────────────┐
                     │ 003 コア API (HTTP)               │
                     ├──────────────────────────────────┤
                     │ 001 ジョブ(受付・キュー) ＋ 002 ランナー管理 │  ← コア(依存なし)
                     └───────────────▲──────────────────┘
                                     │ ランナープロトコル(004 が定義)
                            ┌────────┴─────────┐
                            │ 004 ランナーエージェント│ ←(各 Windows PC)
                            │  └ エグゼキュータ   │ ←(ポート。外部ツールを実行)
                            └──────────────────┘
                     007 通知 / 008 耐障害性(横断)
```

## モジュール一覧

| モジュール | 責務 | 知ってよいもの | 知ってはいけないもの |
|---|---|---|---|
| core(001, 002) | ジョブの受付・キュー(並び順)・状態、ランナーの登録・能力・割り当て、要件マッチング | 自分のドメインだけ | HTTP、DB 製品、GitHub、用途固有の語 |
| core-api(003) | コアを HTTP API として公開。認証済みの主体と権限の判定、永続化(DB アダプタ) | core | GitHub、UI、用途固有の語 |
| runner-agent(004) | ランナー PC 上でジョブを取得・実行・報告。プロセス管理、ログ送信、中断への対応 | ランナープロトコル | GitHub、用途固有の語(エグゼキュータ経由でのみツールを知る) |
| executor(004 のポート) | 1 件のジョブを実際に外部ツールとして実行する実装(用途ごと) | ジョブの payload の形(自分の用途の分) | キュー、他のジョブ |
| github-integration(005) | GitHub 認証(OAuth)、所属→ロールの対応、Actions からの提出の受付と本人性検証、ソース取得、結果の書き戻し | コア API(公開契約のみ) | コアの内部、DB |
| webui(006) | 利用者/管理者向けの画面 | コア API(公開契約のみ) | コアの内部、DB、GitHub(ログインは認証アダプタ経由) |
| notification(007) | 通知の送信(メール/Teams 等のアダプタ)、再送 | ジョブ完了イベント | GitHub |
| profile(用途固有) | 依頼ファイル形式の解釈(→ ジョブ定義)、エグゼキュータ、用途固有の設定。最初の用途: equipment-check | コア API の契約、自分の用途 | コアの内部 |

## コアが扱う汎用モデル(用途固有の語を含まない)

- ジョブ(Job): job_type、requirements(ランナーに求める能力の条件)、payload(コアは中身を解釈しない)、
  source_ref(参照用の出所情報。任意)、submitter、状態、結果。優先度は持たない(並び順は待機列が明示的に持つ)。
- ランナー(Runner): 名前、capabilities(能力の集合。キーと値)、状態、最終応答時刻。
- ランナー要件(Requirement): capabilities に対する条件(一致・包含・数値/版の比較)。
- 状態: queued / running / succeeded / failed / cancelled(詳細は 004 と別途定義)。

## 依頼ファイルの扱い(コアの外)

コアはファイルを読まない。流れは次のとおり。

1. GitHub Actions が、リポジトリ・リビジョン・依頼ファイルの場所を、提出ゲートウェイ(005)に送る(OIDC で本人性を証明)。
2. 提出ゲートウェイが、ソース取得ポートで依頼ファイルをリビジョン固定で取得し、プロファイル(用途ごとの解釈部品)に渡す。
3. プロファイルが、依頼ファイルを「ジョブ定義(job_type・requirements・payload・タイムアウト)」に変換する。
4. 提出ゲートウェイが、コア API にジョブ定義を送る(提出者の代理であることを示し、サービス用の権限で認証)。
5. コアは「要件を満たしうるランナーが登録されているか」を判定し、受付または拒否を返す。
   結果は提出ゲートウェイ経由で GitHub Actions の実行結果に返る。

この構造により、別の用途(別のファイル形式、別の提出元)は、プロファイルや提出ゲートウェイの差し替えだけで適用できる。

## 依存規則(CI で検査する)

- core は他のどのモジュールも import しない(標準ライブラリのみ)。
- core-api は core のみ。
- runner-agent は ランナープロトコルのスキーマのみ(core を import しない)。
- github-integration、webui、notification、profile は、コア API の公開契約(生成クライアントまたはスキーマ)のみ。core の内部を import しない。
- 用途固有の語・GitHub の語を core と core-api に含めない(語彙検査テストを用意する)。

## 機密境界

- 実行 PC の「ジョブ用の作業フォルダ」の外の情報は、ランナーエージェント・エグゼキュータ・外部ツール・GitHub Actions のワークフローから、
  外部へ送信せず、Git にコミットしない(憲章 S1)。
- 外部への書き出しは、書き出し台帳([13-security-egress.md](13-security-egress.md))に載ったものだけ。
- 境界の担当: ランナーエージェント(作業フォルダ、環境変数の許可リスト、パス検査、成果物のパターン)、
  GitHub 連携(ワークフロー雛形の最小権限、書き戻しの項目の固定)、通知(内容の固定)。コアはログ本文・payload を外部へ送らない。

## 公開契約

| 契約 | 形式 | 管理 |
|---|---|---|
| コア API | OpenAPI(バージョン付き) | 破壊的変更はメジャーを上げる。契約テストで検査 |
| ランナープロトコル | スキーマ(JSON Schema 等) | 同上 |
| ドメインイベント | スキーマ | 同上 |
| ポート | Python の抽象インターフェース + 契約テスト | 実アダプタと Fake が同じテストを通る |
