# /speckit.specify 入力(feature 001: core-job-queue)

## 入力

```
# 機能: コア — ジョブの受付・キュー管理

## 背景と目的
外部ツールを実行する「ジョブ」を受け付け、順番待ち(キュー)を管理する、再利用可能なコアを作る。
特定の用途、提出元(GitHub 等)、実行するツールには依存しない。
既存の仕組みの問題(一度動き出すと入れ替えられず、突発の依頼ややり直しに対応できない)を解消する。
最初の用途は「評価機材に接続された Windows PC でしか動かないチェックツールの実行」だが、コアはその語彙を持たない。
ランナーは利用者の共用である。順番はシステムが優先度で自動に決めず、利用者同士の相談で決める。
その結果を、スケジュール変更の権限を持つ利用者が、待機列に反映する(憲章 原則 5)。そのため、待機列は全員が見られる。

## ユビキタス言語
- ジョブ(Job): 1 回の外部ツール実行の依頼。コアは中身(payload)を解釈しない。
- ジョブ定義(Job Definition): ジョブの内容。job_type、ランナー要件、payload、タイムアウト、出所情報(source_ref。参照用)を持つ。
- ランナー要件(Runner Requirement): ジョブの実行に必要なランナーの能力の条件。
- 提出者(Submitter): ジョブを提出した主体。本人性は呼び出し元の認証で確認済みとする。
- 待機列(Queue): 待機中のジョブを、明示的な並び順で保持する 1 本の列。優先度の概念は持たない。
- 位置を指定した追加: 待機中のジョブを 1 件基準として指定し、その直前または直後に新しいジョブを追加すること。指定がなければ末尾に追加する。突発の依頼は、これで対応する(独立した「割り込み」は持たない)。
- スケジュール変更(Reschedule): 待機中のジョブを、指定した別の待機中のジョブの直前または直後へ移すこと。移したジョブ以外の相対的な順序は変えない。
- やり直し(Rerun): 終了したジョブを、同じ定義で新しいジョブとして追加すること。元のジョブとの関連を記録する。
- 取り消し(Cancel): 待機中のジョブを待機列から外し、中断の状態で終了させること。
- 強制中断(Abort): 実行中のジョブを停止し、中断の状態で終了させること。

## ユーザーシナリオ
1. 提出者(ジョブ追加の権限を持つ主体)は、ジョブ定義を渡してジョブを提出する。要件を満たしうるランナーが 1 台も登録されていなければ、理由とともに拒否される。同じ内容(出所・リビジョン・ジョブの種類が同一)のジョブが待機中のときも、理由と既存のジョブの識別子とともに拒否される。
2. ジョブは、位置の指定がなければ待機列の末尾に並び、条件を満たすランナーが空いたときに、待機列の前から順に(そのランナーの条件を満たすもののうち最も前のものが)実行される。
3. スケジュール変更の権限を持つ利用者は、待機中のジョブを、指定した待機中のジョブの直前または直後へ移して、順序を入れ替えられる。
4. 突発の依頼は、スケジュール変更の権限を持つ利用者が、位置を指定して提出する(例: 先頭のジョブの直前)。
5. 提出者は自分の待機中のジョブを取り消せる。取り消しの権限を持つ主体は、すべての待機中のジョブを取り消せる。強制中断の権限を持つ主体は、実行中のジョブを強制中断できる(理由は必須)。実行中のジョブが自動で止められることはない。
6. ジョブ追加の権限を持つ主体は、誰のジョブでも、終了したジョブをやり直せる。新しいジョブが作られ、元のジョブとの関連が残る。
7. すべての利用者は、誰のジョブかを問わず、すべてのジョブの提出者・状態・待機列内の位置・結果と、ジョブごとの操作の経緯を確認できる。
8. ジョブが終了(成功/失敗/中断)したとき、完了イベントが発行される(通知は別モジュールが受け取る)。

## 機能要件
- FR-1 ジョブ定義は用途に依存しない形で受け付ける。コアは payload を解釈しない。
- FR-2 提出時に、ランナー要件を満たしうるランナーが 1 台も登録されていなければ拒否し、理由を返す。
- FR-3 システムは優先度・割り込みの概念を持たない。待機列の順序は、追加された位置と、スケジュール変更だけで決まる。位置の指定がない追加は末尾に並ぶ。
- FR-4 スケジュール変更の権限を持つ主体は、提出時に待機中のジョブを基準として指定し、その直前または直後に追加できる。基準が待機中でなければ拒否する(末尾への追加に切り替えない)。
- FR-5 スケジュール変更の権限を持つ主体は、誰のジョブかを問わず、待機中のジョブを、指定した別の待機中のジョブの直前または直後へ移せる。移すジョブ・基準が待機中でない場合、両者が同じジョブの場合は拒否する。移したジョブ以外の相対的な順序は変えない。
- FR-6 実行中のジョブを、位置を指定した追加やスケジュール変更を理由に、自動で追い出さない。
- FR-7 待機中のジョブの取り消し、実行中のジョブの強制中断ができる。中断の理由を記録する(強制中断では必須)。
- FR-8 やり直しは、元のジョブの定義(出所のリビジョンを含む)を引き継ぎ、新しいジョブとして追加する。元のジョブは変更されない。やり直しにも、受付の判定(FR-2、重複の判定)を適用する。
- FR-9 1 ランナーにつき同時に実行されるジョブは 1 つ。
- FR-10 ジョブの状態遷移は規則に従い、不正な遷移は拒否される(許可される遷移の詳細は 004 と別途定義)。
- FR-11 権限は権限(permission)単位で判定する(ロールではなく)。
  - ジョブ追加: 自分の名義でのジョブの提出(末尾への追加)、すべての終了したジョブのやり直し(末尾への追加)。
  - 一般: 自分のジョブの中断(取り消し・強制中断の要求)、すべてのジョブとその操作の経緯の閲覧。
  - スケジュール変更: 指定した待機中のジョブの前後へのジョブの追加、すべての待機中のジョブの前後への移動(一般の利用者にも付与できる)。
  - 取り消し: すべての待機中のジョブの取り消し。
  - 強制中断: すべての実行中のジョブの強制中断。
  - 管理: 監査ログ全体(権限による拒否を含む)の閲覧。
  - 提出代行(サービス用): 別の提出者の名義でジョブを提出する。名義上の提出者と実際に提出した主体の両方を記録する。
- FR-12 状態変更(提出(位置の指定を含む)・スケジュール変更・中断の要求と確定・やり直し・完了)は、操作者・日時・対象・変更前後の値・理由を監査ログに残す。各ジョブの操作の経緯は全員が、監査ログ全体は管理の権限を持つ主体が閲覧できる。
- FR-13 ジョブの終了時に、ドメインイベント(ジョブ完了)を発行する。送信の失敗で状態が失われない(取りこぼさない)。
- FR-14 コアは、特定のプラットフォーム・用途の語を含まない。
- FR-15(機密保護)コアは、外部への送信を自ら行わない。外部への書き出しは、ポート(通知、書き戻し)経由で、書き出し台帳(13-security-egress)に載った内容だけとする。ジョブの payload とログの本文は、外部へ送るイベントに含めない(参照用の ID のみ)。
- FR-16 同じ内容(出所・リビジョン・ジョブの種類が同一)のジョブが待機中のとき、提出(やり直しを含む)を拒否し、理由と既存のジョブの識別子を返す。提出者は問わない。実行中・終了済みの場合は受け付ける。
- FR-17 1 人の提出者が同時に待機させられるジョブの数に、上限を設けない(占有には、相談とスケジュール変更・中断で対処する)。
- FR-18 保持期間を設定値で変えられるようにし、終了したジョブ(定義・結果の要約)は既定 1 年、監査ログは既定 3 年で自動削除する(監査ログはジョブより短く設定できない)。ログ本文・成果物の保持は 004 で扱う。

## 受け入れ基準(例)
- 要件を満たしうるランナーが登録されていないジョブは、提出が拒否される。
- 位置の指定なしに提出したジョブは、待機列の末尾に並ぶ。
- スケジュール変更の権限を持つ主体が、待機中のジョブを別の待機中のジョブの直前へ移すと、次の割り当てでそのジョブが先に実行される。移したジョブ以外の相対的な順序は変わらない。
- 突発のジョブを、実行中のジョブを止めずに、先頭のジョブの直前へ位置を指定して追加できる。
- 終了したジョブをやり直すと、同じ定義の新しいジョブが待機列に入り、元のジョブとの関連が確認できる。
- 一般の提出者が他人のジョブを中断しようとすると拒否される。取り消し・強制中断の権限があれば、他人のジョブも中断できる。
- スケジュール変更の権限を持たない主体は、位置を指定した追加・移動ができない。
- 同じ内容のジョブが待機中のとき、重複した提出は拒否される。
- コアのコードに GitHub・特定ツール・「機材」などの語や import が存在しない(検査で確認)。

## スコープ外
- ランナーの登録・能力・稼働状態の詳細(feature 002)
- HTTP API(feature 003)、ランナーエージェントと実行(feature 004)、GitHub 連携(005)、WebUI(006)、通知の送信(007)、耐障害性(008)
- 複数ステップのパイプライン、自動トリガ(憲章の「作らないもの」)
- 優先度、独立した「割り込み」の仕組み(憲章 原則 5 により持たない)

## 未確定事項
- (確定済み)順序の表現: 優先度は持たず、待機列内の明示的な順序(位置を指定した追加とスケジュール変更)だけとする
- (確定済み)保持期間: 終了したジョブ 1 年、監査ログ 3 年(設定値で変更可)
- (確定済み)重複提出: 同一出所・同一リビジョン・同一ジョブの種類のジョブが待機中なら拒否する
- (確定済み)待機できるジョブ数の上限: 設けない
```
