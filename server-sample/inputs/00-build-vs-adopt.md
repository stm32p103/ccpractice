# 作る理由と、作らないものの線引き(判断メモ)

> 一般的な知見に基づく整理。細部は採用前に最新情報を確認すること。

## 結論

**個別に作る。** Jenkins は事情により選択肢から外れ、CI は GitHub Actions に統一されるため、
「Actions では足りない部分(キュー制御と機材マッチング)」だけを、汎用部品として作る。

## 候補が使えない理由

| 候補 | 判断 |
|---|---|
| Jenkins | 運用実績で「一度動き出すと入れ替えられない/突発依頼・やり直しに堪えられない」ことが問題になり、採用取りやめ。選択肢から除外 |
| GitHub Actions のセルフホステッドランナー単体 | キューが FIFO。順序の入れ替え、機材要件による振り分け、管理者による制御ができない |
| LAVA / Labgrid | Linux 前提。Windows のみの環境に不向き |
| Kubernetes 系(Tekton, Argo 等) | 仮想化/コンテナ不可の前提に反する |
| Celery / Airflow 等の汎用基盤 | ランナーの占有管理・WebUI での優先度制御・RBAC は結局自作になり、Windows 対応にも癖がある |

## 懸念: Jenkins の再発明になること

「ジョブの受付・管理、ランナーとジョブの管理、API、WebUI、外部ツールの実行」を汎用化すると Jenkins に近づく。
肥大化を防ぐため、**作らないものを最初に決める**。

### 作らないもの(スコープ外を憲章に明記する)

- パイプライン記述言語(複数ステップの DAG、条件分岐、並列ステージ)。1 ジョブ = 1 回の外部ツール実行
- ソース変更の監視・自動トリガ(トリガは提出のみ。GitHub Actions 等が担う)
- ランナー用 PC の自動プロビジョニング(仮想化不可のため)
- プラグインの動的ロード/配布の仕組み。拡張は「ポート + 起動時の設定で実装を差し替える」だけ
- 汎用のビルド成果物リポジトリ。結果と成果物は保持期間付きの添付として扱う
- 認証基盤・ユーザー管理の独自実装。本人性は外部の認証基盤から得る

### 作るもの(Jenkins の不満点を直接解消する)

- **待機中ジョブの優先度変更・順序入れ替え**(管理者が WebUI/API で実施)
- **突発の依頼の割り込み**(最優先指定で待機列の先頭へ)。実行中ジョブは自動では止めず、管理者が明示的に中断する
- **やり直し**(完了・失敗・中断したジョブを、同じリビジョンと条件で新しいジョブとして再提出。元ジョブとの関連を記録)
- 実行中ジョブの中断(プロセスツリーごと)
- ランナーの要件マッチング(提出時に「満たすランナーが存在しない」を検出して拒否)

## 見直しの条件

次のいずれかが起きたら、作る範囲を見直す。
- 作らないもの一覧に挙げた機能の要望が複数回出た(=汎用 CI 化の兆候)。専用の CI ツールを再評価する。
- ランナー管理(002)が想定より複雑になった。既存のテストファーム管理 OSS の考え方(機材予約・リース)を再確認する。
