# /speckit.constitution 入力

## 入力

```
# プロジェクト憲章

## 目的
ジョブの受付・キュー管理、ランナーとジョブの管理を、特定の用途・プラットフォームに依存しない汎用部品として作り、
最初の用途(評価機材に接続された Windows PC で動くチェックツールの実行)をその上に載せる。
他の用途(別のツール、別の機材、別の提出元)へ、コアを変更せずに適用できることを目指す。

## 最重要原則: 機密情報の保護(持ち出し禁止)
S1. ジョブを実行するワーカー(ランナーエージェント、エグゼキュータ、起動した外部ツール)と、
    GitHub Actions のランナー(ワークフロー)は、実行 PC 内の「ジョブ用の作業フォルダ」の外にある情報を、
    外部に送信してはならず、Git にコミットしてはならない。
    対象の情報: 作業フォルダ外のファイル、環境変数、他のサービスの情報(資格情報、トークン、設定、他のジョブの情報を含む)。
S2. 外部へ書き出す情報がある場合は、「どこに(出力先)・何を(内容)・どの条件で」書き出すかを、
    書き出し台帳(inputs/13-security-egress)と、各 spec・plan に明示する。台帳にない書き出しは禁止する。
    書き出しの追加は、台帳の更新とレビューを要する。
S3. 既定は「何も送らない」。許可リスト(出力先・内容・パス・環境変数)で許可したものだけを扱い、許可リスト外は拒否する。
S4. 担保の方法(plan で実装を決め、テストする):
    - 外部ツールの起動時の環境変数は、空の状態から許可リストの変数だけで組み立てる(親プロセスの環境を継承しない)。
    - ジョブの入力(payload、依頼ファイル由来の値)は、シェルを介さず引数配列として渡す。
      作業フォルダ外を指すパス(.. 、絶対パス、シンボリックリンク、ジャンクション)は、正規化して検査し、拒否する。
    - 成果物やログとして送るのは、作業フォルダ内の、明示したパターンに一致するものだけ。
    - ログは送信前に既知の機密パターンをマスクする(補助的な対策であり、主たる防御ではない)。
    - ワーカーとワークフローは、結果の書き戻しとして Git にコミット/プッシュしない。
      GitHub への書き戻しは、定義済みの項目(状態、短い説明、リンク)に限る。
    - 通知と GitHub への書き戻しに、ログの本文や成果物の中身を含めない。
    - ワークフローは最小権限(contents: read、id-token: write)で動かし、リポジトリの Secrets を使わない。
    - ランナー PC では、専用の低権限アカウントで実行し、作業フォルダ以外への読み取りを ACL で与えない。
      Windows ファイアウォールで、外向き通信を許可先(コア API、ソース取得先)に限定する。
    - 製品自身(エージェント、API、WebUI)は、利用状況の送信(テレメトリ・解析)や外部の配信資産の読み込みを行わない。
S5. 多層防御として実装する。仮想化が使えないため、外部ツール自体が作業フォルダ外を読もうとした場合の技術的な限界を明記し、
    実行を許可するツールとリポジトリを信頼できるものに限る(許可リスト)。
S6. 実装前に、脅威モデル(誰を信頼し、何から守るか)を明文化する。

## 原則
1. モジュール分割と再利用性
   - システムを、独立して使える部品に分ける: コア(ドメイン/アプリケーション)、コア API、ランナーエージェント、
     外部ツール実行(エグゼキュータ)、GitHub 連携、WebUI、通知。詳細は modules 定義(inputs/02-modules)に従う。
   - 各モジュールは独立したパッケージとして、個別にテスト・バージョン管理できる。
   - 依存は一方向: 連携・UI・用途固有部品 → コア API/コア。コアは他のモジュールを import しない。
     依存規則は import の検査(import-linter 等)を CI で実行して守る。
   - モジュール間の結合は、公開された契約(HTTP API の OpenAPI、ランナープロトコルのスキーマ、イベントスキーマ、ポート)のみ。
     契約はバージョン付きで管理し、契約テストで検証する。互換性を壊す変更は、バージョンを上げて明示する。
   - 用途固有の語(機材、評価、特定ツール名)をコアに入れない。用途固有の部分は「プロファイル」として外に置く。
   - 拡張点は「ポート + 起動時の設定による実装の差し替え」だけ。動的なプラグイン読み込み機構は作らない。
2. ドメイン駆動設計(軽量版)
   - 業務用語(ユビキタス言語)を spec・コード・DB・UI で統一する。
   - 境界づけられたコンテキスト: ジョブ(受付・キュー)、ランナー(登録・能力・状態)、アクセス(ユーザー・ロール・権限)、通知。
     コンテキスト間は ID 参照とドメインイベントで結合し、他コンテキストの内部状態を直接参照しない。
   - 集約ルートを経由してのみ状態を変更し、状態遷移の不変条件は集約内で守る。不正な遷移は拒否する。
   - 戦術パターンは必要な箇所のみ使い、過剰な抽象化をしない。
3. プラットフォーム非依存(ポート&アダプタ)
   - GitHub、GitHub Actions、GitLab 等の名称・概念を、コアとコア API に持ち込まない。
   - 外部との接点はポートとして定義し、固有の処理はアダプタに閉じ込める。
     ポート: 提出者の本人性検証、ソース取得、認証基盤、通知、結果の書き戻し、ジョブ定義の解釈、外部ツール実行。
   - 最初のアダプタは GitHub / GitHub Actions。新しいアダプタの追加が、コアの変更なしにできることを設計の合格条件とする。
4. 作らないもの(スコープの規律)
   - パイプライン記述言語(複数ステップの DAG・条件分岐)、ソース変更の監視と自動トリガ、
     ランナー PC の自動プロビジョニング、プラグイン配布基盤、汎用の成果物リポジトリ、認証基盤の独自実装は作らない。
     1 ジョブ = 1 回の外部ツール実行とする。
   - 上記の要望が出たときは、実装せず、スコープの見直しとして扱う。
5. 運用上の要件(この系統の不満を再発させない)
   - 優先度の概念を持たない。待機列の順序は、追加の位置(指定がなければ末尾、権限があれば指定したジョブの前後)と、
     指定したジョブの前後への移動(スケジュール変更)だけで決まる。突発のジョブは、位置を指定した追加として扱う。
   - 位置を指定した追加、スケジュール変更、ジョブのやり直し(再提出)、待機中のジョブの取り消し、
     実行中ジョブの強制中断を、権限を持つ利用者が運用中にいつでも行える(憲章 v2.0.0 の原則 5)。
6. 状態を変える操作はすべて監査ログ(誰が・いつ・何を)に残す。
7. 実行環境は Windows PC のみ。仮想化・コンテナ・クラウドは使えない前提で設計する。
8. 外部公開しない(イントラネット限定)。ランナーへの着信接続は不要な設計にする(ランナーからサーバーへの接続のみ)。
9. 認可は権限(permission)単位の RBAC。ロールは認証基盤から得た所属(グループ)を、設定でロールへ対応付けて決める。
10. 利用者のコードを実行機材で動かすため、実行対象はコミット識別子(SHA 等)で固定し、許可されたソースリポジトリのみ実行する。
11. テスト
   - コアのドメイン層は単体テスト必須。状態遷移と権限は網羅的にテストする。
   - 各ポートに契約テストを用意し、実アダプタと偽のアダプタ(Fake)の両方で同じテストが通ること。
   - GitHub 連携なし(偽の提出経路・偽の認証基盤)でも、コア・コア API・ランナーエージェントの結合テストが動くこと。
12. 未確定事項は spec 内で [NEEDS CLARIFICATION] と明示し、推測で仕様化しない。
13. WebUI は TypeScript + React + Fluent UI(Fluent UI React v9)で作り、UI 部品は Fluent UI を使う(Fluent にない場合のみ独自部品)。Modern Web Guidance(Chrome チームらによるエージェント用スキル)に従う。
    旧来の API や回避策を避け、現在の Web 標準の API・手法を使う(アクセシビリティ、性能、安全性を含む)。
    ガイダンスを参照して実装した箇所は、PR/コミットで根拠(参照したガイドの ID)を示す。
14. 環境構築の支援: サーバーとランナー(ワーカー)の環境構築、DB のマイグレーションは、再実行できる(冪等な)スクリプトで提供する。
    各 feature は実装後に個別に試行するため、各 feature の試行の前に、その feature に必要な構築・マイグレーションを
    スクリプトで再現できるようにする(feature の完了の定義に含め、スクリプトは段階的に拡張する)。
    スクリプトは PowerShell で書き、秘密情報は Windows の資格情報の保管機能に置く。インストーラは公式サイトから、版を固定して取得する。
    スクリプトは、ドライラン、事前確認、動作確認、撤去を備え、環境ごとの値は設定ファイルで与える。
    スクリプトにも機密保護の原則(S1〜S6)を適用する(秘密情報をログに出さない、外部へ送らない、取得物のハッシュを検証する)。
    用途固有の語を含めない。
```
