# /speckit.specify 入力(feature 005: github-integration)

## 入力

```
# 機能: GitHub 連携 — 認証・認可・提出

## 背景と目的
GitHub を、利用者の認証・認可の根拠、およびジョブの提出元として使うための連携部品を作る。
コア API の公開契約だけに依存し、コアには GitHub の概念を持ち込まない。
同じ構造で、別の認証基盤・提出元の連携部品を後から追加できること。

## ユビキタス言語
- 認証アダプタ: WebUI へのログインで、利用者の本人性と所属グループを確認する部品。ここでは GitHub OAuth と組織/チームの所属。
- 提出ゲートウェイ: 提出元からの提出を受け、検証・解釈して、コア API にジョブを提出する部品。
- 提出経路: ここでは GitHub Actions の手動実行(workflow_dispatch)。
- ソース取得: ソースリポジトリから、リビジョンを固定して依頼ファイルを取得する部品。
- プロファイル: 依頼ファイルを、ジョブ定義(job_type、ランナー要件、payload、タイムアウト)に変換する、用途ごとの部品。
- 結果の書き戻し: 提出元にジョブの状態を戻す(任意)。

## 要件
- FR-1(認証・認可)利用者は GitHub 認証でログインできる。所属する組織/チームを取得し、設定の対応表(所属グループ→ロール)で、ロール(利用者/管理者)が決まる。
  ロールの対応は設定で変更でき、コードに組織名・チーム名を埋め込まない。
- FR-2(認証・認可)ロールの変更が GitHub 側で行われた場合、一定時間内に反映される(反映の間隔は clarify で決める)。
- FR-3(提出)利用者は、GitHub Actions を手動実行し、依頼ファイルのパスを指定して提出できる。
  ワークフローの定義は、利用者のリポジトリに置ける再利用可能な形(雛形)で提供する。
- FR-4(提出)提出者の本人性は、GitHub Actions が発行する OIDC トークンの検証で確認する。共有シークレットは使わない。
  トークンから、実行を起動した利用者、リポジトリ、リビジョンを取得する。
- FR-5(提出)ソース取得は、リビジョンを固定して依頼ファイルを取得する。許可されたリポジトリ以外の提出は拒否する。
- FR-6(提出)提出ゲートウェイは、プロファイルでジョブ定義に変換し、サービス主体としてコア API に、提出者の名義でジョブを提出する。
- FR-7(提出)受付または拒否(理由つき)は、Actions の実行結果として確認できる。提出後の状態確認は WebUI で行う(Actions を完了まで待たせない)。
- FR-8(書き戻し・任意)ジョブの状態を、リビジョンに対するステータス等として GitHub に戻せる。無くても全機能が使える。
- FR-9 GitHub への接続情報(アプリの鍵、OAuth の設定)は、設定として外に出し、安全に管理する。
- FR-10 この部品は、コア API の公開契約(OpenAPI の生成クライアント)だけを使い、コアの内部を import しない。
- FR-11 認証アダプタ・提出ゲートウェイ・ソース取得は、ポートとして定義され、偽の実装で、GitHub なしで試験できる。

## 機密保護(最重要。憲章の S1〜S6、書き出し台帳 13-security-egress に従う)
- FR-12 提出用ワークフローの雛形は、ジョブ用の作業フォルダ外の情報(ファイル、環境変数、Secrets、他のサービスの情報)を、外部に送信せず、Git にコミット/プッシュしない。
- FR-13 ワークフローが外部へ書き出すものは、次に限る(台帳の E1〜E3)。これ以外は書き出さない。
  - 提出ゲートウェイへ: リポジトリ、リビジョン、依頼ファイルのパス、OIDC トークン(優先度は持たない。位置の指定の扱いは本 feature で決める)。依頼ファイルの中身は送らない。
  - Actions の実行ログへ: 受付結果(受付 ID、拒否理由)のみ。
  - Git へのコミット/プッシュ、アーティファクト、キャッシュへの書き出しはしない。
- FR-14 ワークフローの権限は `contents: read` と `id-token: write` のみ。リポジトリの Secrets を使わない。環境変数やファイル一覧を出力しない。
- FR-15 GitHub への書き戻し(FR-8)に含める項目は、状態、短い説明、WebUI へのリンクに限る。ログ本文・成果物の中身・ランナーの情報を含めない。
- FR-16 ソース取得の資格は、短命で読み取り専用とし、許可リストのリポジトリにだけ使える。
- FR-17 連携部品の設定(鍵、OAuth のシークレット)は、ジョブの実行環境(ランナー PC)に置かない。

## 受け入れ基準(機密保護)
- 雛形ワークフローの実行ログとネットワーク通信に、環境変数・Secrets・ファイル一覧が現れない(テストで確認)。
- ワークフローがコミット/プッシュを行わない(権限が `contents: read` のため不可能であることを確認)。
- 書き戻しの内容に、ログ本文が含まれない。

## 受け入れ基準(例)
- 別の偽の提出経路(CLI 等)を追加しても、コアとコア API が変更されない。
- 許可されていないリポジトリからの提出は拒否される。
- 所属グループ→ロールの対応表を変更すると、次のログインで権限が変わる。
- 提出時点のリビジョンが固定され、提出後にブランチが進んでも、実行されるのは提出時点の内容。

## スコープ外
- コア・コア API、画面、ランナーエージェント
- GitHub 以外の連携の実装(追加できる構造のみ対象)

## 未確定事項

- [NEEDS CLARIFICATION] ロール反映の間隔(ログインごと/定期)
- [NEEDS CLARIFICATION] GitHub への書き戻しに使う方法(Commit Status/Checks)の要否
- [NEEDS CLARIFICATION] ランナーがソースを取得する際の資格(短命トークン)の発行の担当
```
