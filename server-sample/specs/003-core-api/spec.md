# Feature Specification: コア API — コアを HTTP API として公開する

**Feature Branch**: `job_service`(spec ディレクトリ: `specs/003-core-api`)

**Created**: 2026-11-21

**Status**: Draft

**Input**: User description: inputs/05-specify-003-core-api.md「機能: コア API — コアを HTTP API として公開する」(背景と目的、ユビキタス言語、FR-1〜FR-12、受け入れ基準、スコープ外、未確定事項)。憲章 v2.0.0(優先度の概念を持たない)に合わせ、入力にある「優先度変更」「割り込み」は、スケジュール変更・位置を指定した追加として読み替えた。

## 背景と目的

001(ジョブの受付・キュー)と 002(ランナーの管理)のコアを、HTTP API として公開する。
WebUI、GitHub 連携、他のクライアント、ランナーエージェントは、この API(とランナープロトコル)だけを使ってコアを利用する(憲章 原則 1)。
API は特定の提出元・用途に依存せず、GitHub などのプラットフォームの語を含まない(憲章 原則 3)。

本 feature は、次を定める。

- コアの機能(001・002)を、認証済みの主体に権限の範囲で公開する契約(操作、一覧、エラー、イベントの配信)。
- 主体(人間の利用者・サービス・ランナー)の区別、認証、権限による認可の仕組み。
- 認証基盤をポートとして差し替えられること(偽の認証基盤で、外部サービスなしに一連の操作を試験できること)。

## ユビキタス言語

- **主体(Principal)**: API を呼ぶ認証済みの者。人間の利用者、サービス(連携部品)、ランナーの 3 種類。
- **権限(Permission)**: 操作の可否の単位。ロールは権限の集合。
- **ロール**: 権限の集合。人間の利用者のロールは、認証基盤が確認した所属グループから、設定の対応づけで決まる。
- **サービス主体**: GitHub 連携などの連携部品が使う認証。提出者の代理を許可された権限(提出代行)を持つ。
- **代理元**: 代理で操作したときの、実際に呼び出した主体。名義上の提出者とは別に記録する。

## Clarifications

### Session 2026-11-21

- Q: API の認証方式の詳細と有効期限は? → A: 人間の利用者は、認証基盤で確認した本人性から有効期限付きのセッションを発行する。サービスとランナーは、失効可能な長寿命のトークンを使う(FR-012)。
- Q: イベント配信の方式は? → A: SSE(サーバーからの一方向配信)とする(FR-017)。
- Q: API のバージョニング方針は? → A: URL にバージョンを含める(FR-019)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 生成したクライアントだけでジョブを提出・参照・管理する (Priority: P1)

利用者(または他のシステム)は、API の定義から生成したクライアントだけで、ジョブの提出、一覧・詳細の参照、スケジュール変更、取り消し、強制中断、やり直しを行える。
WebUI や GitHub 連携の実装は使わない。

**Why this priority**: API が、コアの機能を過不足なく公開していることが、すべてのクライアント(WebUI、GitHub 連携、ランナーエージェント)の前提になる。

**Independent Test**: 偽の認証基盤でログインした利用者として、API の定義から生成したクライアントだけを使い、ジョブの提出から結果の参照、やり直しまでを一通り行う。

**Acceptance Scenarios**:

1. **Given** ジョブ追加の権限を持つ人間の利用者, **When** ジョブを提出する, **Then** 待機中のジョブとして受け付けられ、識別子が返る。提出者は呼び出した本人になる。
2. **Given** 待機列に複数のジョブがある, **When** スケジュール変更の権限を持つ主体が、待機中のジョブを別の待機中のジョブの直前に移す, **Then** 待機列の順序が変わり、移したジョブ以外の相対的な順序は変わらない。
3. **Given** 実行中のジョブ, **When** 強制中断の権限を持つ主体が理由を付けて強制中断する, **Then** 中断が要求され、理由が記録される。理由がなければ拒否される。
4. **Given** 終了したジョブ, **When** ジョブ追加の権限を持つ主体がやり直す, **Then** 元の定義を引き継いだ新しいジョブが追加される。
5. **Given** 001・002 が定める操作(ジョブの提出・参照・スケジュール変更・取り消し・強制中断・やり直し、ランナーの管理、監査ログの参照), **When** API の定義を確認する, **Then** それぞれに対応する操作が定義されている。

### User Story 2 - サービス主体が代理で提出する (Priority: P1)

GitHub 連携などのサービス主体は、提出代行の権限により、別の提出者の名義でジョブを提出できる。
監査ログには、名義上の提出者と、代理元(サービス)の両方が残る。一般の利用者は代理で提出できない。

**Why this priority**: 提出元の連携部品(005)が、利用者本人の認証なしにジョブを提出するための唯一の経路であり、代理を厳格に限定することが不正な提出の防止になる。

**Independent Test**: サービス主体と一般の利用者の両方で、別の提出者の名義を指定して提出し、結果と監査ログを比べる。

**Acceptance Scenarios**:

1. **Given** 提出代行の権限を持つサービス主体, **When** 別の提出者の名義でジョブを提出する, **Then** ジョブの提出者は指定した名義になり、監査ログに名義上の提出者と代理元(サービス)の両方が残る。
2. **Given** 一般の利用者, **When** 別の提出者の名義でジョブを提出しようとする, **Then** 権限がないとして拒否され、拒否が監査ログに残る。
3. **Given** 提出代行の権限を持たないサービス主体, **When** 別の提出者の名義で提出しようとする, **Then** 拒否される。
4. **Given** 失効したサービス用の認証情報, **When** その認証情報で API を呼ぶ, **Then** 認証に失敗し、操作は行われない。

---

### User Story 3 - ランナーが自身の認証情報で API を使う (Priority: P1)

ランナーは、ランナーごとの認証情報で認証され、ランナー用の操作(ランナープロトコル。004 で定義)だけを行える。
認証情報が失効したランナーは、ジョブを取得できない。ランナーは、他のランナーの情報や、利用者向けの操作を使えない。

**Why this priority**: ランナーは機材に接続された PC で動くため、認証情報の漏えいの影響を、失効によって止められることが必須。

**Independent Test**: 有効なランナーの認証情報と、失効させた認証情報で、ジョブの取得を試みる。ランナーの認証情報で、利用者向けの操作を呼ぶ。

**Acceptance Scenarios**:

1. **Given** 有効な認証情報を持つランナー, **When** ジョブの取得を要求する, **Then** 002 の割り当ての条件に従って応答する。
2. **Given** 失効したランナーの認証情報, **When** ジョブの取得を要求する, **Then** 認証に失敗し、ジョブは割り当てられない。
3. **Given** ランナーの認証情報, **When** 利用者向けの操作(ジョブの提出、スケジュール変更など)を呼ぶ, **Then** 権限がないとして拒否される。
4. **Given** ランナーの認証情報, **When** 他のランナーの情報を参照・変更しようとする, **Then** 拒否される。

---

### User Story 4 - 人間の利用者を認証基盤で確認し、所属からロールを決める (Priority: P1)

人間の利用者は、認証基盤(ポート)が確認した本人性と所属グループから、ロール(権限の集合)が決まる。
所属グループとロールの対応、ロールと権限の対応は、設定で変更できる。
認証基盤は差し替え可能で、偽の認証基盤を使えば、GitHub なしに利用者としてログインして一連の操作を試験できる。

**Why this priority**: 認可はすべての操作の入口であり、認証基盤を差し替えられなければ、試験も他の用途への適用もできない。

**Independent Test**: 偽の認証基盤で、所属グループの異なる複数の利用者としてログインし、各権限の操作の可否を確認する。対応の設定を変えて、結果が変わることを確認する。

**Acceptance Scenarios**:

1. **Given** 偽の認証基盤が「利用者 A はグループ G に所属」と答える, **When** 利用者 A として API を呼ぶ, **Then** G に対応づけられたロールの権限の範囲で操作できる。
2. **Given** 設定でグループとロールの対応を変更した, **When** 同じ利用者が API を呼ぶ, **Then** 変更後のロールの権限で判定される。
3. **Given** どのロールにも対応づかないグループだけに所属する利用者, **When** 操作を呼ぶ, **Then** 既定のロールに許可された操作(閲覧など)を除き、権限がないとして拒否される。
4. **Given** 認証基盤が本人性を確認できない, **When** API を呼ぶ, **Then** 認証に失敗し、操作は行われない。
5. **Given** API の定義と応答, **When** 内容を確認する, **Then** 特定の認証基盤の名称・概念を含まない。

---

### User Story 5 - 一覧の絞り込みとページ分割、キュー全体の参照 (Priority: P2)

利用者は、ジョブの一覧を、状態・提出者・期間で絞り込み、ページ単位で取得できる。
キュー全体(待機中のジョブ)を、待機列の順序つきで取得できる。001 に従い、順番を利用者同士が相談できるよう、すべての利用者が閲覧できる。

**Why this priority**: 数が増えたジョブを画面や他のクライアントで扱うために必要。ただし、単件の操作(P1)が先に成立していれば、最小の価値は得られる。

**Independent Test**: 多数のジョブを作り、条件を変えて一覧を取得し、結果の件数・順序・ページの継ぎ目を確認する。

**Acceptance Scenarios**:

1. **Given** 状態や提出者の異なる多数のジョブ, **When** 状態・提出者・期間のいずれかまたは組み合わせで絞り込む, **Then** 条件に合うジョブだけが返る。
2. **Given** ページの大きさより多い結果, **When** 続きのページを要求する, **Then** 重複・欠落なく続きが返る。
3. **Given** 待機中のジョブが複数ある, **When** キュー全体の一覧を取得する, **Then** 待機列の並び順で返る。閲覧できることは、スケジュール変更・取り消しなどの権限を意味しない。

### User Story 6 - 状態の変更を購読して画面へ即時に反映する (Priority: P2)

クライアントは、ジョブやランナーの状態の変更を購読し、変更の通知をほぼ即時に受け取れる。
通知は、状態・識別子・短い説明に限り、ログの本文や成果物の中身を含まない。

**Why this priority**: 画面を人手の再読み込みなしに最新に保つために必要。ただし、一覧の再取得でも代替できるため、P2 とする。

**Independent Test**: 購読を開始し、別の主体でジョブの状態を変える。変更の通知が届くまでの時間と内容を確認する。

**Acceptance Scenarios**:

1. **Given** ジョブの状態の変更を購読しているクライアント, **When** そのジョブの状態が変わる, **Then** 変更の通知が受け取れる。
2. **Given** 購読が切断された, **When** 再接続する, **Then** 切断中の変更を取りこぼさずに受け取れる、または取りこぼしを検知して再取得できる。
3. **Given** ログの本文を参照する権限のない主体, **When** 購読する, **Then** 通知にログの本文や成果物の中身は含まれない。

---

### User Story 7 - 原因を判断できるエラーを機械可読な形式で受け取る (Priority: P2)

API の利用者は、失敗したとき、原因を判断できる情報を、機械可読な形式で受け取れる。
例: 要件を満たすランナーがない、権限不足、不正な状態遷移、認証の失敗、重複した提出。

**Why this priority**: クライアント(WebUI、GitHub 連携)が、原因に応じた表示・処理を行うために必要。

**Independent Test**: 各種の失敗(要件を満たすランナーなし、権限不足、不正な遷移、認証失敗、重複)を起こし、応答の種類・理由・対象を確認する。

**Acceptance Scenarios**:

1. **Given** 要件を満たしうるランナーが登録されていない, **When** ジョブを提出する, **Then** その理由を示す機械可読なエラーが返る。
2. **Given** 権限のない主体, **When** 権限を要する操作を呼ぶ, **Then** 権限不足であること(必要な権限の種類)を示すエラーが返る。
3. **Given** 規則にない状態遷移, **When** 操作を呼ぶ, **Then** 不正な遷移であること(現在の状態と対象)を示すエラーが返る。
4. **Given** 失敗の応答, **When** 内容を確認する, **Then** 認証情報、payload、ログの本文、他のジョブの情報など、呼び出した主体に開示する権限のない情報を含まない。

---

### User Story 8 - API の定義から契約を確認し、バージョンで互換性を管理する (Priority: P2)

API は、機械可読な定義(OpenAPI)で記述され、バージョンが付く。クライアントは定義から生成できる。
互換性を壊す変更は、バージョンを上げて公開する。

**Why this priority**: クライアントを個別のパッケージとして独立に保つ(憲章 原則 1)ために必要。ただし、最初の公開の時点では 1 つの版でよい。

**Independent Test**: 定義から生成したクライアントで一連の操作を行う。実装と定義が食い違っていないことを、契約テストで確認する。

**Acceptance Scenarios**:

1. **Given** 公開された API の定義, **When** クライアントを生成する, **Then** 生成したクライアントだけで、ジョブの提出・参照・管理ができる。
2. **Given** 実装と API の定義, **When** 契約テストを実行する, **Then** 食い違いがなければ通り、食い違い(定義にない応答、定義と異なる形式)があれば失敗する。
3. **Given** 互換性を壊す変更, **When** 公開する, **Then** バージョンが上がり、旧バージョンのクライアントは(互換期間の方針に従い)影響を受けない。

---

### User Story 9 - 状態を変える呼び出しをすべて監査ログに残す (Priority: P2)

状態を変えるすべての呼び出しは、呼び出した主体を含めて監査ログに記録される。代理の場合は、代理元も記録される。

**Why this priority**: 憲章 原則 6 の要請。001 が定めるコアの記録に加えて、API 層で認証・認可の結果(拒否を含む)を残す。

**Independent Test**: 各種の状態変更(成功・拒否)を、各種の主体で呼び、監査ログの内容を確認する。

**Acceptance Scenarios**:

1. **Given** 状態を変える操作が成功した, **When** 監査ログを確認する, **Then** 呼び出した主体の種類と識別子、日時、対象、操作の種類が記録されている。
2. **Given** 代理による操作, **When** 監査ログを確認する, **Then** 名義上の主体と代理元の両方が記録されている。
3. **Given** 権限不足で拒否された操作, **When** 監査ログを確認する, **Then** 拒否の事実と呼び出した主体が記録されている。
4. **Given** 認証に失敗した呼び出し, **When** 監査ログを確認する, **Then** 失敗の事実が記録されている。認証情報の値そのものは記録されない。

---

### Edge Cases

- 認証情報(サービス用・ランナー用)を失効させた直後の呼び出し → 失効後に開始した呼び出しは認証に失敗する。失効前に開始した長い呼び出し(購読を含む)がどうなるかは、plan で定める。
- 同じ主体から同時に、同じジョブへの競合する操作(スケジュール変更と取り消しなど)が来る → コアの不変条件(001)に従い、一方が成功し、他方は不正な遷移として拒否される。
- 認証基盤が一時的に利用できない → 認証が必要な呼び出しは、原因(認証基盤の不通)を示して失敗する。ランナーとサービスの認証は、認証基盤に依存しない。
- 所属グループが複数ある利用者 → 対応するロールの権限の和集合で判定する。
- 設定でロールの対応を変えたとき、既にログイン済みの利用者 → 次の呼び出しから、新しい対応で判定する(再ログインを要しない範囲は plan で定める)。
- 一覧のページ分割の途中で、ジョブが追加・削除・状態変更された → ページの継ぎ目で重複・欠落が起きない、または起きうることを明示する(plan で定める)。
- 大きな応答(多数のジョブ、長いログ)や不正に大きな要求 → 上限を設け、上限を超えた要求は理由とともに拒否する。
- イントラネットの外からの到達 → 到達できない(FR-022)。
- 購読中の主体の権限が途中で失われる → 以後の通知は、その主体の権限の範囲に従う。

## Requirements *(mandatory)*

### Functional Requirements

**公開する機能**

- **FR-001**: システムは、コアの次の機能を、HTTP API として公開しなければならない。
  - ジョブ: 提出(位置の指定を含む)、一覧・詳細の参照、スケジュール変更、取り消し、強制中断、やり直し、ジョブごとの操作の経緯の参照
  - ランナー: 作成、一覧・詳細の参照、状態の変更(維持管理、削除など)、認証情報の失効と再発行
  - 監査ログ: 参照
- **FR-002**: システムは、API を OpenAPI で定義し、バージョンを付けなければならない。互換性を壊す変更は、バージョンを上げて公開する。クライアントは、定義から生成できなければならない。
- **FR-003**: システムは、API の応答が公開した定義と食い違わないことを、契約テストで検証できなければならない。
- **FR-004**: システムは、優先度・割り込みの概念を API に持たない(憲章 原則 5、001 FR-005)。順序を変える操作は、位置を指定した追加とスケジュール変更に限る。

**認証と認可**

- **FR-005**: システムは、API を呼ぶ主体を、人間の利用者・サービス・ランナーの 3 種類に区別して認証しなければならない。
  - 人間の利用者: 認証基盤(ポート)が確認した本人性と所属グループから、ロールを決める。
  - サービス: サービス用の認証情報で認証する。認証情報は失効できる。
  - ランナー: ランナーごとの認証情報(002 が発行・失効)で認証する。
- **FR-006**: システムは、操作の可否を、権限(permission)の単位で判定しなければならない。001 が定める権限(ジョブ追加、一般、スケジュール変更、取り消し、強制中断、管理、提出代行)に加え、002 が定めるランナー管理の権限、ランナー用の操作の権限を扱う。
- **FR-007**: システムは、ロール→権限、所属グループ→ロールの対応を、設定で変更できなければならない。コードの変更なしに変えられ、変更は監査ログに残る。
- **FR-008**: システムは、認証基盤を差し替え可能なポートとして定義しなければならない。API の定義と応答は、特定の認証基盤の名称・概念を含まない。偽の認証基盤で、外部サービスなしに、利用者としてログインして一連の操作を試験できなければならない。
- **FR-009**: システムは、サービス主体のうち提出代行の権限を持つものだけに、別の提出者の名義でのジョブの提出を許可しなければならない。一般の利用者・ランナーには許可しない。
- **FR-010**: システムは、失効した認証情報(サービス用・ランナー用)による呼び出しを、認証の失敗として拒否しなければならない。失効したランナーの認証情報では、ジョブを取得できない。
- **FR-011**: システムは、ランナーの認証情報で呼べる操作を、ランナー用の操作(ランナープロトコル)に限り、かつ自身に関する対象に限らなければならない。
- **FR-012**: システムは、認証の方式を主体の種類ごとに分けなければならない。人間の利用者は、認証基盤で本人性を確認したあと、有効期限付きのセッションを発行して認証する。サービスとランナーは、失効可能な長寿命のトークンで認証する(有効期限を持たず、失効するまで有効)。セッションの有効期限の具体的な値は設定で変えられ、既定値は plan で定める。

**エラー**

- **FR-013**: システムは、エラーを、利用者が原因を判断できる機械可読な形式で返さなければならない。少なくとも、要件を満たすランナーなし、権限不足、不正な状態遷移、認証の失敗、入力の不備、重複した提出を区別できなければならない。
- **FR-014**: システムは、エラーの応答に、呼び出した主体に開示する権限のない情報(認証情報、payload、ログの本文、他のジョブの情報など)を含めてはならない。

**一覧とキュー**

- **FR-015**: システムは、ジョブの一覧を、状態・提出者・期間で絞り込み、ページ分割して取得できなければならない。
- **FR-016**: システムは、すべての利用者に、キュー全体(待機中のジョブ)の、待機列の順序つきの一覧を提供しなければならない(001 FR-022)。

**イベントの配信**

- **FR-017**: システムは、ジョブとランナーの状態の変更を、クライアントがほぼ即時に受け取れる手段(購読)を提供しなければならない。配信の方式は、サーバーからクライアントへの一方向のイベント配信(SSE)とする。切断後の再接続では、取りこぼした変更を補える(または取りこぼしを検知して再取得できる)こと。
- **FR-018**: システムは、購読で配信する内容を、状態・識別子・短い説明に限らなければならない。ログの本文・成果物の中身・payload を含めない(001 FR-030)。

**バージョニング**

- **FR-019**: システムは、API のバージョンを、リクエストの URL に含めて示さなければならない(例: `/v1/...`)。互換性を壊す変更は、新しいバージョンの URL として公開し、旧バージョンは互換期間のあいだ並行して提供する。

**監査**

- **FR-020**: システムは、状態を変えるすべての呼び出しを、呼び出した主体(種類と識別子)・日時・対象・操作の種類とともに、監査ログに記録しなければならない。代理の場合は、名義上の主体と代理元の両方を記録する。
- **FR-021**: システムは、権限不足による拒否と認証の失敗を、監査ログに記録しなければならない。認証情報の値そのものは記録しない。

**ネットワーク境界**

- **FR-022**: システムは、イントラネット内からのみ到達できなければならない(憲章 原則 8)。ランナーへの着信接続を必要としない。

**機密保護(憲章 S1〜S6)**

- **FR-023**: システムは、API が外部へ書き出すものを、書き出し台帳(inputs/13-security-egress)に載ったものだけとしなければならない。GitHub への書き戻し(E9)と通知(E10)は、状態・短い説明・リンクに限る。台帳にない書き出しは行わない。
- **FR-024**: システムは、テレメトリ・利用状況の送信・外部の配信資産の読み込みを行ってはならない(台帳 E11)。
- **FR-025**: システムは、ランナーから受け取ったログ・成果物を、API の利用者のうち参照の権限を持つ者だけが参照できるようにし、外部の連携先(通知、書き戻し)には本文を渡してはならない。
- **FR-026**: システムは、認証情報(サービス用・ランナー用のトークンなど)を、保存・ログ・応答・監査ログに平文で残してはならない。発行時の 1 度だけ返す。

### Key Entities *(include if feature involves data)*

- **主体(Principal)**: 認証済みの呼び出し元。種類(人間の利用者/サービス/ランナー)、識別子、所属グループ(人間のみ)を持つ。
- **ロール**: 権限の集合。設定で定義する。
- **権限(Permission)**: 操作の可否の単位。設定で、ロールに対応づける。
- **サービス用の認証情報**: サービス主体を認証する情報。失効できる。提出代行などの権限を持つ。
- **所属グループ→ロールの対応**: 認証基盤から得た所属グループを、ロールに対応づける設定。
- **エラー**: 失敗の種類、原因、対象を、機械可読な形式で表す。
- **状態変更のイベント**: ジョブ・ランナーの状態の変更を表す通知。状態・識別子・短い説明に限る。
- **監査ログ**: 状態を変える呼び出しの記録(呼び出した主体、代理元、対象、操作、日時、結果)。001 のものを共有する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: API の定義から生成したクライアントだけで、ジョブの提出・参照・管理(スケジュール変更、取り消し、強制中断、やり直しを含む)の全操作を行える。WebUI や GitHub 連携の実装は使わない。
- **SC-002**: 偽の認証基盤だけで、外部サービスなしに、利用者としてログインして、001・002 が定める主要な操作を一通り試験できる。
- **SC-003**: サービス主体による代理提出では、監査ログの 100% で、名義上の提出者と代理元の両方が確認できる。一般の利用者による代理提出の試行は 100% 拒否される。
- **SC-004**: 失効した認証情報(サービス用・ランナー用)による呼び出しは、100% 認証に失敗する。失効したランナーは、ジョブを取得できない。
- **SC-005**: 権限を持たない主体による操作は、権限の種類ごとの試験の 100% で拒否され、拒否の事実が監査ログに残る。
- **SC-006**: 失敗の応答は、試験した失敗の種類(要件を満たすランナーなし、権限不足、不正な遷移、認証失敗、入力の不備、重複)のすべてで、機械可読な形式で原因を区別できる。
- **SC-007**: 状態の変更が、購読しているクライアントに、通常の負荷で 3 秒以内に届く。
- **SC-008**: 契約テストで、実装と API の定義の食い違いがあれば失敗として検出できる。
- **SC-009**: 台帳にない外部への書き出し、テレメトリの送信が、送信を記録するテスト用の偽サーバーで 0 件であることを確認できる。
- **SC-010**: 通常の負荷(同時に操作する利用者 50 人まで)で、単件の操作と一覧の取得の応答が、利用者が待ちを感じない時間(2 秒以内)で返る。

## Assumptions

- 認証基盤は、本人性と所属グループを返すポートとして定義する。実際のアダプタ(組織の認証基盤)は、本 feature の範囲外で、設定で差し替える。
- 偽の認証基盤は、本人性と所属グループを、テストの設定で与えられる(外部サービス不要)。
- サービス主体の認証情報の発行・失効は、ランナーの認証情報(002)と同様に、管理の権限を持つ主体が行う。
- 利用者のロールの既定の対応(所属グループなし → 閲覧のみ)は、設定の初期値として与える。具体的な初期値は plan で定める。
- 閲覧の範囲は、001 に従い、すべての利用者がすべてのジョブの状態・結果の要約・操作の経緯を見られる。ログの本文・成果物の閲覧権限は、004 で定める。
- 購読で配信する内容は、状態・識別子・短い説明に限る。配信に失敗してもコアの状態は変わらない(再取得で追いつける)。
- 通常の負荷は、001 の想定(少数〜数十人の利用者、数台〜数十台のランナー)の範囲とする。
- 本 feature の範囲外: ランナーがジョブを取得・実行・報告するためのプロトコルの定義(004 で定義し、本 API が提供する)、画面(006)、GitHub 固有の認証(005)。
- 依存: 001(ジョブの受付・キュー)と 002(ランナーの管理)のコア。コアは API に依存しない(憲章 原則 1)。
