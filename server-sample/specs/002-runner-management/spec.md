# Feature Specification: コア — ランナーとジョブの割り当ての管理(最小版)

**Feature Branch**: `job_service`(spec ディレクトリ: `specs/002-runner-management`)

**Created**: 2026-11-21

**Status**: Draft

**Input**: User description: inputs/04-specify-002-runner-management.md「機能: コア — ランナーとジョブの管理(最小版)」(背景と目的、ユビキタス言語、FR-1〜FR-7、スコープ外、未確定事項)。「別途詰めたい」領域のため、他の feature(001、004)が必要とする最小の契約と境界だけを定め、不明点は clarify に回す。

## 背景と目的

ジョブを実行するランナー(評価機材に接続された Windows PC 上のエージェント)を登録・管理し、ジョブとの割り当てを管理する。
どのランナーが何をできるか(能力)を記述し、ジョブのランナー要件と照合する仕組みを提供する。

本 feature は、次の 2 つの契約を最小限で定める。

- **001(ジョブの受付・キュー)への契約**: 提出時の「要件を満たしうるランナーが登録されているか」の判定と、ランナーが空いたときの割り当ての条件。
- **004(ランナーエージェント)への契約**: ランナーの認証情報、起動時の登録(能力の申告)、生存通知、機材の異常の申告、割り当てのリース。

能力の値の意味はコアが解釈しない。コアは用途固有の語(機材の種類の名前など)を持たない(憲章 原則 1、3)。

## Clarifications

### Session 2026-11-21

- Q: 能力の値の形式と、要件の文法(比較の種類)は? → A: 能力の値は、1 つの値または複数の値(集合)を持てる。比較の種類は「一致」「いずれかに一致」「数値の大小」「版の大小」「集合に含まれる(包含)」の 5 種類とする。
- Q: 能力の登録方法は? → A: ランナーの自己申告のみ(許可した項目に限る)。ここでいう「登録」は、ランナーがサーバーに、自身が起動したことを伝えることを指す。
- Q: 機材の接続状態(機材側の故障)を、ランナーの状態にどう反映するか? → A: ランナーが機材の異常を申告すると、自動で割り当てを止める状態にする。故障の検知は自動ではできないため、ランナーの PC 内で動作するツールから、ランナーを通じて異常(と回復)を通知できるようにする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ランナーを作成し、ランナーが起動時に登録する (Priority: P1)

ランナー管理の権限を持つ利用者は、ランナーを名前を付けて作成し、そのランナー用の認証情報(トークン)を受け取って PC に設定する。
ランナーは起動したとき、トークンを使ってサーバーに登録(起動したことの通知)を行い、あわせて自身の能力の集合を申告する。
申告できる能力のキーは、許可リストに載ったものに限る。能力は、登録のたびに申告の内容で置き換わる。

**Why this priority**: ランナーが登録されていなければ、001 の提出はすべて拒否され、割り当ても起きない。他のすべての機能の前提になる。

**Independent Test**: 偽の主体(権限あり/なし)でランナーを作成し、偽のランナーから能力を申告して登録する。作成・登録の結果、発行されたトークン、拒否の理由、監査ログを確認する。

**Acceptance Scenarios**:

1. **Given** ランナー管理の権限を持つ主体, **When** 名前を指定してランナーを作成する, **Then** ランナーが識別子付きで作成され、未登録(能力なし)・offline の状態になり、トークンが 1 度だけ返る。作成は監査ログに残る。
2. **Given** 同じ名前のランナーが作成済み, **When** 同じ名前で作成する, **Then** 作成は理由とともに拒否される。
3. **Given** 作成済みのランナー, **When** ランナーが有効なトークンで、許可リストのキーだけからなる能力を申告して登録する, **Then** 申告した能力がそのランナーの能力になり、ランナーは online になる。以後の判定と割り当てにこの能力が使われる。変更前後の能力が監査ログに残る。
4. **Given** 登録済みのランナー, **When** ランナーが再起動し、異なる能力を申告して再び登録する, **Then** 能力は新しい申告の内容で置き換わる。
5. **Given** 許可リストにないキーを含む申告, **When** ランナーが登録する, **Then** 登録は理由とともに拒否され、能力は変わらない。拒否が監査ログに残る。
6. **Given** ランナー管理の権限を持たない主体, **When** ランナーを作成する, **Then** 権限がないとして拒否され、拒否が監査ログに残る。

### User Story 2 - 要件を満たしうるランナーがいるかを判定する (Priority: P1)

001 のジョブ提出時に、ジョブのランナー要件を満たしうるランナーが 1 台以上登録されているかを判定する。
ランナーが空いているか・online か・機材の異常があるかは判定に含めない(一時的な状態で提出を拒否しないため)。

**Why this priority**: 001 の受付(FR-002)がこの判定に依存する。判定がなければ、実行できないジョブが待機列に残り続ける。

**Independent Test**: 能力の異なる偽のランナーを数台登録し、さまざまな要件について判定の結果(満たしうる/満たしえない)を確認する。

**Acceptance Scenarios**:

1. **Given** 要件を満たす能力を申告済みのランナーが 1 台ある(状態は offline), **When** その要件で判定する, **Then** 「満たしうる」と返る。
2. **Given** どのランナーの能力も要件を満たさない, **When** 判定する, **Then** 「満たしえない」と返る。
3. **Given** 要件を満たす唯一のランナーが削除された, **When** 判定する, **Then** 「満たしえない」と返る。
4. **Given** 作成されたが一度も登録していない(能力のない)ランナーだけがある, **When** 空でない要件で判定する, **Then** 「満たしえない」と返る。
5. **Given** 要件が文法に合わない(未知の比較の種類、数値でない値への数値の比較など), **When** 判定する, **Then** 判定は理由とともにエラーになり、「満たしうる」とはならない。
6. **Given** 能力「対応機材」の値が集合 {X, Y} のランナー, **When** 要件「対応機材 が Y を含む」で判定する, **Then** 「満たしうる」と返る。

### User Story 3 - 空いた online のランナーに、条件を満たすジョブだけを割り当てる (Priority: P1)

online で、実行中のジョブを持たないランナーが、次のジョブを求める。システムは、そのランナーの能力が要件を満たす待機中のジョブのうち、
待機列で最も前のものを割り当て、一定時間のリースとして貸し出す。条件を満たすジョブがなければ、何も割り当てない。

**Why this priority**: 割り当てがなければジョブは実行されない。001 の「並び順どおりの割り当て」(FR-009、FR-010)を、ランナー側から成り立たせる。

**Independent Test**: 偽のランナーと待機列を用意し、ランナーがジョブを求めたときに、割り当てられるジョブ(またはなし)とリースの期限を確認する。

**Acceptance Scenarios**:

1. **Given** online で空いたランナー R、待機列に R の能力で実行できないジョブ A、実行できるジョブ B がこの順に並ぶ, **When** R がジョブを求める, **Then** B が割り当てられ、リースの期限が返る。A は待機列に残る。
2. **Given** R の能力で実行できる待機中のジョブがない, **When** R がジョブを求める, **Then** 何も割り当てられない。
3. **Given** R が実行中のジョブを持つ, **When** R が別のジョブを求める, **Then** 割り当ては行われない(1 台に同時に 1 件)。
4. **Given** R が maintenance・offline・機材の異常のいずれか, **When** R がジョブを求める, **Then** 割り当ては行われない。
5. **Given** 2 台のランナーが同時にジョブを求め、実行できるジョブが 1 件だけ, **When** 割り当てを行う, **Then** そのジョブは 1 台だけに割り当てられる。

### User Story 4 - 生存通知でランナーの状態とリースを保つ (Priority: P1)

ランナーは定期的に生存通知を送る。生存通知を受けると、ランナーは online になり、実行中のジョブがあればそのリースが延長される。
一定時間生存通知がなければ、ランナーは offline になり、リースは延長されずに期限を迎える。リースが切れたジョブの扱いは 004 と別途定める。

**Why this priority**: 割り当ての条件(online)とリースの延長は、生存通知に依存する。004 のランナーエージェントとの最小の契約である。

**Independent Test**: 時刻を制御できる偽の時計を使い、生存通知の有無に応じた状態の変化とリースの期限を確認する。

**Acceptance Scenarios**:

1. **Given** 登録済みで offline のランナー(maintenance・機材の異常ではない), **When** 有効なトークンで生存通知を送る, **Then** ランナーは online になり、最終応答時刻が更新される。
2. **Given** 実行中のジョブを持つランナー, **When** リースの期限前に生存通知を送る, **Then** リースの期限が延長される。
3. **Given** online のランナー, **When** offline と判定する時間を超えて生存通知がない, **Then** ランナーは offline になり、状態の変化が監査ログに残る。
4. **Given** 実行中のジョブのリース, **When** 延長されずに期限を過ぎる, **Then** リース切れとして記録され、以後そのリースによる延長は受け付けない(ジョブの扱いは 004 と別途定める)。
5. **Given** maintenance のランナー, **When** 生存通知を送る, **Then** 最終応答時刻は更新されるが、状態は maintenance のまま変わらない。

### User Story 5 - 機材の異常を申告し、割り当てを自動で止める (Priority: P2)

機材の故障は自動では検知できない。ランナーの PC 内で動作するツール(外部ツールや点検用のツール)が機材の異常に気付いたとき、
ランナーを通じてサーバーへ異常を申告できる。申告を受けたランナーは「機材の異常」の状態になり、新しい割り当てが自動で止まる。
機材が直ったら、同じ経路で回復を申告すると、割り当てが再開される。

**Why this priority**: 故障した機材にジョブが流れ続けて失敗が積み重なるのを防ぐ。ただし、手動の maintenance(US6)でも最小限の代わりになるため P2 とする。

**Independent Test**: 偽のランナーから異常と回復を申告し、状態の変化、割り当ての停止と再開、監査ログを確認する。

**Acceptance Scenarios**:

1. **Given** online のランナー, **When** ランナーが有効なトークンで機材の異常を申告する(短い説明付き), **Then** ランナーは機材の異常の状態になり、以後割り当てが行われない。申告と説明が監査ログに残り、ランナーの一覧で全員が確認できる。
2. **Given** 機材の異常の状態のランナー, **When** ランナーが回復を申告する, **Then** 生存通知の状況に応じて online または offline に戻り、割り当てが再開される。
3. **Given** 実行中のジョブを持つランナー, **When** 機材の異常を申告する, **Then** 実行中のジョブはシステムからは止めない(ジョブの結果はランナーの報告による。004)。リースも生存通知で延長され続ける。
4. **Given** 機材の異常の状態のランナー, **When** 生存通知が途絶えて offline と判定される時間を過ぎ、その後また生存通知が届く, **Then** 機材の異常は解除されず、状態は機材の異常のまま(回復の申告があるまで)。
5. **Given** 機材の異常の状態のランナー, **When** ランナー管理の権限を持つ主体が異常を解除する, **Then** 回復の申告と同じく割り当てが再開される(ツールが回復を申告できない場合の手段)。

### User Story 6 - ランナーを無効化(maintenance)・削除する (Priority: P2)

ランナー管理の権限を持つ利用者は、ランナーを maintenance にして新しい割り当てを止め、後で戻せる。不要になったランナーは削除できる。

**Why this priority**: 機材の保守時に、そのランナーへ新しいジョブが流れないようにする運用の最小限の手段。登録・割り当てより後でよい。

**Independent Test**: 偽のランナーを maintenance にし、割り当てが止まること、戻すと再開すること、削除後に判定と割り当ての対象から外れることを確認する。

**Acceptance Scenarios**:

1. **Given** online のランナー, **When** ランナー管理の権限を持つ主体が maintenance にする, **Then** 以後そのランナーには割り当てが行われない。理由とともに監査ログに残る。
2. **Given** 実行中のジョブを持つランナー, **When** maintenance にする, **Then** 実行中のジョブは止められず、リースも生存通知で延長され続ける(実行中ジョブがあるときの運用の詳細はスコープ外)。
3. **Given** maintenance のランナー, **When** maintenance を解除する, **Then** 機材の異常と生存通知の状況に応じて、機材の異常・online・offline のいずれかになる。
4. **Given** 実行中のジョブを持たないランナー, **When** 削除する, **Then** ランナーとそのトークンが無効になり、判定・割り当ての対象から外れる。監査ログに残る。
5. **Given** 実行中のジョブを持つランナー, **When** 削除する, **Then** 削除は理由とともに拒否される。

---

### User Story 7 - ランナーのトークンを発行・失効する (Priority: P2)

ランナー管理の権限を持つ利用者は、ランナーのトークンを失効させ、新しいトークンを発行できる(漏えいの疑い、PC の入れ替えなど)。
失効したトークンでは、登録・生存通知・異常の申告・割り当ての要求を受け付けない。

**Why this priority**: ランナーの本人性はトークンだけに依る。漏えい時に止める手段が要るが、作成時の発行(US1)があれば最小の運用は回る。

**Independent Test**: トークンを失効・再発行し、旧トークンでの要求が拒否され、新トークンで受け付けられることを確認する。

**Acceptance Scenarios**:

1. **Given** 有効なトークン, **When** ランナー管理の権限を持つ主体が失効させる, **Then** 以後そのトークンでの登録・生存通知・異常の申告・割り当ての要求は認証の失敗として拒否される。
2. **Given** トークンを失効させたランナー, **When** 新しいトークンを発行する, **Then** 新しいトークンが 1 度だけ返り、それで登録以降の操作ができる。旧トークンは使えないまま。
3. **Given** トークンの発行後, **When** 誰かがそのトークンを再表示しようとする, **Then** システムはトークンの値を表示できない。
4. **Given** 別のランナーのトークン, **When** そのトークンでランナー R として生存通知を送る, **Then** 拒否される(トークンは 1 台のランナーに結び付く)。

### Edge Cases

- 能力が空の申告: 登録できる。要件が空のジョブだけを満たしうる。
- 要件が空のジョブ: すべての登録済みランナーが満たしうる。
- 作成後に一度も登録していないランナー: 能力を持たず、offline のまま。空の要件だけを満たしうる。
- 再登録で、待機中のジョブの要件を満たすランナーがいなくなった: 待機中のジョブは待機列に残り、自動では取り消さない(提出時の判定だけが拒否に使われる)。運用者は待機列とランナーの一覧で気付ける。
- 再登録で、実行中のジョブの要件を満たさなくなった: 実行中のジョブはシステムからは止めない。
- 実行中のジョブ(有効なリース)を持つランナーが再登録した(エージェントの再起動): 再登録は受け付け、有効なリースがあったことを監査ログに残す。そのジョブの扱いは、リース切れと同じく 004 と別途定める。
- 削除済みのランナーと同じ名前での作成: 新しいランナーとして作成でき、削除前のランナーとは別の識別子を持つ。
- 値の型が比較に合わない場合: 要件の側(未知の比較の種類、指定値が数値・版として解釈できない、指定値の形が比較に合わない)は、提出時の要件の検査で文法のエラーとする。能力の側(数値の大小を数値でない能力の値に、包含を集合でない値に適用する等)は、その条件を「満たさない」とする。
- 時刻のずれ: 状態とリースの判定は、サーバー側の時刻だけで行う(ランナーの時刻を使わない)。
- 生存通知の重複・遅延: 期限前に届いたものだけが延長に使われる。延長は通知の受信時刻から計算するため、重複しても結果は変わらない。
- 異常の申告の重複: すでに機材の異常の状態なら、状態は変わらず、説明だけを更新する。異常でないときの回復の申告は、何も変えない。
- ランナー管理の権限と、ランナーのトークンは別物である。ランナーのトークンではランナーの作成・削除・maintenance・トークンの操作はできない。

## Requirements *(mandatory)*

### Functional Requirements

**ランナーの作成と登録(能力の申告)**

- **FR-001**: ランナー管理の権限を持つ主体は、名前を指定してランナーを作成できなければならない。名前は、削除されていないランナーの間で一意とする。作成したランナーは、能力を持たない未登録の状態、かつ offline で始まる。
- **FR-002**: ランナーは、起動時に、有効なトークンでサーバーへ登録(起動したことの通知)を行い、能力の集合を申告できなければならない。登録を受けたランナーは、生存通知を受けたときと同じく状態が決まる(FR-010)。
- **FR-003**: 能力は、ランナーの自己申告だけで設定される。登録のたびに、能力の集合は申告の内容で丸ごと置き換わる。人間の利用者は能力を直接編集しない。
- **FR-004**: 申告できる能力のキーは、許可リストに載ったものに限る。許可リストはランナー管理の権限を持つ主体が設定し、変更は監査ログに残す。許可リストにないキーを含む申告、型の合わない値を含む申告は、登録ごと理由とともに拒否し、能力を変えてはならない(既定は拒否。憲章 S3)。
- **FR-005**: 能力はキーと値の組とする。値は、1 つの値、または複数の値の集合とする。コアは値の意味を解釈せず、比較の種類に応じた比較だけを行う。
- **FR-006**: 能力の変更は、登録の受付後の最初の判定・割り当てから反映されなければならない。実行中のジョブは、能力の変更を理由にシステムからは止めない。

**要件の文法と判定(001 への契約)**

- **FR-007**: ランナー要件は条件の集まりとし、すべての条件を満たすとき「要件を満たす」とする。各条件は、能力のキー、比較の種類、比較する値からなる。比較の種類は次の 5 つとする。
  - 一致: 能力の値(1 つの値)が、指定した値と等しい
  - いずれかに一致: 能力の値(1 つの値)が、指定した値の一覧のいずれかと等しい
  - 数値の大小: 能力の値を数値として、指定した値と比べる(より大きい・以上・より小さい・以下)
  - 版の大小: 能力の値を版(区切られた数の並び)として、指定した版と比べる(より新しい・以上・より古い・以下)
  - 包含: 能力の値(集合)が、指定した値をすべて含む
  - 要件に指定したキーを、ランナーが能力として持たない場合、その条件は満たさない。
- **FR-008**: システムは、ランナー要件を与えられたとき、その要件を満たす能力を持つランナーが、削除されていないランナーの中に 1 台以上あるかを判定しなければならない。状態(online / offline / 機材の異常 / maintenance)と、空いているかどうかは判定に含めない。文法に合わない要件(未知の比較の種類、比較に合わない指定値など)は、判定の対象とせず理由とともにエラーとする。
- **FR-009**: 要件と能力の照合は、判定(FR-008)と割り当て(FR-013)で同じ規則を使わなければならない(提出時に満たしうるとされた要件が、割り当てで別の解釈をされない)。

**ランナーの状態**

- **FR-010**: ランナーの状態は、次の優先順で決まる。
  1. maintenance: ランナー管理の権限を持つ主体が設定している間
  2. 機材の異常: ランナーが異常を申告し、回復の申告(または権限を持つ主体による解除)がまだない間
  3. offline: 最後の登録・生存通知から、offline と判定する時間(既定 90 秒、設定値)が過ぎている、または一度も登録していない
  4. online: 上のいずれでもない
  - maintenance と機材の異常は、生存通知の有無では解除されない。maintenance の間も、機材の異常の申告と回復の申告は記録され、解除後の状態に反映される。

**機材の異常の申告**

- **FR-011**: ランナーは、有効なトークンで、機材の異常とその回復を申告できなければならない。申告は、ランナーの PC 内で動作するツールが、ランナーを通じて行えるようにする(ツールからランナーへの伝え方は 004 で定める)。異常の申告には短い説明(長さに上限を設ける)を付けられる。
- **FR-012**: ランナー管理の権限を持つ主体は、機材の異常を手動で解除できなければならない(ツールが回復を申告できない場合のため)。

**割り当てとリース**

- **FR-013**: システムは、online で実行中のジョブを持たないランナーがジョブを求めたとき、そのランナーの能力が要件を満たす待機中のジョブのうち、待機列で最も前のものを 1 件割り当てなければならない。条件を満たすジョブがなければ、何も割り当てない。待機列の並び順は 001 が定める。
- **FR-014**: システムは、maintenance・機材の異常・offline のランナー、実行中のジョブを持つランナーに、割り当てを行ってはならない。1 件のジョブを 2 台以上のランナーに同時に割り当ててはならない(同時に求められた場合も)。
- **FR-015**: 割り当ては、期限付きのリースとして記録しなければならない。リースの長さの既定は 3 分とし、設定値で変えられる。
- **FR-016**: システムは、実行中のジョブを持つランナーから、リースの期限前に生存通知を受けたとき、リースの期限を、受信時刻からリースの長さだけ延長しなければならない。ランナーへ伝える生存通知の間隔の既定は 30 秒とし、設定値で変えられる。リースの長さと offline と判定する時間は、生存通知の間隔の 2 倍より短く設定できない。
- **FR-017**: システムは、延長されずに期限を過ぎたリースを、リース切れとして記録し、以後そのリースの延長を受け付けてはならない。リース切れのジョブの扱い(待機列へ戻す/失敗とする)とジョブの状態遷移は、004 と別途定める。
- **FR-018**: ランナーの状態とリースの判定は、サーバー側の時刻だけで行わなければならない。

**無効化と削除**

- **FR-019**: ランナー管理の権限を持つ主体は、ランナーを maintenance にし、また解除できなければならない。maintenance にする理由を記録できる。実行中のジョブは止めず、そのリースは生存通知で延長され続ける。
- **FR-020**: ランナー管理の権限を持つ主体は、実行中のジョブを持たないランナーを削除できなければならない。削除したランナーのトークンは無効になり、ランナーは判定・割り当ての対象から外れる。実行中のジョブを持つランナーの削除は、理由とともに拒否する。
- **FR-021**: 削除したランナーの識別子と名前は、過去のジョブ・監査ログから辿れるよう記録に残す(新しいランナーに同じ識別子を与えない)。

**認証情報(トークン)**

- **FR-022**: システムは、ランナーの作成時と再発行の操作時に、そのランナーに結び付いたトークンを発行し、発行時に 1 度だけ返さなければならない。発行後、システムはトークンの値を誰にも表示できない形で保持する。
- **FR-023**: ランナー管理の権限を持つ主体は、ランナーのトークンを失効させられなければならない。1 台のランナーが同時に持てる有効なトークンは 1 つとし、再発行すると以前のトークンは失効する。
- **FR-024**: システムは、ランナーからの登録・生存通知・異常と回復の申告・割り当ての要求を、そのランナーの有効なトークンでのみ受け付けなければならない。失効・無効のトークン、別のランナーのトークンによる要求は拒否する。
- **FR-025**: ランナーのトークンは、ランナーとしての操作(登録、生存通知、異常と回復の申告、割り当ての要求、004 が定める報告)だけに使え、ランナーの作成・削除・maintenance・トークンの操作・許可リストの変更や、ジョブの提出には使えない。

**権限と閲覧**

- **FR-026**: システムは、ランナーの作成・maintenance の設定と解除・機材の異常の手動の解除・削除・トークンの発行と失効・能力のキーの許可リストの変更を、「ランナー管理」の権限(permission)で判定しなければならない。この権限は、001 の「管理」の権限とは別とし、自動では含めない。
- **FR-027**: すべての利用者は、ランナーの一覧(名前、状態、能力、機材の異常の説明、実行中のジョブの識別子、最終応答時刻)を確認できなければならない(ランナーが共用で、順番の相談の材料になるため)。トークンの値は表示しない。

**監査**

- **FR-028**: システムは、ランナーの作成・登録(能力の変更前後の値)・状態の変更(maintenance の設定と解除、機材の異常と回復の申告と手動の解除、自動の online / offline の変化)・削除・トークンの発行と失効・許可リストの変更・リース切れ・登録や申告の拒否を、操作者(ランナー、人間の主体、自動の変化はシステム)・日時・対象・操作の種類・変更前後の値・理由とともに監査ログに残さなければならない。権限・認証による拒否も記録する。トークンの値は監査ログに含めない。
- **FR-029**: 監査ログの閲覧範囲と保持期間は、001 の監査ログと同じ規則に従う(001 FR-026、FR-032)。具体的には、ランナーごとの操作の経緯(成功した作成・登録・状態の変更・削除・トークンの発行と失効・許可リストの変更・リース切れの、操作者・日時・変更前後の値・理由)は、すべての利用者が確認できる。権限・認証・申告の検査による拒否の記録を含む監査ログ全体は、001 の「管理」の権限(`audit.read_all`)を持つ主体だけが閲覧できる(「ランナー管理」の権限は閲覧を含まない)。

**コアの性質**

- **FR-030**: ランナー管理は、001 と同じくコアの一部であり、特定のプラットフォーム・用途・実行ツールの語(機材の種類の名前など)を含まず、それらの部品に依存してはならない。能力のキーと値、機材の異常の説明の中身は、用途ごとの設定(プロファイル)と運用が与える。
- **FR-031**: ランナー管理は、外部への送信を自ら行ってはならない。ランナーへの応答(割り当て・リースの期限・生存通知の間隔)は、ランナーからの要求への応答としてだけ返す(ランナーへの着信接続を要しない。憲章 原則 8)。

### 外部への書き出し(憲章 S2)

ランナー管理自身は外部へ何も送信しない。ランナーからコアへ届く情報(登録時の能力の申告、生存通知、機材の異常と回復の申告)は、書き出し台帳の E4(ランナーエージェント → コア API)に当たる。

| 経路 | 内容 | 台帳の対応 | 制限 |
|---|---|---|---|
| ランナー → コア(登録) | 能力の集合 | E4 | 許可リストのキーだけ。ホスト名・ユーザー名・パス等の PC 情報は、許可リストに載せない限り送らない(FR-004) |
| ランナー → コア(異常の申告) | 機材の異常/回復、短い説明 | E4 | 説明は長さに上限を設ける。作業フォルダ外の情報(ファイル内容、環境変数、資格情報)を含めない。説明に載せてよい内容は 004 と台帳で定める |
| コア → ランナー(応答) | 割り当てたジョブの識別子とジョブ定義(004 が実行に要するもの)、リースの期限、生存通知の間隔 | E16(2026-11-21 に追記) | 他のランナーの情報・他のジョブの情報・トークンを含めない |

機材の異常の申告は、台帳 E4 に「ランナーの状態(機材の異常とその回復、短い説明)」として追記済み(2026-11-21)。

### Key Entities *(include if feature involves data)*

- **ランナー(Runner)**: ジョブを 1 件ずつ実行する主体。識別子、名前、能力の集合、最終登録日時、最終応答時刻、maintenance の設定と理由、機材の異常の有無と説明、実行中の割り当て(なし/1 件)を持つ。状態は FR-010 の規則で決まる。削除後も識別子と名前は記録に残る。
- **能力(Capability)**: ランナーの性質を表すキーと値の組。値は 1 つの値または集合。コアは値の意味を解釈しない。ランナーの申告だけで設定される。
- **能力のキーの許可リスト**: ランナーが申告してよいキー(と値の型)の一覧。ランナー管理の権限を持つ主体が設定する。
- **ランナー要件(Runner Requirement)**: ジョブが求める能力の条件の集まり。各条件は、能力のキー、比較の種類(一致・いずれかに一致・数値の大小・版の大小・包含)、比較する値からなる。すべての条件を満たすとき「要件を満たす」とする。
- **割り当て(Assignment)/リース(Lease)**: ジョブとランナーの対応。割り当て日時、リースの期限、最終延長日時、状態(有効/リース切れ/終了)を持つ。1 件のジョブに有効な割り当ては同時に 1 つ。
- **ランナーのトークン(Runner Token)**: ランナーの本人性を示す認証情報。1 台のランナーに結び付き、発行日時、失効日時を持つ。値はシステムからは再表示できない。
- **監査ログの記録**: 001 と共通。操作者(ランナー、人間の主体、またはシステム)、日時、対象のランナー、操作の種類、変更前後の値、理由、結果(成功/拒否)。
- **ジョブ(参照のみ)**: 001 のもの。ランナー管理は、待機列の並び順とジョブの要件を参照して割り当てを決めるが、ジョブの状態遷移は 001・004 が定める。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 要件と能力の組み合わせ(5 つの比較の種類、1 つの値と集合、キーの欠落、型の不一致)を網羅したテストで、判定(満たしうるか)と割り当て(条件を満たすか)の結果が食い違う例が 0 件である。
- **SC-002**: 要件を満たさないランナーへの割り当て、maintenance・機材の異常・offline のランナーへの割り当て、1 台への 2 件以上の同時の割り当て、1 件のジョブの 2 台への割り当てが、並行の要求を含むテストで 0 件である。
- **SC-003**: 空いた online のランナーがジョブを求めてから、割り当て(またはなし)の結果が返るまで 2 秒以内である(待機中のジョブ 500 件、ランナー 50 台の規模で、95% 以上)。
- **SC-004**: 生存通知が途絶えたランナーは、offline と判定する時間 + 30 秒以内に offline になり、その時点以降は新しい割り当てを受けない。
- **SC-005**: 生存通知を間隔どおりに送り続けるランナーのリースが、期限切れになった例が 0 件である(長時間のジョブを模したテストで)。
- **SC-006**: 機材の異常を申告したランナーに、申告の受付後に新しいジョブが割り当てられた例が 0 件である。回復の申告(または手動の解除)のあとは、次のジョブの要求から割り当てが再開される。
- **SC-007**: 許可リストにないキーを含む能力の申告が、テストで 100% 拒否され、能力が変わった例が 0 件である。
- **SC-008**: 失効・無効・別のランナーのトークンによる登録・生存通知・申告・割り当ての要求が、テストで 100% 拒否される。発行後にトークンの値が画面・応答・監査ログに現れた例が 0 件である。
- **SC-009**: ランナー管理の権限を持たない主体による作成・maintenance・異常の解除・削除・トークンの操作・許可リストの変更が、権限の組み合わせを網羅したテストで 100% 拒否される。
- **SC-010**: ランナーの作成・登録・状態の変化・削除・トークンの操作・許可リストの変更の 100% が監査ログに記録される。
- **SC-011**: 新しいランナーは、権限を持つ利用者による作成(トークンの受け取り)1 回と、PC へのトークンの設定・ランナーの起動だけで、online になり割り当てを受けられる。
- **SC-012**: ランナー管理の部分に、用途固有の語・プラットフォーム固有の語・それらの部品への依存が存在しないことを、001 と同じ自動の検査で確認でき、検出が 0 件である。

## Assumptions

- 入力の「管理者」は、憲章 原則 9 と 001 にあわせて、「ランナー管理」の権限を持つ主体と読み替えた。誰に付与するかは運用で決める。
- 用語: 本 spec では、人間がランナーの記録とトークンを用意する操作を「作成」、ランナーが起動して自身の存在と能力をサーバーに伝える操作を「登録」と呼ぶ(Clarifications 2026-11-21)。001 の「要件を満たしうるランナーが登録されているか」は、削除されていないランナーのうち、申告済みの能力が要件を満たすものがあるか、と読む。
- 入力 FR-2 の「管理者が能力を更新できる」は、Clarifications の回答(自己申告のみ)により取り下げた。人間が能力に関与できるのは、許可リストの設定だけとする。
- 能力の申告の中身(どの値を申告するか)は、ランナー側の設定やツールが与える。PC や機材から能力を自動で取得する仕組みは、入力どおりスコープ外(004 で必要なら扱う)とする。
- 機材の故障の検知は自動ではできない前提とする。異常を見つけるのは、ランナーの PC 内で動作するツール(または人)であり、コアは申告を受けて割り当てを止めるだけである。ツールからランナーへの伝え方は 004 で定める。
- 利用者(人間)の本人性と権限は、001 と同じく呼び出し元(コア API 003 と認証のアダプタ)が確認済みとして渡す。ランナーの本人性は、本 feature のトークンで確認する。トークンの形式・有効期限の詳細と、伝送の保護は 003・004 と plan で定める。
- ランナーの作成の流れ(登録コードの発行者と有効期限など、11-clarify の環境構築の項)は、本 spec では「権限を持つ利用者が作成し、トークンを受け取って PC に設定する」最小の形とする。
- 判定(FR-008)が状態を含まないのは、001 FR-002 の「ランナーが空いているかどうかは判定に含めない」にあわせたため。maintenance・機材の異常・offline のランナーしか要件を満たさないジョブも受け付けられ、待機列で待つ。
- ランナーがジョブを求めたこと(割り当ての要求)も、生存の証拠として最終応答時刻を更新する。FR-010 の「最後の登録・生存通知」には、割り当ての要求と機材の異常・回復の申告を含める(ランナーからの有効なトークンでの接続はすべて生存の証拠とする)。リースの延長は、生存通知だけが行う。
- 割り当ては、ランナーがジョブを求めたとき(ランナーからの接続)に行う。コアからランナーへは接続しない(憲章 原則 8)。
- 既定値(生存通知の間隔 30 秒、offline と判定する時間 90 秒、リースの長さ 3 分)は、一時的な通信の途絶(生存通知の 2〜3 回の欠落)で誤って offline・リース切れにしない長さとして選んだ。clarify で見直してよい。
- リース切れのジョブの扱い、ジョブの状態遷移の細則、強制中断の停止の手順、機材の異常の申告中に実行中だったジョブの結果は、004 と別途定める。本 spec は「リース切れを記録し、延長を受け付けない」「異常の申告でシステムからジョブを止めない」までとする。
- maintenance にしたときの実行中のジョブの扱いは、最小限として「止めない」とした。詳細な運用(完了を待つ、強制中断と組み合わせる等)はスコープ外とする。
- 規模の目安は 001 と同じ(ランナー数十台、待機中のジョブ数百件)。
- 次はスコープ外とする: ランナーの自動検出、能力の自動取得、メンテナンス運用の詳細、ジョブの状態遷移の細則とリース切れの扱い(004)、機材の故障の自動検知、ランナー PC のセットアップの自動化(憲章 原則 4)、ランナー PC と評価機材の冗長化(008)。
