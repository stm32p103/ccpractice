# Research: ランナーエージェント — 外部ツールの実行

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-11-22

spec の `[NEEDS CLARIFICATION]` は 0 件(Q1〜Q3 は回答済み)。本書は、plan の技術上の未確定事項を決める。
各項目を **Decision / Rationale / Alternatives considered** で記す。

## R1. パッケージ構成と依存の向き

- **Decision**: 次の 4 パッケージ(+ testing の拡張)を、既存の uv ワークスペースに加える。
  - `runner-protocol/`(`job_runner_protocol`): ランナープロトコルの共有スキーマと、依存のない値の型。標準ライブラリのみ。
  - `runner-agent/`(`job_runner_agent`): エージェント本体(取得・実行の管理・報告・機密保護)と、ポート(`Executor`、`SourceFetcher`、`ArtifactStore`、`ProcessLauncher`、`SecretSource`、`CoreClient`)。依存は `job_runner_protocol` と httpx だけ。**`job_core*` を import しない**。
  - `profile-equipment-check/`(`job_profile_equipment_check`): 最初の用途のエグゼキュータ。`job_runner_agent` のポートだけを import する。
  - `runner-service/`(`job_runner_service`): 組み立てと起動の入口(Windows サービスから起動される)。設定を読み、**コード内の対応表**(エグゼキュータの名前 → 実装)から実装を選んで組み立てる。
- **Rationale**: 憲章 原則 1(用途固有の部品はプロファイルとして外に置く。拡張点は「ポート + 起動時の設定による実装の差し替え」だけ。動的なプラグイン読み込みを作らない)。`core-server` と同じ構造にし、エージェント本体を用途固有の語から守る(FR-011、FR-022)。依存の向きは import-linter で検査する(plan の「依存規則」)。
- **Alternatives considered**: (a) 設定の文字列から `importlib` で実装を読み込む — 動的なプラグイン読み込みになるため憲章に反する。(b) プロファイルをエージェント本体と同じパッケージに置く — 用途固有の語・import が本体に入る(FR-022 違反)。

## R2. 言語・並行モデル・主な依存

- **Decision**: Python 3.12 以上、`asyncio`。コアとの通信は `httpx.AsyncClient`。TOML は標準ライブラリ(`tomllib`)。Windows の API(Job Object、ログオン付きのプロセス生成、資格情報の読み取り、リパースポイントの判定、ACL)は、`ctypes` で直接呼び、`pywin32` などの追加の依存を加えない。1 台のランナーが同時に実行するジョブは 1 件(002 の `runner_busy`)。
- **Rationale**: 001〜003 と同じ言語・開発の道具を使える(原則 7)。待ち受け・生存通知・ログ送信・プロセスの監視が並行して動く必要があり、`asyncio` が最も単純。依存を減らすことは、台帳 E15(取得物の検証)の対象を減らす。
- **Alternatives considered**: スレッド — 共有状態の競合が増える。`pywin32` — 大きな依存で、必要な呼び出しは数十個に収まる。

## R3. ランナープロトコルの拡張(003 §2.6 を拡張)

- **Decision**: 003 のエンドポイントを変えず、次を**加える**。詳細は [contracts/runner-protocol.md](contracts/runner-protocol.md)。
  1. `POST /v1/runner/jobs/{job_id}/logs`: ログのチャンクの送信(`seq` で冪等)。
  2. `POST /v1/runner/jobs/{job_id}/source-credential`: ジョブのソースの取得資格(短命・読み取り専用)の取得。
  3. `POST /v1/runner/jobs/{job_id}/result` の本文を拡張: `exit_code`、`failure_reason`(固定の語彙)、`artifacts`(参照のみ)、`counters`(件数だけ)。既存の `outcome`、`result_summary` は互換。
  4. 利用者向け: `GET /v1/jobs/{job_id}/logs`(範囲の取得)、`GET /v1/jobs/{job_id}/artifacts`(参照の一覧)。権限 `job.read_output` を新設する。
  5. `HeartbeatResult`(登録・生存通知・異常の申告・回復の応答)に `abort_requested: bool` を加える(中断の指示。R6)。
- **待ち受け**: long polling は**採用しない**。固定の間隔(既定 5 秒。±20% のゆらぎ)で `job-requests` を問い合わせる。003 が 004 に残した「長時間の待ち受け」は、この決定で閉じる。
- **Rationale**: 003 の最小版との後方互換を保ち、スキーマを `runner-protocol/` に切り出して、エージェントとコア API が同じ契約テストを通す(憲章 原則 1)。短い間隔の問い合わせは、サーバーが接続を保持しないため単純で、ランナー数十台の規模(001 の想定)では負荷が小さい(1 台あたり 0.2 件/秒)。
- **Alternatives considered**: long polling — サーバーの接続の保持・タイムアウトの設計が増え、API のプロセスが 1 つ(003 R9)のため資源の枯渇の対象が増える。待機中の遅れ(最大 5 秒)は運用上問題にならない。WebSocket/SSE のランナー向け — 着信接続に近い構成で、憲章 原則 8 の「ランナーからサーバーへの接続のみ」の趣旨に合わない。

## R4. 実行アカウント(FR-010)と、機密の分離

- **Decision**: **2 つのローカルアカウント**で動かす。
  - **エージェントのアカウント**(例: `svc-runner-agent`): Windows サービスの実行アカウント。ランナーのトークン、ツール用アカウントの資格、状態フォルダ(ジャーナル、監査、ログの待避)、成果物の保存先への書き込みを持つ。作業フォルダの親を所有する。
  - **ツールのアカウント**(例: `svc-runner-tool`): 外部ツールを実行する、専用の低権限アカウント。**ジョブの作業フォルダだけ**に変更の権限を持ち、他のフォルダ(エージェントの状態フォルダ・設定・資格情報・成果物の保存先を含む)への読み取りを ACL で与えない。
  - エージェントは、`CreateProcessWithLogonW` で、ツールのアカウントとして外部ツールを**一時停止の状態で**起動し、環境ブロックを自分で組み立てて渡し(R5)、Job Object(R8)に割り当ててから再開する。ツールのアカウントの資格は、Windows の資格情報の保管機能(エージェントのアカウントだけが読める)に置く(憲章 原則 14)。
  - 開発・試験用に、同じアカウントで直接起動する `DirectLauncher` を用意するが、**`profile = "dev"` のときだけ**選べる(起動時の検査。003 T-A9 と同じ方式)。
- **Rationale**: 1 つのアカウントで動かすと、外部ツールが、エージェントのトークン・設定・状態を、同じアカウントの権限で読める(S1 の「他のサービスの情報」に当たる)。アカウントを分ければ、ACL で「作業フォルダ以外への読み取りを与えない」(憲章 S4)が OS の権限として成立する。仮想化が使えないため(S5)、これが最も強い OS の境界である。
- **Alternatives considered**: (a) 1 アカウント + ファイルの ACL だけ — 同じ主体からの読み取りを ACL では防げない。(b) アクセストークンの制限(制限付きトークン、AppContainer)— 既存のツール(機材の SDK など)との互換性が不明で、設定が難しい。将来の強化として脅威モデルに記す。(c) 仮想化・コンテナ — 憲章 原則 7 で使えない。
- **リスクと検証(スパイク)**: ログオン付きの生成が、サービスの文脈(非対話・セッション 0)で、対象のツールを起動できるかは、ツールの種類による。実装の最初に、偽のツールで検証するスパイクを置く(tasks の先頭)。成立しない場合は、plan を改定して再度の確認を行う(アカウント 1 つへの縮退はしない)。
- **残るリスク**: 外部ツールが、ツールのアカウントの権限の範囲で、OS の既定で全員に読み取りを許す場所(例: `C:\Windows`、`Program Files`)を読むこと。これらは機密でない前提とし、ランナー PC のセットアップ(009)で、機密のフォルダに、ツールのアカウントへの拒否を設定する。
- **スパイクの結果(T001、2026-11-24、対話セッション・別のローカルアカウント `svc-spike-tool`)**: `runner-agent/spikes/logon_spike.py` で、次を確認した。
  - 項目 1(一時停止で生成 → Job Object へ割り当て → 再開): OK。
  - 項目 2(環境ブロックを空から渡せる): OK。
  - 項目 3(作業フォルダ外のファイルが読めない): OK。ただし、**ドライブのルートの既定の ACL(Authenticated Users の読み取り)を継承する場所では、読めてしまう**。継承を切って明示的に許可した主体だけにした場合に成立した。ランナー PC の構築(009)では、機密のフォルダの継承を切ることを、項目に含める。
  - 項目 4(`TerminateJobObject` で孫まで停止): OK。
  - 項目 5(エージェントの強制終了で子・孫が終了): OK(`--crash` の後、ツールのアカウントの `python.exe` が 0 件)。
  - **未確認**: サービスの文脈(非対話・セッション 0。WinSW のサービスとして、エージェントのアカウントで実行)での同じ検査。T001 は、これが済むまで完了にしない。
  - 既知の限界: スパイクの子は環境が空のため、ツールのアカウント名を出力できない(`tool_account` が null)。別アカウントでの実行の確認は、項目 3 の成立で代える。

## R5. 環境変数の構築(FR-015)と作業フォルダ

- **Decision**:
  - 環境ブロックは**空**から組み立てる。入れるのは、(1) 設定の `env_allow`(名前 → **固定の値**。親の環境の値は読まない)、(2) エージェントが定める変数: `TEMP`、`TMP`(作業フォルダ内の `tmp\`)、`JOB_WORK_DIR`、`JOB_SIGNAL_DIR`(R9)、(3) エグゼキュータが要求し、**設定でそのエグゼキュータに許可された名前**だけ(値はジョブの入力から取れない)。`ComSpec`、`PATH` は、`env_allow` に載せたときだけ与える。
  - 作業フォルダは、`<work_root>\<job_id>-<乱数>` を**新規に作成**する(既存なら失敗)。ACL は、ツールのアカウントとエージェントのアカウントだけ。外部ツールの作業ディレクトリは、この直下の `work\`。ソースは `src\`、ツールの一時ファイルは `tmp\`、エージェントとの信号は `signal\`。
  - 終了後(成功・失敗・中断・タイムアウト)に削除する。削除に失敗したら、再試行し、残った場合は監査に記録して、次の起動時と一定時間ごとに掃除する。
- **Rationale**: 憲章 S4。「許可リストの値を設定で固定」することで、エージェント自身の環境(トークンの入った変数など)が、設定の誤りでも入らない。
- **Alternatives considered**: 名前の許可リストで親の環境から値を引き継ぐ — エージェントの環境に秘密が入った場合に漏れる。値を設定に固定する方が単純で、監査しやすい。

## R6. 中断・タイムアウト・生存通知(FR-002、FR-006、FR-007)

- **Decision**:
  - 生存通知は、**割り当てを受けた直後**から、ジョブの終了(報告の完了)まで、コアの応答で指示された間隔(既定 30 秒)で送る。準備(ソースの取得、成果物の保存)の間も送る。
  - 中断の指示は、生存通知の応答の `abort_requested = true` で受ける(着信接続なし)。受けたら、プロセスツリーを Job Object ごと終了させ、`POST /v1/runner/jobs/{job_id}/stopped` を送る。生存通知の間隔の分(最大 30 秒)の遅れが生じるため、中断の応答の間隔は、中断を要求された後の最初の通知で確認できるよう、**中断の確認の目安を「通知の間隔 + 10 秒以内」**とする(SC-005 の「10 秒以内」は、指示の受信から停止までの時間)。
  - タイムアウトは、ジョブ定義の `timeout`(ジョブの開始 = 割り当てから)を、**ツールの起動の時点から**数える(準備の時間を含めない。準備の上限は別に設ける: 設定 `prepare_timeout_seconds`、既定 600)。超えたら、Job Object を終了し、`failure_reason = "timeout"` の失敗を報告する。
  - プロセスの停止は、**即時の強制終了**(`TerminateJobObject`)とする。終了を待ち(最大 5 秒)、残ったら失敗として記録する。
- **Rationale**: 003 は `HeartbeatResult` に中断の情報を持たない。ランナーは着信を受けないため(原則 8)、既存の通知の応答に載せるのが最小の変更である。ツールの種類を知らないため、通知を送って終了を待つ方式は、ツールごとの対応が要り、確実に止まる保証もない。
- **Alternatives considered**: 中断専用の問い合わせ — 生存通知と二重になる。正常終了の要求(Ctrl+Break)を先に送る — ツールが応答しないと待つ時間が延びる。必要になれば、エグゼキュータの設定で追加できる(将来)。

## R7. プロセスの起動(FR-003、FR-016)

- **Decision**: エグゼキュータは、ジョブの payload から**実行計画(`ExecutionPlan`)**を作る。計画は次のとおりで、エージェントが検証してから起動する。
  - `tool_id`: **設定の登録簿**(`tools.<id> = 実行ファイルの絶対パス)にある識別子だけ。payload からパスを指定できない。
  - `args`: 引数の列。各要素は `Literal(str)`(そのまま渡す)か `WorkPath(相対パス)`(作業フォルダ内に解決して渡す)。シェルを介さず、引数配列で起動する(`.bat`・`.cmd`・シェルの組み込みコマンドは `tool_id` に登録できない)。
  - `cwd`: 作業フォルダ内の相対パス(既定は `work\`)。
  - `artifact_patterns`: 成果物の出力パターン(作業フォルダ内の相対のパターン)。
  - `extra_env`: 追加の環境変数の名前と値。名前が、そのエグゼキュータの許可リスト(設定)にあるものだけ。
  - すべての `WorkPath`・`cwd`・パターンは、同じ**パスの検査**(下)を通す。違反は、ツールを起動せず、`failure_reason = "input_rejected"` で報告し、監査に記録する。
- **パスの検査**: 次を、**文字列の検査と実ファイルの検査の両方**で拒否する: 絶対パス(ドライブ・UNC・`\\?\`・デバイス名)、`..` の要素、代替データストリーム(`:`)、予約名(`CON` など)、末尾の空白・ドット。正規化した結果が作業フォルダの配下であること。既存の要素は、**シンボリックリンク・ジャンクション(リパースポイント)でないこと**を、要素ごとに `FILE_ATTRIBUTE_REPARSE_POINT` で確認する。
- **Rationale**: 憲章 S4。「payload を解釈できるのはエグゼキュータだけ」(用語)を保ちつつ、**何を起動できるか**をエージェントの設定(許可リスト)で縛る。payload の悪意のある値が、起動するプログラムや作業フォルダ外のパスに到達しない。
- **Alternatives considered**: エグゼキュータが `subprocess` を自分で呼ぶ — 環境変数・シェル・パスの検査を、用途ごとに実装することになり、S4 を保証できない。**エグゼキュータは、プロセスを起動しない**(計画を返すだけ)ことを、アーキテクチャテストで検査する(`subprocess`、`os.system`、`ctypes` の import の禁止)。

## R8. プロセスツリーの停止(FR-006、FR-007)

- **Decision**: 起動したプロセスを、**Job Object**(`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を設定)に割り当てる(一時停止で生成 → 割り当て → 再開)。停止は `TerminateJobObject`。子・孫のプロセスは、Job Object の中に生成されるため、プロセスツリーから離脱しても停止できる。エージェントが異常終了しても、ハンドルが閉じられて、ツールが終了する。メモリの上限(ジョブごと)も、設定で与えられる。
- **Rationale**: Windows でプロセスツリーを確実に止める標準の手段。憲章 S5 が挙げる「必要なら Job Object などの制限」に合う。
- **Alternatives considered**: `taskkill /T` — 親が先に終了した孫は止まらない。

## R9. ツールからエージェントへの機材の異常の伝え方(FR-023)

- **Decision**: ツールは、作業フォルダ内の `signal\` に、**決まった名前のファイル**を書いて伝える。`fault.txt`(異常。UTF-8、1〜200 文字、改行・制御文字なし)、`recovered`(回復。空でよい)。場所は、環境変数 `JOB_SIGNAL_DIR` で知らせる。エージェントは、実行中に定期的(1 秒)に確認し、新規・更新があれば、002 の規則(長さ・文字種の検査)を通して `POST /v1/runner/fault`・`DELETE /v1/runner/fault` へ送る。検査に違反する内容は、送らず、監査に記録する(内容は記録しない)。
- **Rationale**: 着信を受けず(原則 8)、ツールから PC の外へ送らない(台帳 E4・E8)。ファイルは、どの言語のツールでも書けて、作業フォルダ内で完結する。エージェントだけがコア API へ送る。
- **Alternatives considered**: ローカルの HTTP/名前付きパイプ — 待ち受けのポート・ACL の設計が増える。標準出力の特定の行 — ログと混ざり、マスクや切り詰めの影響を受ける。
- **注**: spec の Assumptions にある既定(申告ファイル)と一致する。

## R10. ログの送信とマスク(FR-004、FR-017)

- **Decision**:
  - 外部ツールの標準出力・標準エラーを、**別々のパイプ**で読み、行ごと(UTF-8。デコードできないバイトは置換)に分けて、マスクを通してから、チャンク(最大 64 KiB、または 1 秒ごと)にまとめて、`logs` へ送る。各チャンクに、ジョブの中での通し番号 `seq` を付け、コアは同じ `seq` を冪等に受理する(再送で重複しない)。
  - **マスク**: (1) **完全一致**: エージェントが保持する秘密の値(ランナーのトークン、ジョブの取得資格、ツールのアカウントの資格)を、値そのものと、その一般的な符号化(Base64、URL 符号化)で置換する。(2) **パターン**: 設定の正規表現の一覧(既定: `ss_`・`st_`・`rt_` の接頭辞のトークン、`Bearer` の値、`gh[pousr]_`、`AKIA…`、PEM の秘密鍵のブロック、JWT、`password=`・`secret=`・`token=` の値)。置換は固定の `***`。複数行(PEM)は、開始の行から終了の行までを保持して置換する。1 行が 8 KiB を超えるときは、重なりを持たせて分割し、境界をまたぐ一致も検査する。
  - **量の制限**: ジョブごとの総量(既定 10 MiB)、1 秒あたりの量(既定 1 MiB/秒)。超えた分は破棄し、`[出力を切り詰めました]` の 1 行を 1 回だけ加え、`counters.log_truncated = true` を報告する。パイプは読み続け、ツールをブロックさせない。
  - **到達しない間**: マスク後のチャンクを、状態フォルダに、容量を限って待避する(既定 64 MiB。ACL はエージェントのアカウントだけ)。復旧後に `seq` の順に送る。上限を超えたら、古い方ではなく**新しい方**を切り詰める(順序を保つ)。
  - マスクの発動は、件数(`counters.masked_lines`)と監査に記録する。**一致した内容は記録しない**。
- **Rationale**: 憲章 S4(マスクは補助的な対策であり、主たる防御ではない)。主たる防御は、アカウントの分離・環境変数・作業フォルダ(R4、R5)。完全一致は、エージェントが渡した秘密が、ツールの出力に現れても止められる。
- **Alternatives considered**: ログを成果物として保存先に置く — 端末の WebUI で逐次参照する要件(FR-004)に合わない。

## R11. 成果物と保存先(FR-005、FR-018、FR-025。Q2 の回答)

- **Decision**:
  - 成果物は、ツールの終了後、`artifact_patterns` に一致する**作業フォルダ内の通常のファイル**だけを対象にする(リパースポイントは辿らない。ハードリンクは 1 つ目の名前だけ、通常ファイルとして扱う)。件数(既定 100)・1 ファイルの大きさ(既定 2 GiB)・合計(既定 4 GiB)の上限を、設定で与える。超過は、収集せずに失敗(`artifact_limit_exceeded`)として報告する。
  - 保存は `ArtifactStore` ポートで行う。実装は 2 つ。
    1. `SharedFolderArtifactStore`(最初に作る): **ランナー自身の PC の共有フォルダ**(エージェントのアカウントが書き込める)へ、`<job_id>\<名前>` として書き、参照として **UNC パス**(`\\<ホスト>\<共有名>\<job_id>\<名前>`)を返す。ホスト名・共有名は設定で与える。**「実行結果」フォルダはランナーごとの設定(`artifact_store.shared_folder.local_path`)で指定する**。**共有フォルダのアクセス権の設定は本システムの範囲外**とし(ジョブの依頼者のチーム全体で参照するため、運用で行う)、エージェントは、アクセス権を作成・変更しない。エージェントのアカウントに書き込みの権限が必要なことだけを、起動時の自己検査(テストファイルの書き込みと削除)で確認する。
    2. `HttpsStorageArtifactStore`(保存先の製品が決まってから。tasks の後半。台帳のレビューを要する): **大容量ストレージ**へ HTTPS(PUT)でアップロードし、参照として **URL** を返す。資格は、Windows の資格情報の保管機能に置く。
  - コア API へ報告するのは、`ArtifactReference`(`name`、`kind`(`unc`|`url`)、`reference`、`size_bytes`、`sha256`)だけ。成果物の中身はコアを通らない(台帳 E6 の改定のとおり)。保存先は、ジョブの識別子の下に置き、**保持期間(既定 30 日)を過ぎたものを、エージェントが起動時と 1 日ごとに削除する**。保存先の総容量の上限(既定 200 GiB)に達したら、新しい書き込みを拒否する(`artifact_store_failed`)。
  - 保存先の選択は設定 `artifact_store.kind`(`shared_folder`|`https_storage`|`disabled`)。**既定は `disabled`**(成果物の収集をしない)。有効化には、台帳 E6 のレビュー済みの宛先の設定を要する(spec Assumptions)。
- **Rationale**: 大容量のファイルでコア(サーバー)の容量・帯域を使わない(ユーザーの回答)。コアには参照だけを送るため、成果物の中身が通知・WebUI・監査に混ざらない(憲章 S4)。
- **Alternatives considered**: サーバー側に保存 — 大容量でサーバーの負荷が大きい(Q2 の B を選択)。参照に、ホストの IP やローカルパスを使う — 利用者が開けない。ローカルパスは参照に含めない(作業フォルダ外のパスを含めない)。
- **注**: UNC のホスト名は、ランナーの PC 情報であり、E4 の「PC 情報は許可リストに載せない限り送らない」の対象に近い。台帳の E6 の改定(利用者の承認済み)で、参照としての送信を許可したものとして扱い、許可する項目を `artifact_store.unc_host`・`share_name` の設定値に限る。

## R12. ソースの取得(FR-026。Q3 の回答)

- **Decision**:
  - 取得は**エージェント**が行う。手順: (1) ジョブ定義の `source`(リポジトリ)が、設定の許可リストにあることを確認(なければ作業フォルダを作らず、`repository_not_allowed` で報告し、監査に記録)。(2) `POST /v1/runner/jobs/{job_id}/source-credential` で、短命の取得資格を得る。(3) `SourceFetcher` ポートで、`revision`(コミット識別子。憲章 原則 10)を `src\` へ取得する。(4) 資格を、取得の直後に破棄する(メモリから消去。ジョブの終了を待たない)。エグゼキュータ・外部ツールには、資格を渡さず、`src\` の読み取り専用の内容だけを渡す。取得した内容の `.git` は残さない(取得の方式が履歴を持つ場合は、削除する)。
  - 004 では、ポートと、`LocalDirectorySourceFetcher`(試験・開発用。許可した親フォルダの下のディレクトリをコピー。**`profile = "dev"` のときだけ**)を作る。GitHub の実アダプタは **005 が実装する**(憲章 原則 3。GitHub の語はエージェントに入れない)。
  - コア API 側の `source-credential` は、`SourceCredentialIssuer` ポート(core-api。実アダプタは 005、Fake は testing)を呼ぶ。資格は、コアが**保存せず**、ログ・監査・エラーに含めない。応答は、そのランナーに割り当て中のジョブだけに限る。
- **Rationale**: 取得の許可リストと資格の扱いを、エージェントに集約でき(憲章 S3)、エグゼキュータに資格が渡らない(用途ごとの実装に、資格の扱いを任せない)。用途固有の語を入れない(原則 1)。
- **Alternatives considered**: エグゼキュータが取得 — 資格が用途ごとの実装に渡る(Q3 の B を選択しない)。長期の資格をランナーに置く — 漏れた場合の影響が大きい。
- **台帳**: E7 の「短命の取得資格」を、コア API からエージェントへ返す経路が必要(E16 の応答の内容に加える)。**台帳の E16(と E7)の改定案を、実装の着手前にレビューへ出す**(plan の Constitution Check)。

## R13. サーバーへの到達の途絶と報告の確実性(FR-009)

- **Decision**:
  - コアへの要求は、失敗(接続・タイムアウト・`5xx`)したとき、指数のバックオフ(1 秒〜60 秒、±20% のゆらぎ)で再試行する。実行中のジョブは、コアの状態に関係なく継続する。
  - 終了の結果は、報告する前に、**状態フォルダのジャーナル**(1 件 1 ファイル。原子的な書き込み)へ書く。成功の応答(または確定の拒否)を得るまで、再試行する。報告の拒否(`409` の `lease_expired`・`invalid_state_transition`、`403`、`404`)は、**確定**として扱い、記録して破棄する(結果の重複を防ぐ。003 の `FinishResult` を、再送で変えない)。
  - エージェントの起動時に、ジャーナルにある未報告の結果を、先に報告してから、通常の問い合わせを始める。
  - **リースの長さを超える途絶**では、コアがリース切れでジョブを失敗として確定する(R14)。復旧後の報告は拒否される。エージェントは、拒否を記録し、実行中のツールがあれば止め、作業フォルダを削除する。
- **Rationale**: SC-006(結果は 1 回だけ報告され、失われない・重複しない)は、**途絶がリースの長さ(既定 3 分)より短い**ときの約束である(spec のエッジケース)。それより長い途絶は、Q1 の回答(失敗として確定)に従う。
- **Alternatives considered**: 結果の識別子を付けた冪等な再送(コアが同じ結果を再度受け付ける) — 001 の遷移の規則を変える。確定の拒否として扱う方が、コアの変更が少ない。

## R14. リース切れの扱い(FR-024。Q1 の回答)

- **Decision**: コアは、リース切れのジョブを、`SweepRunners` で、待機列へ戻さず**失敗として確定する**(失敗の理由コード `lease_expired`)。自動の再実行・リトライはしない。やり直しは、利用者の再提出(憲章 原則 5)。
  - **コア側の変更**(001・002 への小さな変更): `SweepRunners` が、リース切れのジョブ(実行中)を、`FAILED`(理由 `lease_expired`)に遷移させる。001 の「実行中の状態の詳細は 004 と別途定義」の約束のうち、この 1 規則を、本 feature で確定する。ジョブの状態遷移の細則・リトライは、引き続きスコープ外。
  - エージェント側: 生存通知の応答で、リースの期限が `None`(切れ)になったら、リース切れと判断し、実行中のツールを止め、作業フォルダを削除し、結果は報告しない(確定の拒否)。再登録(エージェントの再起動)でも、有効なリースがあったジョブは、リースが切れるまで、コアの上で実行中のままになる(エージェントの再起動後、ツールは Job Object で終了している)。このため、起動時に、**自分に割り当て中のジョブがあれば、直ちに失敗(`agent_restarted`)を報告**する(`runner_busy` の解消)。
- **Rationale**: ユーザーの回答(Q1: B)。副作用のあるツールの二重実行を防ぐ。エージェントの再起動時に、リース切れを待たずに失敗を報告することで、ランナーの占有を最小にする。
- **Alternatives considered**: 再キュー — 二重実行のおそれ(Q1 の A を選択しない)。

## R15. 認証情報・秘密の保管

- **Decision**: ランナーのトークン(`rt_`)と、ツールのアカウントの資格は、**Windows の資格情報の保管機能**(エージェントのアカウントの領域。DPAPI)に置く。`SecretSource` ポートで読み、設定ファイルには**資格情報の名前だけ**を書く。コア API の URL は、`profile != "dev"` のとき HTTPS だけを許可し、サーバーの証明書の検証を無効にできない(組織の CA は、設定で指定できる)。
- **Rationale**: 憲章 原則 14(秘密情報は Windows の資格情報の保管機能)。003 の `SecretSource` と同じ考え方。コア API が HTTP の場合のトークンの盗聴(T-W12)を避ける。
- **Alternatives considered**: 設定ファイルの平文 — 禁止。環境変数 — サービスの設定・プロセスの環境に残る(dev のみ許可。警告)。
- **注**: コア API を HTTPS で公開する構成は 009 の範囲。dev では HTTP を許可する。

## R16. Windows サービス(FR-008)

- **Decision**: **WinSW**(003 R17 と同じ)でサービス化する。エージェントのアカウントで実行し、開始の種類は自動(遅延)、失敗時は再起動(1 回目 5 秒、2 回目以降 30 秒)。エージェントは、サービスの停止の信号(`CTRL_BREAK`/`CTRL_C`)を受けたら、実行中のジョブの Job Object を終了し、`failure_reason = "agent_shutdown"` の失敗を、**最大 5 秒**だけ報告を試みて、作業フォルダを削除して終了する(報告できなければ、リース切れ(R14)に任せる)。サービスの登録・アカウント・ファイアウォールの設定は、009 のランナー用のスクリプトの項目として引き継ぐ(原則 14。plan の Constitution Check)。
- **Rationale**: PC の再起動後の自動復帰(SC-007)。003 と同じ道具で、取得物の検証対象を増やさない(台帳 E13・E15)。
- **Alternatives considered**: `pywin32` のサービスの枠組み — 追加の依存。`sc.exe create` で Python を直接 — 停止の信号・再起動・ログの扱いを自作することになる。

## R17. 外向きの通信の制限(FR-019、E8)

- **Decision**: (1) エージェントの外向きは、コア API・ソース取得先・成果物の保存先だけ(設定)。(2) **外部ツール(ツールのアカウント)の外向きの通信は、Windows ファイアウォールのユーザー単位の規則で遮断する**(既定拒否。必要な通信は台帳に追加してから許可)。設定は 009 のランナー用のスクリプトで行い、エージェントの起動時に、**規則の存在を確認し(自己検査)、なければ起動を拒否する**(`profile = "dev"` を除く)。(3) エージェントは、テレメトリ・解析・外部の資産を使わない(禁止 API の検査と、送信を記録する偽のサーバーでの検証)。
- **Rationale**: 憲章 S4(ファイアウォールで、外向き通信を許可先に限定する)。自己検査で、構成の抜けを検知する。
- **Alternatives considered**: エージェントがファイアウォール規則を作る — 管理者権限が要り、低権限のエージェントの原則に反する。

## R18. 試験の方針(FR-012。憲章 原則 11)

- **Decision**:
  - **偽のコア(`FakeRunnerCore`)**: ランナープロトコルを話す、メモリ上の ASGI アプリ(`testing/.../runner_fakes/`)。ジョブの割り当て、リース、中断の指示、ログ・結果・成果物の参照の受信、送信の記録、途絶・遅延・拒否の注入を持つ。
  - **偽のエグゼキュータ**: スリープする、子プロセスを起動する、出力する、ダミーの秘密を読もうとする、パスの逸脱を要求する、など。**偽のツール**は、試験用の小さな実行ファイル(Python のスクリプトを、`tool_id` に登録した `python.exe` 経由で起動)。
  - **契約テスト**: `Executor`、`SourceFetcher`、`ArtifactStore`、`ProcessLauncher`、`CoreClient`、`SecretSource` に用意し、実アダプタと Fake の両方で通す。ランナープロトコルは、スキーマ(JSON Schema)と、コア API の OpenAPI の整合を検査する(003 の生成物と比べる)。
  - **機密の検査**: ダミーの秘密(作業フォルダ外のファイル、環境変数、エージェントのトークン)を読んで出力・成果物に書こうとするツールで、ログ・成果物・コアへの全通信に現れないこと(SC-002)。送信を記録する偽のサーバーで、台帳にない宛先・内容が 0 件(SC-003)。パスの逸脱の網羅(`..`、絶対、ドライブ、UNC、デバイス、代替ストリーム、シンボリックリンク、ジャンクション)(SC-004)。
  - **OS の機能の試験**(Job Object、ログオン付きの生成、ACL、リパースポイント)は、Windows 上の `pytest -m windows` で実行する(既定では実行しない)。2 アカウントの検証は、`-m twoaccount`(ランナー用の構築スクリプトで作ったアカウントがある環境)。
  - **アーキテクチャテスト**: 依存規則、用途固有の語・GitHub の語の不在(SC-008)、エグゼキュータがプロセス起動・ネットワーク・`ctypes` を import しないこと、エージェントが `subprocess` を使う場所が `launcher` だけであること。
  - **エンドツーエンド**: コアの実装(`job_testing` の `build_api()`)と、エージェントを、同じプロセスの中で接続する結合試験(GitHub・WebUI なし)。
- **Rationale**: 憲章 原則 11(GitHub 連携なしでも、コア・コア API・ランナーエージェントの結合試験が動く)。

## R20. 環境構築の支援(憲章 原則 14)

- **Decision**: 本 feature の完了の定義(試行に必要な構築を、スクリプトで再現できること)のため、次を行う。
  - **開発環境(`ops/dev`)**: ワークスペースに 4 パッケージを加えた `uv sync`、`-VerifyOnly` に 004 の検証(偽のコアでの一巡、パスの検査、秘密の検査、サービスなしの起動)を追加。
  - **ランナー PC(009 の `setup-runner.ps1` の項目として引き継ぐ。本 feature は、項目と検査の仕様を定める)**: 2 つのローカルアカウントの作成、作業フォルダ・状態フォルダ・共有フォルダの作成と ACL、ツールのアカウントへの外向きの遮断の規則、資格情報の保管、WinSW の登録、設定ファイルの雛形、設定の検証(ドライラン)、撤去。
  - 009 の基盤が未了のあいだは、完了の定義(ランナー PC での再現)を満たせない(⚠️。003 と同じ条件を持ち越す)。
- **Rationale**: 憲章 原則 14。サーバー側(003)と同じ運び方にする。
