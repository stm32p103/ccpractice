# Quickstart: ランナーエージェントの検証

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Contracts**: [contracts/](contracts/)

実装後に、004 が動くことを確かめる手順。コマンドは、リポジトリのルートから実行する。
実行環境は Windows。用途固有のツールは使わず、偽のツール(試験用の小さなスクリプト)で確認する。

## 前提

- 開発環境の構築: `ops/dev/setup-dev.ps1`(004 の追加分を含む。冪等。`-WhatIf` でドライラン)。4 パッケージ(`runner-protocol`、`runner-agent`、`profile-equipment-check`、`runner-service`)を `uv sync` する。
- 2 アカウントの検証(V38)は、ランナー用の構築スクリプト(009 の `setup-runner.ps1` の項目)でアカウントと ACL を作った PC だけで行う。それ以外の PC では、V1〜V37 を行う。

## 1. 自動の試験

```powershell
uv run pytest runner-protocol runner-agent profile-equipment-check runner-service testing core core-api -q   # 既定(各パッケージを個別に実行する。ルートからの一括実行は、001〜003 から既存の conftest の名前の衝突がある)
uv run pytest runner-agent -m windows -q                          # Job Object・リパースポイント・資格情報(Windows 上)
uv run pytest runner-agent -m twoaccount -q                       # 2 アカウント(構築済みの PC のみ。環境変数 JOB_TEST_TOOL_ACCOUNT ほか。handoff-009.md)
uv run lint-imports                                               # 依存規則
uv run ruff check . ; uv run mypy
```

## 2. 検証の項目(spec の受け入れ基準との対応)

偽のコア(`FakeRunnerCore`)、偽のエグゼキュータ、偽のツール、送信を記録する偽のサーバーを使う(`testing/src/job_testing/runner_fakes/`)。

| # | 検証 | 手順(概要) | 期待 | spec |
|---|---|---|---|---|
| V1 | 取得 → 実行 → 報告 | 偽のコアにジョブを 1 件置く。スリープするだけのエグゼキュータで実行 | 1 件だけ取得され、成功が報告される。作業フォルダが残らない | US1-1、SC-001 |
| V2 | 条件に合うジョブがない | 偽のコアに合わないジョブだけを置く | 取得されず、5 秒ごと(±20%)に問い合わせる。着信を受けない | US1-2 |
| V3 | 生存通知 | 実行を 2 分以上続ける | 通知の間隔ごとにリースが延長される。準備中も通知される | US1-3、FR-002 |
| V4 | ログの逐次送信 | 1 行ずつ出力するツール | 1〜2 秒以内にコアに届く。`seq` が連続し、再送しても重複しない | US1-4、FR-004 |
| V5 | 対応のないジョブ種別 | 設定にない `job_type` | 起動せず `unsupported_job_type` で失敗が報告される | US1-5 |
| V6 | ダミーの秘密 | 作業フォルダ外のファイル・環境変数(ダミー)、エージェントのトークンを読んで出力・成果物に書くツール | ログ・成果物・コアへの全通信にダミーの値が 0 件 | US2-1、SC-002 |
| V7 | 環境変数 | 親の環境にダミーの変数を置き、環境を出力するツール | `env_allow` + エージェントの定める変数だけ。ダミーが見えない | US2-2、FR-015 |
| V8 | パスの逸脱 | `..`、絶対、ドライブ、UNC、デバイス名、代替ストリーム、シンボリックリンク、ジャンクションを含む入力 | すべて `input_rejected`。ツールは起動されない。監査に残り、`counters.path_rejections` が増える | US2-3、SC-004 |
| V9 | 台帳にない送信 | 一巡(取得・実行・ログ・結果・成果物)を、送信を記録する偽のサーバーの下で行う | E4〜E7(と保存先)以外の宛先・内容への通信が 0 件 | US2-4、SC-003 |
| V10 | ログのマスク | トークンの形・PEM・エージェントの秘密の値を出力するツール | `***` に置換。`counters.masked_lines` が増える。一致した内容が監査にない | US2-5 |
| V11 | 成果物のパターン | パターンに一致するファイルと、しないファイル、リンクを作るツール | 一致する通常のファイルだけが保存先へ。参照(UNC)だけがコアへ。上限超過は `artifact_limit_exceeded` | US2-6、FR-018、FR-025 |
| V12 | 中断 | 子・孫プロセスを起動するツールを実行し、コアで強制中断 | 通知の応答で停止し、プロセスが 0 件。`stopped` が報告される(指示の受信から 10 秒以内) | US3-1、SC-005 |
| V13 | タイムアウト | `timeout` を短くしたジョブ | プロセスが 0 件。`failed`(`timeout`)が報告される | US3-2 |
| V14 | 後始末 | V12・V13 の後 | 作業フォルダが削除され、取得資格が破棄されている | US3-3、SC-009 |
| V15 | サーバーの途絶 | 実行中に偽のコアを(リースより短く)停止 → 復旧 | ジョブは継続し、復旧後に結果が 1 回だけ報告される。ログが欠けない | US4-1・3、SC-006 |
| V16 | リースを超える途絶 | 偽のコアを、リースの長さより長く停止 → 復旧 | コアは `lease_expired` で失敗を確定済み。エージェントは、報告の拒否を記録し、ツールを止めて削除する | FR-024、Q1 |
| V17 | エージェントの再起動 | 実行中にエージェントを終了 → 起動 | ツールが残らない。起動時に `agent_restarted` の失敗が報告され、ランナーが空く | R14 |
| V18 | 再起動後の復帰 | サービスとして登録した PC を再起動 | 自動で起動し、能力を再登録して問い合わせを再開する | US4-2、SC-007 |
| V19 | 追加の容易さ | 偽のエグゼキュータを、設定の対応表に加える(コードの変更はエグゼキュータの追加だけ) | エージェントの中核を変えずに実行できる | US5-1、SC-008 |
| V20 | 語彙の検査 | `runner-agent`・`runner-protocol` を検査 | 用途固有の語・GitHub の語・`job_core*` の import が 0 件 | US5-2、SC-008 |
| V21 | 単体の試験 | コアなしで、equipment-check のエグゼキュータを試験 | 引数・作業ディレクトリの組み立てと結果の解釈が検証できる | US5-3 |
| V22 | 許可リスト外のリポジトリ | 許可リストにない `source` のジョブ | 作業フォルダを作らず `repository_not_allowed`。監査に残る | US6-1 |
| V23 | 取得資格 | 取得の前後で、資格の値を探す | ログ・状態フォルダ・監査・環境・エグゼキュータの入力に値がない | R12 |
| V24 | 異常の申告 | ツールが `signal\fault.txt` を書く(正しい内容 / 201 文字 / 制御文字) | 正しいものだけコアへ。違反は送らず、監査に型だけ記録 | FR-023 |
| V25 | 結果のジャーナル | 報告の直前にエージェントを強制終了 | 起動時に未報告の結果が先に報告される(または確定の拒否で破棄) | R13 |
| V26 | 既定は拒否 | 許可リストが空の設定で起動 | どのジョブも実行されない。`artifact_store = disabled` では、収集されない | S3 |

## 3. 手動の一巡(開発環境)

1. `uv run python -m job_core_server --config core-server/config/server.dev.toml`(003)でコア API を起動する。
2. `runner-service/config/agent.dev.toml`(`profile = "dev"`、`DirectLauncher`、`LocalDirectorySourceFetcher`、偽のツールの登録)で、`uv run python -m job_runner_service --config <path>` を起動する。
3. API で、ジョブを提出し(003 の手順)、ログ(`GET /v1/jobs/{id}/logs`)と結果を確認する。
4. 強制中断・タイムアウト・ネットワークの途絶(API の停止)を、V12・V13・V15 の手順で試す。
