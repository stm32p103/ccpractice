# Feature Specification: コア — ジョブの受付・キュー管理

**Feature Branch**: `job_service`(spec ディレクトリ: `specs/001-core-job-queue`)

**Created**: 2026-11-20

**Status**: Draft

**Input**: User description: inputs/03-specify-001-core-job-queue.md「機能: コア — ジョブの受付・キュー管理」(背景と目的、ユビキタス言語、ユーザーシナリオ 1〜8、FR-1〜FR-15、受け入れ基準、スコープ外、未確定事項)。2026-11-20 の見直しで、優先度と割り込みの概念を廃止し、位置を指定したジョブの追加と、スケジュール変更(指定したジョブの前後への移動)に置き換えた。

## 背景と目的

外部ツールを 1 回実行する依頼(ジョブ)を受け付け、順番待ち(待機列)を管理する、再利用可能なコアを作る。
コアは特定の用途・提出元・実行ツールに依存しない。

既存の仕組みには「一度動き出すと順序を入れ替えられず、突発の依頼ややり直しに対応できない」という不満がある。
本 feature は、運用中に位置を指定した追加・スケジュール変更・中断・やり直しをいつでも行えるようにして、この不満を解消する(憲章 原則 5)。

ランナー(実行環境)は利用者の共用である。順番はシステムが優先度で自動に決めるのではなく、
新しいジョブは指定がなければ待機列の最後に並ぶ。順番の調整は利用者同士で相談して決め、スケジュール変更の権限を持つ利用者が、
指定したジョブの前後への追加や移動で、その結果を待機列に反映する。
そのため、待機列は全員から見えるようにする。

最初の用途は、特定の実行環境でしか動かないツールの実行だが、コアはその用途の語彙を持たない(憲章 原則 1、3)。

## Clarifications

### Session 2026-11-20

- Q: 終了したジョブ(状態と結果の要約)と監査ログを、どれくらいの期間残すか? → A: 期間を設定値で変えられるようにし、既定はジョブ 1 年・監査ログ 3 年で自動削除する。
- Q: 他人の待機中のジョブを取り消せるのは誰か? → A: 待機中のジョブの取り消しと、実行中のジョブの強制中断を、それぞれ別の権限(「取り消し」「強制中断」)とする。
- Q: 監査ログを、管理者以外の利用者も見られるようにするか? → A: 各ジョブの操作の経緯(追加・スケジュール変更・中断・やり直し)は全員が見られる。監査ログ全体(権限による拒否を含む)の閲覧は管理の権限とする。
- Q: 他人のジョブのやり直しは、誰が行えるか? → A: ジョブの追加と同等に扱う。ジョブ追加の権限があれば、誰の終了したジョブでもやり直せ、指定しなければ末尾に追加される。スケジュール変更の権限があれば、指定したジョブの前か後に追加できる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ジョブを提出し、並んだ順に実行される (Priority: P1)

提出者は、ジョブ定義(ジョブの種類、ランナー要件、payload、タイムアウト、出所情報)を渡してジョブを提出する。
要件を満たしうるランナーが 1 台も登録されていなければ、提出は理由とともに拒否される。
受け付けられたジョブは、位置の指定がなければ待機列の最後に並び、条件を満たすランナーが空いたときに、待機列の前から順に 1 件ずつ割り当てられる。
提出にはジョブ追加の権限が要る。

**Why this priority**: 受付と並び順どおりの割り当てがなければ、他のすべての操作(スケジュール変更、中断、やり直し)が成り立たない。これ単体で「待機列に並べて順番に実行する」という最小の価値を持つ。

**Independent Test**: 偽のランナー一覧(登録済みのランナーとその能力)を用意し、複数のジョブを提出して、受付/拒否の結果と、ランナーが空くたびに割り当てられるジョブの順序を確認する。

**Acceptance Scenarios**:

1. **Given** 要件を満たしうるランナーが 1 台も登録されていない, **When** 提出者がジョブを提出する, **Then** 提出は拒否され、「要件を満たすランナーがない」ことが分かる理由が返る。ジョブは待機列に入らない。
2. **Given** 要件を満たしうるランナーが登録されている, **When** 提出者がジョブを提出する, **Then** ジョブは受け付けられ、識別子が返り、待機中の状態で待機列の最後に並ぶ。
3. **Given** ジョブ A、B がこの順に提出され待機中, **When** 条件を満たすランナーが空く, **Then** A が先に割り当てられる。
4. **Given** ランナーがジョブを 1 件実行中, **When** そのランナーの条件を満たす別のジョブが待機している, **Then** 実行中のジョブが終わるまで、そのランナーに 2 件目は割り当てられない。
5. **Given** 待機列の先頭のジョブの要件を満たすランナーが空いていない, **When** 別の要件のジョブを満たすランナーが空く, **Then** そのランナーの条件を満たすジョブのうち、待機列で最も前のものが割り当てられる(条件を満たさない前のジョブを理由に、空いたランナーを遊ばせない)。
6. **Given** 出所・リビジョン・ジョブの種類が同じジョブが待機中, **When** 同じ内容のジョブが提出される, **Then** 提出は拒否され、理由と待機中の既存のジョブの識別子が返る。既存のジョブが実行中または終了済みであれば、受け付けられる。
7. **Given** ジョブ追加の権限を持たない主体, **When** ジョブを提出する, **Then** 権限がないとして拒否される。

### User Story 2 - 権限を持つ利用者が、位置を指定して追加し、スケジュールを変更する (Priority: P1)

利用者は、共用のランナーの待機列を見ながら、順番をどうするかを相談して決める(相談の手段は本 feature のスコープ外)。
スケジュール変更の権限を持つ利用者は、相談の結果に従い、次の 2 つの操作で待機列に反映する。

- **位置を指定した追加**: 新しいジョブを、指定した待機中のジョブの前、または後に追加する。突発の依頼(割り込み)は、待機列の先頭のジョブの前に追加することで扱う。
- **スケジュール変更**: 誰のジョブかを問わず、待機中のジョブを、指定した待機中のジョブの前、または後に移す。

どちらの操作も、実行中のジョブを止めない。

**Why this priority**: 既存の仕組みの最大の不満(運用中に順序を制御できない、突発の依頼に対応できない)を解消する、本 feature の存在理由そのもの。

**Independent Test**: 複数の提出者のジョブを待機させた状態で、スケジュール変更の権限を持つ利用者が、指定したジョブの前後へのジョブの追加と、他人のジョブの前後への移動を行い、待機列の並びと次の割り当ての順序が変わること、実行中のジョブが影響を受けないこと、権限のない利用者の操作が拒否されることを確認する。

**Acceptance Scenarios**:

1. **Given** ジョブ A、B、C がこの順に待機中で、ランナーがジョブを実行中, **When** スケジュール変更の権限を持つ利用者が、新しいジョブ X を A の前に追加する, **Then** 待機列は X、A、B、C の順になり、X は次に空いたランナー(条件を満たすもの)に割り当てられ、実行中のジョブは止まらずに続く。
2. **Given** ジョブ A、B、C がこの順に待機中, **When** スケジュール変更の権限を持つ利用者が、新しいジョブ X を A の後に追加する, **Then** 待機列は A、X、B、C の順になる。
3. **Given** ジョブ A、B、C がこの順に待機中, **When** スケジュール変更の権限を持つ利用者が C を A の前へ移す, **Then** 待機列は C、A、B の順になり、次の割り当てで C が先に割り当てられる。
4. **Given** ジョブ A、B、C がこの順に待機中, **When** スケジュール変更の権限を持つ利用者が A を B の後へ移す, **Then** 待機列は B、A、C の順になる。移したジョブ以外の相対的な順序は変わらない。
5. **Given** 他人のジョブが待機中, **When** スケジュール変更の権限を持つ利用者がそれを移す, **Then** 移動は受け付けられ、移した利用者・移動前後の位置が監査ログに残る。
6. **Given** スケジュール変更の権限を持たず、ジョブ追加の権限だけを持つ利用者, **When** 位置を指定してジョブを追加しようとする、またはジョブを移そうとする, **Then** 権限がないとして拒否され、ジョブは追加されず、待機列は変わらない。
7. **Given** 実行中または終了したジョブ, **When** それを移そうとする、またはそれを基準に追加・移動しようとする, **Then** 待機中のジョブだけが対象・基準になれるとして拒否される。

### User Story 3 - 待機中のジョブを取り消し、実行中のジョブを強制中断する (Priority: P2)

提出者は自分の待機中・実行中のジョブを中断できる。他人のジョブについては、取り消しの権限を持つ利用者が待機中のジョブを取り消し、強制中断の権限を持つ利用者が実行中のジョブを強制中断できる。2 つは別の権限で、片方だけを付与できる。中断は理由とともに記録される。
実行中のジョブが、位置を指定した追加やスケジュール変更などによって自動で止められることはない。

**Why this priority**: 誤った提出や不要になったジョブで、ランナーや待機列が塞がれ続けることを防ぐ。スケジュール変更(US2)を補う運用操作。

**Independent Test**: 待機中のジョブの取り消しと、実行中のジョブの強制中断を行い、状態・中断理由・中断者が記録されること、権限のない中断が拒否されることを確認する。

**Acceptance Scenarios**:

1. **Given** 自分の待機中のジョブ, **When** 提出者が取り消す, **Then** ジョブは中断の状態で終了し、待機列から外れ、ランナーに割り当てられない。後ろのジョブは 1 つずつ前に詰まる。
2. **Given** 他人の実行中のジョブ, **When** 強制中断の権限を持つ利用者が理由を添えて強制中断する, **Then** 中断の要求と理由が記録され、ランナーが停止を確認した時点でジョブは中断の状態で終了する。
3. **Given** 他人のジョブ, **When** 取り消し・強制中断の権限を持たない提出者が中断しようとする, **Then** 権限がないとして拒否され、ジョブの状態は変わらない。
4. **Given** 他人の待機中のジョブ, **When** 取り消しの権限を持つ利用者が取り消す, **Then** ジョブは中断の状態で終了し、待機列から外れる。
5. **Given** 他人の実行中のジョブ, **When** 取り消しの権限だけを持ち、強制中断の権限を持たない利用者が中断しようとする, **Then** 権限がないとして拒否され、ジョブは実行を続ける(逆に、強制中断の権限だけでは他人の待機中のジョブを取り消せない)。
6. **Given** 終了済み(成功/失敗/中断)のジョブ, **When** 誰かが中断しようとする, **Then** 不正な状態遷移として拒否される。

### User Story 4 - 終了したジョブをやり直す (Priority: P2)

ジョブ追加の権限を持つ利用者は、誰のジョブかを問わず、終了したジョブをやり直せる。やり直しはジョブの追加と同等に扱う。
やり直しは、元のジョブの定義(出所のリビジョンを含む)を引き継いだ新しいジョブを作り、通常の提出と同じく待機列に並べ(指定がなければ最後、スケジュール変更の権限があれば指定したジョブの前後)、元のジョブとの関連を残す。元のジョブは変更されない。

**Why this priority**: 突発の不具合や一時的な失敗のあとに、同じ条件で再実行する運用が日常的に発生する。再提出の手間と、条件の取り違えを防ぐ。

**Independent Test**: 終了したジョブをやり直し、新しいジョブが同じ定義で待機列の最後に入ること、新旧の関連がどちらからも確認できること、元のジョブが変わらないことを確認する。

**Acceptance Scenarios**:

1. **Given** 失敗で終了した自分のジョブ, **When** 提出者がやり直す, **Then** 同じ定義(出所のリビジョンを含む)の新しいジョブが待機列の最後に入り、新しいジョブから元のジョブを、元のジョブからやり直しのジョブを辿れる。
2. **Given** 終了したジョブ, **When** やり直す, **Then** 元のジョブの状態・結果・記録は変更されない。
3. **Given** 待機中または実行中のジョブ, **When** やり直そうとする, **Then** 終了していないジョブはやり直せないとして拒否される。
4. **Given** 元のジョブの要件を満たしうるランナーが、現在 1 台も登録されていない, **When** やり直す, **Then** 通常の提出と同じく、理由とともに拒否される。
5. **Given** 他人の終了したジョブ, **When** ジョブ追加の権限を持つ利用者がやり直す, **Then** 新しいジョブが待機列の最後に入り、やり直した利用者が新しいジョブの提出者になる。元のジョブとの関連は残る。
6. **Given** 終了したジョブ A と、待機中のジョブ B, **When** スケジュール変更の権限を持つ利用者が、A を B の前に置く指定でやり直す, **Then** 新しいジョブが B の直前に入る。スケジュール変更の権限がなければ、位置の指定は権限がないとして拒否され、ジョブは作られない。
7. **Given** ジョブ追加の権限を持たない主体, **When** 自分または他人の終了したジョブをやり直そうとする, **Then** 権限がないとして拒否される。

### User Story 5 - ジョブの状態と結果を確認する (Priority: P2)

すべての利用者が、全員のジョブの状態と結果、待機列の並び順を確認できる。

**Why this priority**: 提出者が「自分のジョブがいつ実行されるか・どうなったか」を知る唯一の手段であり、利用者同士が順番を相談する(US2)材料になる。

**Independent Test**: 複数の提出者のジョブを用意し、一般の提出者にも全件が同じ項目で、待機列の並び順どおりに見えることを確認する。

**Acceptance Scenarios**:

1. **Given** 自分と他人のジョブがある, **When** 一般の提出者が一覧を確認する, **Then** すべてのジョブが、提出者・状態・待機列内の位置・結果とともに見え、待機中のジョブは待機列の並び順で見える。
2. **Given** 他人のジョブの識別子, **When** 一般の提出者がそのジョブを確認する, **Then** 自分のジョブと同じ項目が見える。
3. **Given** 他人のジョブが見えている, **When** 取り消し・強制中断の権限を持たない提出者がそのジョブを中断しようとする, **Then** 見えることは操作の権限を意味せず、権限がないとして拒否される。

### User Story 6 - 状態変更の記録と完了の知らせ(監査ログ・完了イベント) (Priority: P3)

状態を変える操作(提出、スケジュール変更、中断、やり直し、完了)は、誰が・いつ・何をしたかが監査ログに残る。
各ジョブの操作の経緯は全員が見られ、相談で決めた順番がそのとおり反映されたかを当事者が確かめられる。監査ログ全体は管理者が閲覧できる。
ジョブが終了したとき、ジョブ完了のドメインイベントが発行され、通知などの別モジュールが受け取る。送信に失敗しても、イベントは失われない。

**Why this priority**: 運用の追跡と通知の前提だが、受付・順番の制御が先に成り立つ必要がある。

**Independent Test**: 各操作を行って監査ログの記録を確認する。イベントの受け手を一時的に失敗させてジョブを終了させ、受け手の復旧後にイベントが届くことを確認する。

**Acceptance Scenarios**:

1. **Given** 任意の状態変更の操作, **When** 操作が成功する, **Then** 操作者・日時・対象のジョブ・操作の種類・変更前後の値(移動前後の位置、中断理由を含む)が監査ログに残る。
2. **Given** 一般の提出者, **When** 監査ログ全体を閲覧しようとする, **Then** 拒否される。管理の権限を持つ利用者は閲覧できる。
3. **Given** 他人がスケジュール変更で自分のジョブを後ろへ移した, **When** 一般の提出者が自分のジョブの操作の経緯を確認する, **Then** 移した利用者・日時・移動前後の位置が見える。他人のジョブの経緯も同じ項目で見える。
4. **Given** 権限がなく拒否された操作がある, **When** 一般の提出者がジョブの操作の経緯を確認する, **Then** 拒否された操作は経緯に含まれない(監査ログ全体でのみ見える)。
5. **Given** ジョブが成功/失敗/中断で終了する, **When** 終了が確定する, **Then** ジョブ完了イベントが発行される。イベントには識別子と状態などの参照用の情報だけが含まれ、payload やログの本文は含まれない。
6. **Given** イベントの受け手が一時的に受け取れない, **When** ジョブが終了する, **Then** ジョブの終了状態は確定したまま失われず、受け手が復旧した後にイベントが届く。

### Edge Cases

- 追加・移動の基準に指定したジョブ(「B の前へ」の B)が、操作の時点で待機中でない(割り当て済み・中断済み) → 操作は理由とともに拒否される。位置を指定した追加では、末尾への追加に切り替えず、ジョブ自体を受け付けない。利用者は最新の並びを見て操作し直す。
- 待機列が空のときに、位置を指定して追加する → 基準にできるジョブがないため拒否される。位置を指定しない追加(末尾)を使う。
- スケジュール変更と割り当てが同時に起きる → どちらか一方だけが成立する。移すジョブまたは基準のジョブが先に割り当てられた場合、スケジュール変更は「待機中でない」として拒否される。
- 権限を持つ利用者同士が、同じジョブを続けて移す → 後の操作が有効になり、両方の操作が監査ログに残る。
- ジョブを自分自身の前後へ移す → 不正な指定として拒否される。
- 既に B の直前にある A を「B の前」へ移す、など位置が変わらない移動 → 成功として扱い、待機列は変わらない。
- 先頭や末尾へ追加・移動したい → 「先頭」「末尾」を指定する専用の操作は持たない。先頭のジョブの前、末尾のジョブの後を指定する(位置を指定しない追加は、権限を問わず末尾になる)。
- 中断の操作と割り当てが同時に起きる → どちらか一方だけが成立する。待機中として取り消しが成立したジョブは割り当てられず、割り当てが先に成立した場合は実行中のジョブの強制中断として扱う。権限の判定はその時点の状態で行うため、他人のジョブについて取り消しの権限だけを持つ利用者の操作は、割り当てが先に成立していれば拒否される。
- 強制中断の要求のあと、ランナーが停止を確認する前に、ジョブが成功/失敗で終わった → 先に確定した終了を正とし、中断の要求はその旨とともに記録に残す。
- ジョブの受付後に、要件を満たすランナーがすべて登録解除された → ジョブは待機のまま残り、提出時の判定はやり直さない(待機の長期化の扱いはランナー管理 002 で扱う)。
- やり直しのジョブをさらにやり直す → 新しいジョブは直前のジョブとの関連を持ち、関連を辿れば最初のジョブまで遡れる(保持期間を過ぎて削除されたジョブより前には遡れない)。
- やり直しの元のジョブが、保持期間を過ぎて削除された → やり直しのジョブは残り、元のジョブの識別子は「削除済み」として分かる。削除済みのジョブはやり直せない。
- 提出代行の権限を持たない主体が、別の提出者の名義で提出する → 拒否される。
- 提出代行で提出されたジョブ → 名義上の提出者が「自分のジョブ」として中断でき、実際に提出した主体(サービス)も監査ログに残る。
- ジョブ定義に必須の項目(ジョブの種類、ランナー要件、payload、タイムアウト)がない、またはタイムアウトが正の値でない → 理由とともに拒否される。payload の中身は検査しない。
- 終了したジョブをやり直すとき、同じ内容のジョブが既に待機中 → やり直しにも重複の判定(FR-006)を適用し、理由と待機中のジョブの識別子とともに拒否される。
- 別の提出者が、同じ内容のジョブを提出する → 提出者が違っても同じ内容として扱い、理由と待機中の既存のジョブの識別子とともに拒否される。
- 存在しないジョブへの操作 → 「存在しない」という理由とともに拒否される(全ジョブが閲覧可能なため、権限による拒否と区別してよい)。

## Requirements *(mandatory)*

### Functional Requirements

**受付**

- **FR-001**: システムは、ジョブ定義(ジョブの種類、ランナー要件、payload、タイムアウト、任意の出所情報)を、用途に依存しない形で受け付けなければならない。payload は解釈せず、そのまま保持する。
- **FR-002**: システムは、提出時に、ランナー要件を満たしうるランナーが 1 台も登録されていなければ、提出を拒否し、理由を返さなければならない(ランナーが空いているかどうかは判定に含めない)。
- **FR-003**: システムは、必須の項目を欠く、またはタイムアウトが正の値でないジョブ定義を、理由とともに拒否しなければならない。
- **FR-004**: システムは、ジョブ追加の権限を持つ主体からの提出を受け付け、受け付けたジョブに一意の識別子を与え、待機中の状態で待機列に並べなければならない。位置の指定がなければ、待機列の最後に並べる。
- **FR-004a**: スケジュール変更の権限を持つ主体は、提出時に、待機中のジョブを 1 件基準として指定し、その前または後に新しいジョブを追加できなければならない。基準のジョブが待機中でない場合、提出を理由とともに拒否し、ジョブを作らない(末尾への追加に切り替えない)。
- **FR-005**: システムは、優先度・割り込みの概念を持たない。待機列の順序は、追加された位置と、FR-011 のスケジュール変更だけで決まる。
- **FR-006**: システムは、同じ内容(出所・リビジョン・ジョブの種類が同一)のジョブが待機中のときに提出された場合、提出を拒否し、理由と待機中の既存のジョブの識別子を返さなければならない。判定は提出者を問わず行い、やり直しにも適用する。同じ内容のジョブが実行中または終了済みであれば、受け付ける。出所情報を持たないジョブは、この判定の対象としない。
- **FR-007**: システムは、1 人の提出者が同時に待機させられるジョブの数に、上限を設けない。待機列の占有には、利用者同士の相談と、スケジュール変更・中断で対処する。

**順序と割り当て**

- **FR-008**: システムは、待機中のジョブを 1 本の待機列として、明示的な並び順で保持しなければならない。
- **FR-009**: システムは、ランナーが空いたとき、そのランナーで実行できる待機中のジョブのうち、待機列で最も前のものを割り当てなければならない。
- **FR-010**: システムは、1 台のランナーに同時に 2 件以上のジョブを割り当ててはならない。
- **FR-011**: スケジュール変更の権限を持つ主体は、誰のジョブかを問わず、待機中のジョブを、基準として指定した別の待機中のジョブの直前または直後へ移せなければならない(スケジュール変更)。移したジョブ以外の相対的な順序は変えない。変更は、変更後の最初の割り当てから反映される。
- **FR-012**: システムは、移すジョブ、または基準に指定したジョブが待機中でない場合、または両者が同じジョブの場合、スケジュール変更を理由とともに拒否し、待機列を変えてはならない。
- **FR-013**: システムは、実行中のジョブを、位置を指定した追加やスケジュール変更を理由に自動で停止・待機列へ戻してはならない。

**中断**

- **FR-014**: 提出者は自分の、取り消しの権限を持つ主体はすべての、待機中のジョブを取り消せなければならない。取り消したジョブは中断の状態で終了し、待機列から外れ、割り当てられない。
- **FR-015**: 提出者は自分の、強制中断の権限を持つ主体はすべての、実行中のジョブを強制中断できなければならない。システムは中断の要求を記録し、ランナーの停止の確認をもってジョブを中断の状態で終了させる(停止の手順はランナーエージェント 004 で定める)。
- **FR-016**: システムは、中断の理由を記録しなければならない。実行中のジョブの強制中断では、理由の入力を必須とする。

**やり直し**

- **FR-017**: ジョブ追加の権限を持つ主体は、誰のジョブかを問わず、終了したジョブ(成功/失敗/中断)をやり直せなければならない。
- **FR-018**: システムは、やり直しで、元のジョブの定義(ジョブの種類、ランナー要件、payload、タイムアウト、出所情報とそのリビジョン)を引き継いだ新しいジョブを作り、元のジョブとの関連を記録しなければならない。元のジョブは変更しない。
- **FR-019**: システムは、やり直しにも FR-002 と FR-006 の受付の判定を適用しなければならない。
- **FR-020**: やり直しは新しいジョブの追加として扱い、ジョブ追加の権限を要する。並ぶ位置は通常の提出と同じく、指定がなければ最後、スケジュール変更の権限があれば指定したジョブの前後とする(FR-004、FR-004a)。やり直しのジョブの提出者は、やり直しを行った主体とする(元のジョブの提出者は、やり直しの関連から辿れる)。

**状態と閲覧**

- **FR-021**: システムは、ジョブの状態遷移を規則に従って行い、規則にない遷移を拒否しなければならない。少なくとも、待機中 → 実行中 → 終了(成功/失敗/中断)、待機中 → 中断を持ち、終了した状態からは遷移しない(実行中の状態の詳細と、実行中からの遷移の規則は 004 と別途定義する)。
- **FR-022**: すべての利用者は、誰のジョブかを問わず、すべてのジョブの提出者・状態・待機列内の位置・結果を、待機列の並び順で確認できなければならない(ランナーが共用で、利用者同士が順番を相談するため)。閲覧できることは、中断・やり直し・スケジュール変更の権限を意味しない。

**権限**

- **FR-023**: システムは、操作の可否を、ロールではなく権限(permission)の単位で判定しなければならない。少なくとも次の権限を持つ。
  - ジョブ追加: 自分の名義でのジョブの提出(末尾への追加)、すべての終了したジョブのやり直し(末尾への追加)
  - 一般: 自分のジョブの中断、すべてのジョブとその操作の経緯の閲覧
  - スケジュール変更: 指定した待機中のジョブの前後へのジョブの追加、すべての待機中のジョブの、指定したジョブの前後への移動(一般の利用者にも付与できる)
  - 取り消し: すべての待機中のジョブの取り消し
  - 強制中断: すべての実行中のジョブの強制中断
  - 管理: 監査ログ全体の閲覧
  - 提出代行(サービス用): 別の提出者の名義でのジョブの提出
- **FR-024**: システムは、提出者の本人性を自ら検証せず、呼び出し元が認証済みの主体と権限を渡すことを前提とする。提出代行では、名義上の提出者と、実際に提出した主体の両方を記録する。

**監査とイベント**

- **FR-025**: システムは、状態を変える操作(提出(位置の指定を含む)、スケジュール変更、中断の要求と確定、やり直し、完了)のすべてについて、操作者・日時・対象・操作の種類・変更前後の値(位置を指定した追加では基準のジョブと前後、スケジュール変更では移動前後の位置)・理由を監査ログに残さなければならない。拒否された操作のうち、権限による拒否も記録する。
- **FR-026**: すべての利用者は、誰のジョブかを問わず、ジョブごとの操作の経緯(成功した提出・スケジュール変更・中断の要求と確定・やり直し・完了の、操作者・日時・変更前後の値・理由)を確認できなければならない。管理の権限を持つ主体は、権限による拒否の記録を含む監査ログ全体を閲覧できなければならない。
- **FR-027**: システムは、ジョブの終了(成功/失敗/中断)が確定したとき、ジョブ完了イベントを発行しなければならない。イベントの発行は終了の確定と一体で記録し、受け手への送信に失敗しても、終了の状態とイベントが失われてはならない(受け手は同じイベントを複数回受け取りうる)。

**依存しないこと・機密保護**

- **FR-028**: コアは、特定のプラットフォーム(提出元)・用途・実行ツールの語を含まず、それらの部品に依存してはならない。この性質は自動の検査で確認できなければならない。
- **FR-029**: コアは、外部への送信を自ら行ってはならない。外部への書き出しは、ポート(通知、結果の書き戻し)を経由し、書き出し台帳(inputs/13-security-egress)に載った内容だけとする。
- **FR-030**: コアは、外部へ渡すイベントに、payload とログの本文を含めてはならない(参照用の識別子のみ)。

**保持**

- **FR-031**: システムは、終了したジョブ(定義・結果の要約・中断の記録を含む)を、終了日時から保持期間を過ぎたあとに自動で削除しなければならない。保持期間は設定値で変えられ、既定は 1 年とする。待機中・実行中のジョブは削除しない(ログ本文・成果物の保持は 004 で扱う)。
- **FR-032**: システムは、監査ログの記録を、記録日時から保持期間を過ぎたあとに自動で削除しなければならない。保持期間は設定値で変えられ、既定は 3 年とする。監査ログの保持期間は、ジョブの保持期間より短く設定できない(削除されたジョブの経緯を、監査ログで追えるようにするため)。

### 外部への書き出し(憲章 S2)

コア自身は外部へ何も送信しない。コアから外へ出る情報は、次のポート経由のものだけである。

| 経路 | 内容 | 台帳の対応 | 制限 |
|---|---|---|---|
| ジョブ完了イベント(通知 007 などが受け取る) | ジョブの識別子、状態、終了日時、やり直しの関連の識別子、提出者の識別子 | E10(通知)の元データ | payload・ログの本文・成果物の中身を含めない |
| 結果の書き戻しのポート(GitHub 連携 005 などが実装) | ジョブの識別子、状態、出所情報(参照用) | E9(書き戻し)の元データ | ログの本文・成果物の中身・ランナーの情報を含めない |

上記以外の書き出しを加える場合は、台帳の更新とレビューを要する。

### Key Entities *(include if feature involves data)*

- **ジョブ(Job)**: 1 回の外部ツール実行の依頼。識別子、ジョブ定義、提出者、提出時刻、状態、割り当てられたランナーの識別子、結果の要約、中断の記録、やり直しの元のジョブの識別子を持つ。状態の変更はジョブを通してのみ行う。
- **待機列(Queue)**: 待機中のジョブの明示的な並び。並びの変更は、追加(提出・やり直し。最後、または指定したジョブの前後)、取り出し(割り当て・取り消し)、スケジュール変更(指定したジョブの前後への移動)だけで起きる。
- **ジョブ定義(Job Definition)**: ジョブの内容。ジョブの種類、ランナー要件、payload(コアは解釈しない)、タイムアウト、出所情報(参照用。リビジョンを含みうる)。やり直しではそのまま引き継ぐ。
- **ランナー要件(Runner Requirement)**: ジョブの実行に必要なランナーの能力の条件。条件の文法と判定はランナー管理(002)が定め、コアの受付は「満たしうるランナーがいるか」の判定結果だけを使う。
- **提出者(Submitter)**: ジョブの名義上の主体。認証済みの識別子と権限の集合として渡される。提出代行では、実際に提出した主体も併せて持つ。
- **中断の記録**: 中断の要求者、要求日時、理由、確定日時。
- **やり直しの関連**: 新しいジョブから元のジョブへの参照。元のジョブからも辿れる。
- **監査ログの記録**: 操作者、日時、対象のジョブ、操作の種類、変更前後の値、理由、結果(成功/拒否)。
- **ジョブ完了イベント**: ジョブの終了を知らせるドメインイベント。参照用の識別子と状態だけを持つ。
- **ランナー(参照のみ)**: ランナー管理(002)のもの。コアのジョブ側は識別子で参照し、内部状態を直接持たない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 位置を指定した追加とスケジュール変更は、受け入れシナリオのすべてで、指定どおりの位置に並び、変更後の最初の割り当てに反映される(反映されない例が 0 件)。
- **SC-002**: 位置を指定せずに提出・やり直しされたジョブが、待機列の最後以外に並んだ例が 0 件である。
- **SC-003**: 位置を指定した追加・スケジュール変更・新しい提出によって、実行中のジョブが止められたり待機列へ戻されたりした例が 0 件である。
- **SC-004**: 権限を持つ利用者は、相談の結果を、待機中のジョブ 1 件につき 1 回の操作で待機列に反映でき、ほかのジョブの実行を止めずに済む。
- **SC-005**: 提出の受付/拒否の結果は、提出から 2 秒以内に返る(待機中のジョブ 500 件、ランナー 50 台の規模で、95% 以上)。
- **SC-006**: 権限のない操作(ジョブ追加の権限を持たない主体による提出・やり直し、取り消しの権限を持たない主体による他人の待機中のジョブの取り消し、強制中断の権限を持たない主体による他人の実行中のジョブの強制中断、スケジュール変更の権限を持たない主体による位置を指定した追加・やり直しとスケジュール変更)は、権限の組み合わせを網羅したテストで 100% 拒否される。
- **SC-007**: 状態を変える操作の 100% が監査ログに記録され、成功した操作は、対象のジョブの操作の経緯として全利用者が操作者・日時・内容を確認できる。
- **SC-008**: ジョブの終了の 100% について完了イベントが少なくとも 1 回届く。受け手が一時的に停止していた場合も、復旧後に届く。
- **SC-009**: コアに用途固有の語・プラットフォーム固有の語・それらの部品への依存が存在しないことを、自動の検査で確認でき、検出が 0 件である。
- **SC-010**: 外部へ渡すイベントに payload・ログの本文が含まれた例が、検査で 0 件である。

## Assumptions

- 提出者の本人性とその権限は、呼び出し元(コア API 003 と認証のアダプタ)が確認済みとして渡す。コアは認証を行わない。
- 「要件を満たしうるか」の判定(能力と要件の照合)と、ランナーの登録・稼働状態は、ランナー管理(002)が提供する。コアはその結果を使う。
- 実行中の状態の詳細(実行の開始、停止の確認、リース切れなど)と、そこからの遷移の規則は 004 と別途定義する。本 spec は待機中・終了と、その間の遷移の枠だけを定める。
- タイムアウトはジョブ定義の一部として保持する。タイムアウトによる停止はジョブ自身の上限であり、FR-013 の「自動で止めない」(他のジョブを理由にした追い出しの禁止)とは別の扱いとして、004 で定める。
- 入力にあった「優先度」は廃止した。「割り込み」は独立した概念としては持たず、スケジュール変更の権限による「先頭のジョブの前への追加」として扱う。
- 順番をどうするかの相談(話し合いの場、合意の取り方、依頼の受け付け)はスコープ外とする。コアは、相談の結果を反映する位置を指定した追加とスケジュール変更の操作と、相談の材料になる待機列の閲覧だけを提供する。
- スケジュール変更の権限を誰に付与するかは運用で決める(全利用者に付与してもよい)。取り消し・強制中断の権限も同様に運用で付与する。管理の権限は、ジョブ追加・スケジュール変更・取り消し・強制中断の権限を自動では含まない(必要なら併せて付与する)。
- 提出代行(サービス)が位置を指定して追加する場合は、その主体にスケジュール変更の権限も要る。
- 閲覧の範囲は、ジョブの一覧と状態・結果の要約までとする。ログの本文・成果物の閲覧範囲は 004 で扱う。ジョブごとの操作の経緯は全員が見られ、監査ログ全体の閲覧は管理の権限に残す(FR-026)。
- 重複の判定でいう「同じ内容」は、出所・リビジョン・ジョブの種類の一致とする。payload やランナー要件の違いは見ない(コアは payload を解釈しないため)。
- 待機中のジョブの取り消しでは、理由は任意とする。実行中のジョブの強制中断では、理由を必須とする。
- 規模の目安: ランナーは数十台、同時に待機するジョブは数百件。
