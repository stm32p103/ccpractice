# 憲法 (constitution) の入力

`/speckit-constitution` に渡す原則です。各原則に「理由」と「確かめ方」を付けています。

## 原則

### I. 誤ったアドレスを黙って出さない

解決できない・確信が持てない場合は、推測の値を返さず `ResolveError` を投げるか、`Resolved.notes` に注意を残す。

- 理由: RAM モニタで違うアドレスを見ると、利用者は誤った値を正しいと信じてしまう。エラーより害が大きい
- 確かめ方: 存在しない変数・メンバ、範囲外のインデックス、同名の変数の曖昧さが、エラーになるテストがあること
  (`verification/lvalues.txt` の `!` 行)

### II. 正解はコンパイラに出させる

配置 (オフセット、ビット位置、サイズ) の正しさは、手計算や別ツールではなく、
**同じ処理系でビルドしたコード** (`&(lhs)`、`sizeof`、ビットフィールドだけを全ビット 1 にした初期化イメージ) と比べて確かめる。

- 理由: ビットフィールドの並び、パディング、enum のサイズは処理系ごとに異なり、仕様書の読み違いが起きやすい
- 確かめ方: `dsr-verify-toolchain` がすべて一致すること

### III. 処理系に依存する部分は `sources/` に閉じ込める

`SymbolResolver` と `model` は処理系を知らない。処理系ごとの癖は `DebugInfoSource` の実装
(`sources/dwarf/<処理系>.py` のフックの上書き) と `SymbolAddressSource` の実装で吸収し、
`model` の定義 (オフセットはバイト、ビット位置はリトルエンディアン式に正規化) に揃えて返す。

- 理由: 処理系を追加するたびに中核を直すと、検証済みの処理系を壊す
- 確かめ方: 処理系の追加で `resolver.py`・`model.py`・`sources/dwarf/common.py` に変更がないこと。
  `common.py` を直すのは「標準の DWARF の解釈が誤っていた」場合だけで、その場合は全処理系の検証をやり直す

### IV. コメント形式どうしの衝突を許容しない

ある形式の判定用の正規表現が、ほかの形式のサンプルに合致してはならない。
すべての形式は、サンプルと期待する抽出結果を持つ。

- 理由: 2 つの形式が同じコメントを読めると、パーサの並び順で結果が変わり、誤った単位・LSB を返す
- 確かめ方: `dsr-comment-catalog` が「全形式 OK、衝突 0 件」であること

### V. 利用者の領分に踏み込まない

ライブラリは「左辺値 → 配置と、コメントの抽出結果」までを担当する。次は利用者 (ツール開発者) の責任とし、ライブラリに入れない。

- コメントから作る情報の型 `T` と、その作り方 (`build`)
- 値の加工や上書き (LSB の差し替えなど)
- マクロの展開 (ビルドと同じプリプロセッサで行う)
- 出力形式 (CSV、モニタツールの設定ファイル など)

- 理由: 利用者ごとに異なる要求をライブラリが抱えると、API が膨らみ保守できなくなる
- 確かめ方: 新しい API が上の項目を扱っていないこと

### VI. 自動生成物を手で編集しない

`comments/formats/__init__.py`、`comments/CATALOG.md`、`verification/results/` 以下は、ツールで生成する。

- 確かめ方: 生成コマンドを再実行して差分が出ないこと

### VII. 依存を最小にする

実行時の依存は `pyelftools` だけ。Python 3.12 以上 (型パラメータ構文 `class X[T]` を使う)。

## 完了条件 (すべての変更に共通)

1. `dsr-verify-toolchain verification/toolchains/<処理系>.json` が、検証済みのすべての処理系で
   「正常系がすべて一致 (関数内 static は照合のみ)、エラー期待がすべてエラー」になる
2. `dsr-comment-catalog` が「全形式 OK、衝突 0 件」になる
3. 公開 API を変えた場合は `README.md` と `docs/speckit/06-usage-examples.md` のサンプルが動く
