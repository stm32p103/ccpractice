# 現在の機能の仕様 (ベースライン)

実装済みの機能を、Spec Kit の仕様の形 (何を・なぜ) で記述したものです。新しい機能の仕様は、これを前提に書いてください。

## 背景と目的

組み込みプログラムの開発者は、実機でマイコンの RAM の値を見るとき、RAM モニタツールに
**アドレス** と **マスク** (どのビットを見るか) を設定する。見たい対象はソースコード上の「左辺値」
(変数、配列の要素、構造体のメンバ、ビットフィールド、およびそれらを表すマクロ) で指定されることが多い。
さらに、値を物理量に直すための **単位・LSB (重み)・オフセット・説明** がソースのコメントに書かれている。

本ライブラリは、左辺値とビルド結果 (DWARF 付きの ELF) から、モニタツールの設定に必要な情報を求める。
ソースを変えて再ビルドしても、ビルド結果を読み直すだけで正しいアドレスが得られることを重視する
(重いソース解析をしない)。

## 利用者

- **ツール開発者**: このライブラリを組み込んで、RAM モニタの設定を作るツールを開発する人。
  コメントから作る情報の型や出力形式を自分で決める
- **適合の担当者**: 新しい処理系 (コンパイラ) や新しいコメントの書き方に対応させる人。
  付属のスキルと検証ツールを使う

## 利用者ストーリー

### US1: 左辺値からアドレスとマスクを得る (最優先)

ツール開発者として、`st.ar[1].bits.level` のような左辺値を渡して、読み出すアドレス・幅・マスクを得たい。
RAM モニタの設定を手で計算しなくて済むようにするため。

受け入れ条件:
1. 単純な変数、配列の要素 (多次元を含む)、構造体・共用体のメンバ、それらの組み合わせを解決できる
2. ビットフィールドでは、それを含む格納単位のアドレス・幅と、マスク・シフト量・ビット幅が得られる
3. 外部結合の変数、ファイル内 static、関数内 static を解決できる (static はスコープ指定で区別できる)
4. 結果はコンパイラ自身が計算した値と一致する (05 の検証)

### US2: 値の解釈を知る

ツール開発者として、読み出したデータを符号付き整数・符号なし整数・浮動小数点・真偽値のどれとして扱うかを知りたい。

受け入れ条件: `Resolved.encoding` が `Encoding` (列挙型) で得られ、`match` で分岐できる。
幅は型の名前ではなく `size` (ビットフィールドなら `bit_size`) で判断できる。

### US3: マクロで書かれた左辺値を扱う

ツール開発者として、`ST_AR1_LEVEL`、`SIG(eng, spd)` (`##` で名前を組み立てる)、`CH_M(B, 3)` のような
マクロで書かれた左辺値も解決したい。

受け入れ条件: ビルドと同じプリプロセッサで展開した式を渡せば解決できる。
展開後に残る定数式 (`2 + (1) * 2`) と enum 定数 (`CH_B`、`CH_NUM - 1`) はインデックスとして評価される。

### US4: コメントから単位・LSB などを得る

ツール開発者として、宣言のコメントに書かれた単位・LSB・オフセット・説明を、自ツールの型で受け取りたい。

受け入れ条件:
1. 宣言の行末のコメント、または宣言の直前のコメントから読み取る。配列の要素なら配列の宣言、メンバならメンバの宣言のコメント
2. 複数のコメント形式に対応でき、優先度 (渡したパーサの順) で選ばれる
3. 結果の型 `T` は利用者が決め、形式ごとの抽出結果 (parsed) から `build` で作る

### US5: 新しい処理系に対応させる

適合の担当者として、新しいコンパイラ (例: Green Hills の RH850 向け) の DWARF の癖を、中核を変えずに吸収したい。

受け入れ条件: `dwarf-adapter` スキルで、ビルドの確認 → 調査 → 処理系ごとのクラスの生成 → 検証 が行え、
検証がすべて一致する (04・05)。

### US6: 新しいコメント形式に対応させる

適合の担当者として、利用者が示したソースの抜粋から、新しいコメント形式のパーサを作りたい。

受け入れ条件: `comment-parser` スキルで、正規表現の提案 → 既存形式との衝突確認 (衝突は許容しない) →
parsed の形の確認 → 生成 が行え、`dsr-comment-catalog` が全形式 OK・衝突 0 件になる (04・05)。

## 機能要件

| ID | 要件 |
|---|---|
| FR-01 | 入力は DWARF 付きの ELF。map ファイルは使わない |
| FR-02 | 左辺値の文法: `識別子`、`.メンバ`、`[定数式]`、括弧。定数式は 10/16 進の整数 (u/l の接尾辞可)、enum 定数、`+ - * / % << >>`、単項の `- ~`、括弧 |
| FR-03 | スコープ指定: `ファイル名::変数`、`関数名::変数`、`ファイル名::関数名::変数` |
| FR-04 | 結果 `Resolved` は、アドレス、幅、マスク・シフト量・ビット幅 (ビットフィールドのみ)、型名、`Encoding`、`Linkage`、ルート変数のアドレスとそこからのオフセット、コメントの解析結果 `T`、コメントを探した位置、注意事項を持つ |
| FR-05 | ビットフィールドの読み出し幅は宣言型の幅。宣言型の格納単位をまたぐ場合は、範囲を覆う最小の 1/2/4/8 バイトとし、注意事項に記録する |
| FR-06 | ルート変数が volatile なら、メンバの型名にも volatile を付ける |
| FR-07 | アドレスはデバッグ情報のものを優先し、なければ ELF のシンボル表から補う。両方ある場合は照合し、食い違えば注意事項に残す |
| FR-08 | 次の場合は `ResolveError`: 変数がない、同名の変数が複数ありスコープで絞れない、メンバがない、配列でないものへの `[]`、構造体でないものへの `.`、範囲外のインデックス、ビットフィールドの先をたどる、アドレスが得られない、未対応の DWARF の表現 |
| FR-09 | コメントの候補は「宣言の行で始まる行末コメント」→「宣言の直前の行で終わる、行頭からのコメントのまとまり (連続する `//` 行は 1 件に連結)」の順。文字列リテラル中の `//` は無視する |
| FR-10 | コメントパーサは、パーサの優先度を外側、コメント候補を内側にして試し、最初に結果を返したものを採用する |
| FR-11 | コメントパーサは `parse(comment) → extract(comment) → build(parsed)`。`extract` は形式ごと (ライブラリ側)、`build` は利用者が実装する |
| FR-12 | 利用者が使うものは `import dwarf_symbol_resolver` の 1 か所から import できる |

## 範囲外 (やらないこと)

| 項目 | 理由 |
|---|---|
| ポインタを経由した参照 (`p->x`、`*p`) | 実行時にアドレスが変わり、静的に決まらない |
| 自動変数 (スタック上の変数) | 固定アドレスを持たない |
| マクロ展開 | 処理系の事前定義マクロやビルドオプションを再現できず、ビルドと違う展開になる危険がある。利用者がビルドと同じプリプロセッサで行う (06 にやり方) |
| map ファイルの読み込み | DWARF だけで解決できる。map は処理系ごとに書式が違い、static が出ないものもある |
| 値の上書き (LSB の差し替えなど) | 利用者が `Resolved` を受け取ってから加工すればよい (原則 V) |
| ソースコードの構文解析 (clang など) | 配置は DWARF、コメントは宣言の位置 (DWARF の `decl_file`/`decl_line`) から読めば足りる |
| `sizeof`・キャストを含むインデックス | 未対応 (07 の候補) |
| ビッグエンディアン | 未対応。ビットフィールドで `ResolveError` になる (07 の候補) |

## 成功の基準

- 検証済みの処理系 (arm-none-eabi-gcc、DWARF 2/3/4/5) で、検証用の左辺値 32 件がすべて期待どおり
  (正常系 29 件: コンパイラの正解と一致 28 件 + 関数内 static のシンボル表との照合 1 件、エラー期待 3 件: すべてエラー)
- 処理系やコメント形式の追加で、中核 (`resolver.py`、`model.py`、`sources/dwarf/common.py`) を変えずに済む
