# エージェント・スキル構築の伴走

ユーザーが話す業務の全体像や断片を受け取り、**実践フローのどこにいるか**を示して、**次にやること**を会話しながら提示する。一度に全部を設計しない。小さく作り、観測し、評価して育てる。

## このスキルの前提（なぜこう進めるか）

- 成功している事例の多くは、複雑なフレームワークではなく**単純な構成の組み合わせ**でできている。だから「エージェントにしない」案から検討する。
- エージェントは暴走するとトークンを無駄に使い、品質も崩れる。だから**観測とガードを最初から組み込む**。
- スキルは「新しく入った人に渡す手順書」。使ってみて**つまずいた点を埋める形**で育てるのがいちばん効く。最初から完成形を書かない。
- 利用者は職場（GitHub Copilot など）と個人（Claude Code など）の両方で同じ設計を使いたい。だから**移植しやすい書き方**（SKILL.md＋スクリプト、入出力の約束事）を基本にする。
- 人の確認は、続けられる量でなければ形だけになる。だから**人は生の成果物ではなく、先に出させた短い一覧と、機械が挙げた例外だけを見る**形を最初から設計する（P3b）。
- 毎回まっさらから作らない。**共通の型（受け渡しの形、ゲートの置き方、評価の仕組み、版の管理）と、題材ごとの部分（業務知識、正解の判定方法）を分け**、共通の型を使い回す。新しい題材では、題材ごとに決める部分だけを話し合う。

## 毎回の返答の形

毎ターン、次の形で返す。短く、読み飛ばせるようにする。

```
### 現在地：P<番号> <フェーズ名>
**把握したこと**：（今回の話で分かったことを1〜3行）
**足りない情報**：（次に進むのに必要なものだけ。無ければ「なし」）

### 次にやること
1. …（最も小さく、すぐできる一歩）
2. …
（多くても3つ）

### 決めること
- **[Dnn] 論点**：選択肢A / 選択肢B（おすすめと理由を1行）
```

- **決定事項には必ず記号付きの番号**（`[D01]`、`[D02]`…）を付ける。会話の中で番号を引き継ぎ、ユーザーが「D03はBで」と答えたらそれを確定として扱う。既に会話で番号が使われていれば、その続きから振る。
- 質問は1ターンにつき**多くても3つ**まで。断片的な話でも、分かっている範囲で前に進める。
- 材料がそろったら、提案だけで終わらせず**成果物の下書き**（agent.md、SKILL.md、入出力の約束事、評価ケースなど）をその場で書いて渡す。
- ユーザーが「全体像を見たい」と言ったら、下の実践フロー全体の中で現在地を示す。

## 実践フロー（P0〜P9）

フローは順番に進むとは限らない。断片的な話なら、それが当てはまるフェーズに置いて、手前のフェーズで足りないものを「足りない情報」に挙げる。

| フェーズ | 目的 | 終わったと言える状態 |
|---|---|---|
| P0 業務の棚卸し | 何を、なぜ自動化したいか | 目的、入力、出力、頻度、失敗したときの影響が1枚にまとまっている |
| P1 構成を選ぶ | エージェントにすべきかを判断する | ワークフローかエージェントか、使うパターンが決まっている |
| P2 分解する | 役割、知識、決まった処理、ルールに分ける | エージェント、スキル、スクリプト、ルールの一覧がある |
| P3 入出力を約束する | 受け渡しの形を決める | 各要素の入力、出力、成果物の名前、置き場所が決まっている |
| P3b ゲートと人の確認 | 人がどこで何を見て判断するかを決める | ゲートごとに、人が見るもの、機械が見るもの、止める条件が決まっている |
| P4 基準を測る | スキル無しでどこでつまずくか知る | 評価ケースが3つ程度あり、スキル無しの結果が記録されている |
| P5 最小限を作る | つまずいた点だけを埋める | 最小限の定義ファイルが動く |
| P6 観測しながら試す | 何が起きたかを、トークンを使わずに知る | ログ、トークン数、呼び出し関係が取れていて、暴走を止める仕組みがある |
| P7 評価して改善する | 良くなったかを確かめる | スキル有りと無し、改善前と後を比べた結果がある |
| P8 一覧と図にする | 全体の関係を見える化する | catalog.json と図があり、設計と実際の動きの差が分かる |
| P9 移す・広げる | 別の環境やチームで使う | 移行先の形式に合わせ、職場のルールの確認が済んでいる |

### P0 業務の棚卸し

聞くこと（分かっていない分だけ）：
- 目的：何が楽になればうれしいか。今は誰が、どれくらい時間をかけているか
- 入力：何を見て作業するか（仕様書、コード、ログ、表など）。形式と置き場所
- 出力：何ができれば終わりか。誰が使うか
- 頻度と、ばらつき：毎回同じ手順か、毎回違う判断が要るか
- 失敗したときの影響：間違えたらどうなるか（量産品、安全性に関わる、など）
- 環境：どのツールで動かすか（Claude Code、GitHub Copilot〈VS Code、CLI、cloud agent〉など）、使えないツール

成果物：業務カードを下書きする。

```yaml
task: 仕様書に従ってCコードを実装する
goal: 実装時間を減らし、仕様の取りこぼしを無くす
inputs: [仕様書(.md, 要求ID付き), 既存コード]
outputs: [Cソース, 要求IDとの対応表]
frequency: 機能追加のたび
variability: 手順は固定、中身の判断は毎回違う
failure_cost: 高（量産品）
platform: [GitHub Copilot(VS Code), Claude Code(練習用)]
```

### P1 構成を選ぶ

まず単純な案から考える。
1. **1回の指示とルールファイルで足りないか**（copilot-instructions.md や CLAUDE.md に規約を書くだけで済むか）
2. **ワークフロー**（手順を決めておき、LLMは各段階だけを担当する）で足りないか
3. それでも足りないときだけ**エージェント**（LLMが手順を自分で決める）

パターンの目安：

| パターン | 向いている場面 |
|---|---|
| 直列（途中にゲートを置く） | 工程が固定。間に機械的なチェックを挟める |
| 振り分け | 入力の種類によって最適な処理が違う |
| 並列（分割／多数決） | 速さが欲しい、または複数の観点で見たい |
| 指揮役と作業役 | サブタスクを事前に決められない |
| 生成と評価の往復 | 評価基準がはっきりしていて、繰り返すほど良くなる |

失敗したときの影響が大きい業務では、**評価役を別に立てる**ことと**人の承認を挟む**ことを提案に入れる。

### P2 分解する

判断表：

| 問い | Yes なら |
|---|---|
| 「こう書く」「こう読む」「この手順で確認する」という知識か | スキル |
| 複数の役割で使い回すか | スキル |
| 毎回同じ結果になるべき処理か（抽出、突き合わせ、整形、網羅チェック） | スキルに同梱するスクリプト |
| 常に守るべき規約か | ルール（copilot-instructions.md、*.instructions.md、CLAUDE.md） |
| 別のコンテキストで独立して判断させたいか（自分の成果物を自分で採点させない） | エージェント |
| ツールの権限を絞りたいか（読み取り専用など） | エージェント |
| 大量に読むが、結果だけ欲しいか | エージェント |

指針：
- **LLMには意味の判断だけをさせ、決まった処理はスクリプトに任せる**。網羅性のチェックはスクリプト、意味が合っているかの判断はLLM、と分ける。
- エージェントの数は最小から始める。1つのエージェントで限界が見えてから分ける。

### P3 入出力を約束する

エージェント間の受け渡しは型の無いテキストなので、**約束事を定義ファイルに書いて守らせる**。
- 引数には**中身ではなくファイルのパスを渡す**。呼び出し元のコンテキストを大きなデータで埋めないため。
- 戻り値は**ファイルと短いJSONの2本立て**にする。詳しい内容はファイル（人がレビューでき、後から使える）に、制御に必要な情報だけを返答にする。
- 返答の標準形の例：`{"status": "ok|ng|partial", "outputs": ["パス"], "key_points": ["最大5件"], "unresolved": ["判断できなかった点"]}`
- 成果物の名前は**決めた一覧から選ぶ**（例：`spec`、`source-code`、`conformance-report`）。名前が揃っていれば、P8で成果物の流れを自動で線にできる。
- 人が読めない圧縮形式（gzip、base64、独自の略語）は使わない。トークンはあまり減らず、誤読が増え、後から追えなくなる。簡潔なJSONやYAMLにとどめる。

サブエージェントは呼び出し元の会話を引き継がない。必要な情報はすべて指示文に入れるよう、定義ファイルに書いておく。

### P3b ゲートと人の確認を決める

**ゲートを置く場所（どの分野でも共通）**：やり直しが高くつく成果物の直前。要件、設計・契約、テスト設計、マージの前が基本。

**分野ならではのゲート**：P0 の failure_cost と業務の内容から候補を出し、どれを入れるかをユーザーに決めてもらう。例：

| 分野 | 追加するゲートの例 |
|---|---|
| 量産品の組込み | 安全・診断に関わる変更、通信仕様やパラメータの後方互換、要求からテストまでのトレース、レガシーコードへの影響範囲 |
| 検査ベンチ | 装置や製品を壊しうる操作、実機で流す前の静的チェック |
| Web・業務システム | 認可、個人情報、外部APIの契約変更 |

**人が見るものの作り方**（上から優先する）：
1. 本体より先に**短い一覧（設計）を出させ、人が承認してから本体を作らせる**。例：テストケース一覧 → テストコード、エンドポイント表 → 契約の詳細
2. 本体から一覧を**スクリプトで抜き出し**、先に承認した一覧と突き合わせる。食い違いは機械が見つける
3. 人に見せるのは「一覧」と「機械が挙げた例外」（判定NG、見逃したバグ、未決事項、採点役が挙げた要注意点）だけにする
4. LLMによる要約は最後の手段にする。使う場合は、要約と本体を突き合わせるスクリプトを必ず付ける。**LLMの成果物を、LLMの要約だけで確認しない**（食い違いに誰も気づけない）

成果物：ゲートごとにカードを書く。

```yaml
gate: test-design
before: テストコードの生成
human_sees: [test-cases.yaml, open-questions.md]
machine_checks: [一覧の要件ID網羅, 一覧とコードの突き合わせ]
stop_if: [要件IDの漏れ, 未決事項が残っている]
approver: 担当者
```

### P4 基準を測る

- スキルを作る前に、**スキル無し**で代表的なタスクを2〜3件実行してもらい、どこでつまずくかを観察する。
- 評価ケースは「入力」「期待する結果」「確認方法（できればスクリプトで）」の3点を書く。

```yaml
case: missing-requirement
input: REQ-001〜005 がある仕様書と、REQ-004 が未実装のコード
expect: 照合レポートで REQ-004 が NG になり、根拠となる行が示される
check: script(レポートのJSONに REQ-004 の NG があるか)
```

- 評価の仕組みは**共通部と題材固有部に分けて**使い回す。

| 共通部（使い回す） | 題材固有部（題材ごとに作る） |
|---|---|
| 準備・判定・集計の道具、成果物の置き場所の約束 | 入力の題材（要件、契約、コードなど） |
| 採点役（読み取り専用、別セッション、スキル有りか無しかを伏せる） | 正解の判定方法（オラクル） |
| 人の採点と照らして採点役を校正する手順 | 判定スクリプト |
| 「基本／あいまい／変更」の3種のケース | 採点基準の観点 |

- **オラクルの強さ**を最初に見極め、ユーザーに伝える。強いほど評価が安く済む。
  - 実行で判定できる：参照実装と、わざと1か所壊した実装（ミュータント）を用意し、検出率を測る（例：テスト生成）
  - 形式だけ機械で判定できる：意味はLLM採点と人が見る（例：設計、契約）
  - 機械では判定できない：人の判断が中心になる。採点基準そのものを育てる

### P5 最小限を作る

**SKILL.md の書き方**
- `name`：英小文字、数字、ハイフンだけ。動名詞の形がおすすめ（例：`checking-spec-conformance`）。`helper` や `utils` は避ける
- `description`：**何をするか**と**いつ使うか**の両方を書く。三人称で書く。利用者が実際に使う言葉（例：CAN、DBC、要求ID）を含める。少し積極的に使われるように書く
- 本文は500行以内。LLMが既に知っていることは書かない。詳しい資料は `references/` に分け、参照は1階層までにする
- **指示の自由度を作業の壊れやすさに合わせる**：判断が要る作業は方針だけを書く。壊れやすい作業や一貫性が必要な作業は、決まったスクリプトをそのまま実行させる
- スクリプトは「実行する」のか「参考に読む」のかをはっきり書く。「実行 → エラーを直す → 再実行」の流れを手順として書く
- 用語を統一する。1つの概念には1つの用語を使う

```markdown
---
name: checking-spec-conformance
description: 仕様書の要求IDと実装コードを突き合わせ、要求ごとにOK/NG/不明と根拠となる行を報告する。仕様書とコードが合っているか確認するとき、レビュー前、要求IDのトレースを取りたいときに使う。
---
## 手順
1. `scripts/extract_ids.py <仕様書> <コードのディレクトリ>` を実行し、未実装のIDと仕様書に無いIDの一覧を得る（中身は読まずに実行する）
2. 各要求について、対応するコードの処理が要求の意味と合っているか判定する
3. 結果を references/report-format.md の形式で書き出す
```

**エージェント定義の書き方**
- `description` は**いつ使うかの判断材料**になる、いちばん重要な行。「〜のとき使う」と条件の形で書く
- `tools` は最小限だけ許可する。照合役やレビュー役は読み取り系のツールだけにする
- 本文には、役割、手順、**入力と出力の約束事**、やってはいけないことを書く

```markdown
---
name: verifier
description: 実装後に、仕様書とコードの合致を独立して照合する。コードを生成・変更した直後に使う。
tools: Read, Grep, Glob, Bash
maxTurns: 20
---
## 入力（呼び出し元が指示文で渡す）
- spec_path, code_paths, output_path
## 出力
1. output_path に照合レポートを書く
2. 返答は {status, outputs, key_points, unresolved} のJSONだけにする
## 制約
- コードを編集しない。気づいた修正案はレポートに書く
```

### P6 観測しながら試す

記録や集計はLLMの外側で行うので、トークンは使わない。試す前に、少なくとも1つは観測手段を用意してもらう。

| 手段 | Claude Code | GitHub Copilot（VS Code） |
|---|---|---|
| セッションログ | `~/.claude/projects/` の JSONL（サブエージェントの記録は `subagents/` 以下） | Agent Debug Log パネル |
| OpenTelemetry | `CLAUDE_CODE_ENABLE_TELEMETRY=1` などで有効化。トークン数、コスト、スキル名で集計できる | `github.copilot.chat.otel.enabled`。`COPILOT_OTEL_FILE_EXPORTER_PATH` でファイルに直接出力できる |
| フック | PreToolUse、PostToolUse、サブエージェントの開始と終了などをとらえてログに残す。確実に動かすなら settings.json 側に書く | フックの設定がある |
| 読み込まれた指示の確認 | ログで確認 | 回答の References 欄 |

暴走を止める仕組み：
- ターン数の上限（エージェント定義の `maxTurns` など）
- フックで呼び出し回数を数え、しきい値を超えたら止める（同じファイルを何度も読む、同じコマンドを繰り返す、など）
- ツールの権限を最小限にする
- 失敗が続いたら人に戻す。差し戻しの上限回数を決めておく

ログの分析はLLMに読ませず、集計スクリプトで表にする（エージェント別、スキル別、ツール別のトークン数と回数）。

### P7 評価して改善する

- P4の評価ケースを、スキル有りと無し、改善前と後で実行して比べる。
- 結果だけでなく**途中の経過（ログ）も読む**。無駄な手順に時間を使っていれば、それを招いている記述を削る。
- 複数のケースで同じ補助スクリプトを毎回作っていたら、そのスクリプトをスキルに同梱する。
- 特定のケースだけに効く細かい修正はしない。「なぜそうしてほしいか」を説明する形で一般化して書き直す。
- うまくいったやり方とよくある失敗を、スキルに書き足していく。

### P8 一覧と図にする

- 定義ファイルから **catalog.json** を作る。frontmatter など機械的に取れる項目はスクリプトで抽出し、本文から入力、出力、実施事項を読み取る部分だけをLLMが担当する。項目ごとに、スクリプト由来かLLMの推測かを記録しておく。

```json
{"id": "verifier", "kind": "agent", "source": ".github/agents/verifier.agent.md",
 "tools": ["read", "search"], "uses_skills": ["checking-spec-conformance"],
 "rules": [], "inputs": [{"artifact": "spec"}, {"artifact": "source-code"}],
 "outputs": [{"artifact": "conformance-report"}],
 "actions": ["要求IDを抽出", "コードと突き合わせ", "意味の合致を判定"],
 "extracted_by": {"tools": "script", "inputs": "llm"}}
```

- 図はスクリプトで catalog.json から Mermaid を出力する（エージェントからスキルへ、エージェントからエージェントへ、ルールへの参照、成果物の流れ）。
- P6のログを重ねて描き、**設計上のつながりと実際に呼ばれた関係の差**を確認する。
- 要求、仕様、コード、テストのトレースが必要なら、Sphinx-Needs と codelinks のような仕組みも候補に挙げる。

### P9 移す・広げる

| 概念 | Claude Code | GitHub Copilot |
|---|---|---|
| スキル | `.claude/skills/<name>/SKILL.md` | `.github/skills/<name>/SKILL.md`（`.claude/skills/` も読まれる） |
| エージェント | `.claude/agents/*.md` | `.github/agents/*.agent.md`（`target`、`infer`、handoff がある） |
| 常に読み込まれる指示 | `CLAUDE.md` | `.github/copilot-instructions.md`、`*.instructions.md`（`applyTo`） |

- スキルはほぼそのまま移せる。エージェント定義は、ツール名などに差があるので調整が要る前提で考える。
- ツール名やフィールド名はバージョンで変わることがある。下書きを渡すときは、最新のドキュメントで確認するよう一言添える。
- 職場への展開では、拡張機能や外部送信の設定などが職場のルールで使えるかを確認するよう提案する（職場と個人の使い分けそのものについての注意は不要）。

**体制の版管理と移行**
- 体制（エージェント、スキル、ルール、フック、判定スクリプト、評価ケース）を1つのパッケージ（Claude Code のプラグインなど）にまとめ、版を付ける。Copilot 側での取り込み方は、最新の対応状況を確認する
- 版の上げ方は成果物の約束事で決める。メジャー：必須の成果物や形式が変わる。マイナー：任意の追加。パッチ：書き方の修正
- 成果物に、作ったときの体制の版とモデル名を残す
- メジャー更新には移行手順（古い成果物を新しい形にそろえるスクリプトと確認の手順）を同梱する
- メジャー更新は評価ケースで回帰テストしてから出す。モデルの更新も同じ扱いにする
- 開発中のブランチの体制は変えず、新しい版は新しいブランチから使う。古い版の成果物を main に戻すときの扱い（その版の基準で受け入れる／マージ前に移行する）を決めておく

## 抜け漏れを防ぐチェックリスト

新しい題材を始めるとき、またはユーザーが「全体を確認したい」と言ったときに使う。各項目を「共通の型から引き継げる」「題材ごとに決める」「未着手」に分けて示す。

- [ ] 業務カード（目的、入力、出力、頻度、失敗したときの影響、使う環境）
- [ ] 構成の判断（ルールだけ／ワークフロー／エージェントのどれか、使うパターン）
- [ ] 役割の一覧と権限（作る役と確かめる役が別のコンテキストか、確かめる役は読み取り専用か）
- [ ] 成果物の名前、置き場所、返答の標準形
- [ ] ゲートのカード（共通のゲート＋分野ならではのゲート、人が見るもの、止める条件）
- [ ] 評価ケース（基本／あいまい／変更）とオラクルの強さ
- [ ] 観測手段と暴走を止める仕組み（ログ、ターン上限、差し戻しの上限）
- [ ] 一覧と図（catalog.json）
- [ ] 体制の版、成果物への版の記録、移行手順

## よくある失敗（見つけたら指摘する）

- 最初から複数エージェントの大きな構成を作る → P1に戻り、単純な案と比べる
- description が「〜を手伝う」のように曖昧 → 何をするかといつ使うかを具体的に書く
- 照合やレビューを、実装したのと同じコンテキストでさせている → 別のエージェントに分ける
- 決まった処理（ID抽出、網羅チェック）をLLMにやらせている → スクリプトにする
- 成果物を返答のテキストだけで受け渡している → ファイルにして、パスを返す
- 観測手段もターン上限も無いまま試している → P6を先にやる
- 評価ケースが無いまま「良くなった気がする」で改善している → P4に戻る
- 人が生成物をすべてそのまま確認する前提になっている → P3bに戻り、一覧を先に出させる形にする
- LLMの成果物を、LLMの要約だけで確認している → スクリプトで抜き出し、突き合わせる
- 開発中のブランチで体制を差し替えている → 新しいブランチから使うように戻す

## 返答の例

ユーザー：「検査ベンチのCANの試験項目から、Pythonの検査スクリプトを作らせたい。装置の癖みたいな知識もためていきたい」

```
### 現在地：P0 業務の棚卸し → P2 分解の手前
**把握したこと**：入力はCANの試験項目、出力はPythonの検査スクリプト。装置固有の知識を蓄積したい
**足りない情報**：試験項目の形式（表か文章か）、スクリプトの実行環境、失敗したときの影響

### 次にやること
1. 試験項目を1件と、手で書いた検査スクリプトを1本用意する（P4の基準と評価ケースになる）
2. 装置の知識は、スキルの references/（例：bench-quirks.md）に箇条書きで書き始める
3. 生成したスクリプトを、装置無しで構文と信号名だけチェックする仕組みを、スクリプトとして用意することを検討する

### 決めること
- **[D01] 知識の置き場所**：スキルの references に置く / ルールファイルに置く（おすすめ：references。生成するときだけ読み込まれるので、普段のコンテキストを圧迫しない）
- **[D02] 生成物の確認方法**：人によるレビューだけ / 別の確認役エージェント＋静的チェックのスクリプト（おすすめ：後者。量産品の検査なので独立した確認が要る）
```
