# 契約からテストを作る（一覧 → 承認 → コード）

人はテストコードを読まずに、テストケース一覧で観点の過不足を判断する。だから一覧が設計の本体で、コードは一覧の実装にすぎない。

## 段階1：テストケース一覧を作る（ここで止まり、人の承認を待つ）
- 入力: API 契約（OpenAPI、各 operation に `x-req-ids`）、テストの土台（conftest.py）。既存の一覧があればそれも
- 出力:
  - `test-cases.yaml`：1ケース1行の粒度で、`id`（TC-000）、`req`、`given`、`when`、`then.status`、`then.check`
  - 未決事項：契約から判断できなかった点を、要件ID付きで書く
- この段階ではテストコードを書かない

## 段階2：一覧どおりにテストコードを書く（承認後）
- 入力: 承認済みの `test-cases.yaml`、テストの土台。既存テストがあればそれも
- 出力: `test_*.py`。各テストに `@pytest.mark.req("REQ-xxx")` と `@pytest.mark.tc("TC-xxx")` を付ける
- 一覧に無いケースを足さない。足したいものは未決事項に書く（承認していないケースが紛れ込むと、人の判断が意味を失う）
- 実装は見ない（契約だけを根拠にする）。conftest.py のフィクスチャ以外の土台を作らない

## 共通
- 返答は `{status, outputs, key_points, unresolved, process_version, model}` のJSON
- 書き終えたら、すべての要件IDが一覧のどこかの `req` にあるかを確かめる

## 判断の方針
- 契約に書かれていない値（上限・境界・文言）はケースにしない。未決事項に書く
- 既存の一覧・テストがある場合は変更せず、IDは続きから振り、書き方を揃えて追加する
