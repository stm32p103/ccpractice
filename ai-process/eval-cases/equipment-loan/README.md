# 題材: 備品の貸出・返却

仕様駆動開発の小さな例です。2つのスキルを同じ手順で評価し、性質の違いを比べます。

- A: 要件 → OpenAPI 契約（`drafting-openapi-contract`）
- B: 契約 → テストケース一覧 →（人の承認）→ テストコード（`writing-contract-tests`）

## ケース
| | 基本 | あいまい | 変更 |
|---|---|---|---|
| A | A1 要件v1から契約 | A2 上限値・延滞の定義が無い要件 | A3 契約v1にREQ-009（延長）を追加 |
| B | B1 契約v1から | B3 境界条件が書かれていない契約 | B2 契約v2に合わせて追加 |

## 正解の判定方法（オラクル）
| | A | B |
|---|---|---|
| スクリプト | 形式の正しさ、要件IDの網羅、必要なエラー応答、後方互換、未決事項の記録 | 参照実装で通るか、ミュータント10種の検出率、一覧とコードの突き合わせ、要件IDの網羅 |
| 人が見るもの | 契約の表（操作・要件・応答。追加分に印） | テストケース一覧、見逃したバグ、一覧とコードの食い違い |
| LLM採点 | 意味の反映、設計の自然さ、エラー設計、推測の扱い | 意図の検証、読みやすさ、契約の範囲、推測の扱い |

`fixtures/app/`（参照実装とミュータント）と `selftest/`（模範解答）は、生成役に見せません（答えになるため）。

## 確かめたい仮説
- A は正解が1つに決まらないので、スクリプトで見られるのは形式まで。**採点基準そのものを育てる**必要がある
- B は実行して判定できるので、**スクリプトの判定がそのまま品質の指標になる**
- A では、LLM採点と人の採点がずれやすい
- B では、「通るが弱い」テスト（検出率が低い）が出やすい
