# concept — アイディア出しと構想の整理

目的:開発者の頭の中にある構想を、`/speckit.specify` に渡せる形の **concept.md** にまとめる。
ここでは「何を・なぜ」だけを扱い、**技術や実装方法は書かない**。

## 進め方

1. **聞き取り(1回に最大5問)**
   - 最初に聞くこと:誰が困っているか / 何ができれば嬉しいか / 今回の範囲(機能の一部か全体か)。
   - 選択肢が考えられる質問は (a)(b)… の案を添える。
2. **広げる**
   - 開発者の案に対して、関連しそうなユースケース候補や、見落としやすい観点
     (権限、件数が増えたとき、取り消し・履歴、参照系の検索条件 など)を **提案として** 挙げる。
   - 採用するかは開発者が決める。採用されなかった案は「却下した案」に残す。
3. **集約との関係を確認**
   - `specs/domain/` があれば読み、関係しそうな集約を挙げる。新しい集約が要りそうなら候補として記す。
   - ユースケースごとに「更新系(Command)」か「参照系(Query)」かを付ける。
4. **書き出す**
   - `templates/concept-template.md` の形で `specs/concept/YYYY-MM-<短い名前>.md` に保存する。
   - 決まっていないことは無理に埋めず「未決事項」に `Q1`, `Q2` … として残す。
5. **確認と引き渡し**
   - 開発者に内容を確認してもらう。
   - 次の作業として `/speckit.specify` に渡す依頼文(末尾の「specify への入力」)を提示する。
   - バックログの「機能の進捗」表の concept 欄を `済 <日付>` にする。

## ルール

- 技術(言語・フレームワーク・DB・画面の作り)を書かない。出てきたら「メモ(設計段階で検討)」に退避する。
- 1つの concept に詰め込みすぎない。ユースケースが 7 つを超えたら分割を提案する。
- `/speckit.specify` を実行した concept は、先頭の `status:` を `frozen` にし、
  `specified_as:` に機能フォルダ名を書く。以後は書き換えない。
  後から考えが変わったら、新しい concept を作る。
